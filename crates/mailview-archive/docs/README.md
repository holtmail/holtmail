# holtmail-mailview-archive

The served mail view over the archive: `ArchiveMailView` implements [`MailView` and `MailActions`](../../mailview/docs/README.md) over the store (served tables, effective flags, local flags and places, subscriptions, mail changes, raw drafts, the change log), the blob store, the search index and `holtmail-access`. IMAP, JMAP and later the web app read and change mail through it, so every client sees the same tree, UIDs, flags and states, and every write passes the same five locks the web API checks. It never talks to a mail server and never deletes a message from the archive: a client's write becomes a held mail change for `mail-writeback`, a local flag, a local place, a raw draft or a subscription.

## API

- `ArchiveMailView::new(store, blobs, index, archiver, ViewConfig)`; `archiver` is the outbox's `Archiver`, used to archive the bytes of client appends. Cheap to share; it keeps no state of its own, so every answer reflects the store.
- `ViewConfig { switches, local_flags, append_limit, inline_build, search_cap, structure_cache, expensive_per_user }`: the `[write]` switches, `[serve] local_flags`, `APPENDLIMIT` (50 MiB by default), how many members a read may number by itself in a view that was never built (5 000; a view with more answers `MailViewError::Building { done, total }` until it is built) and how many index matches one search text may have before the search fails with `TooMany` (`MAX_MATCHES`, 100 000), how many parsed structures are kept and how many expensive steps one user runs at once.
- `prepare(viewer, budget) -> Progress { views, built, assigned, total }`: opens every view of the viewer's layout and spends up to `budget` UIDs on views not yet built. The server's build job calls it for every archive a device reads; `Progress::done()` once every view is built.

The contract's guarantees hold as written there; the conformance suite runs against this implementation in `tests/archive.rs` (SQLite store, file blobs, Tantivy index, real ingest, and a `Driver` that settles mail changes the way writeback and sync would).

## How it works

- **Who may look.** A call loads the viewer's user, `holtmail-access`'s role in the archive, the archive's accounts with their capabilities, its folders and the user's subscriptions. No role, no `read` scope or an unknown archive is `NotFound("archive")`.
- **Layout.** One account: its folders at the top, the inbox-role folder as `INBOX`, the drafts-role folder folded into `Drafts`, `All` folders not served. Several accounts: unified role mailboxes, then `Accounts/<account>/<path>`. Levels without a folder are `node:` placeholders; paths are sorted, so parents come first; a `/` inside a name shows as `∕`.
- **Served views.** Each selectable mailbox reads one `ServedKey`: a unified role mailbox its `Role` view, a folder its `Folder` view, `All`, `Kept` and the user's `Drafts`. With one account, a folder that is the archive's only folder with its role reads the `Role` view instead, so the user's local places of that role (a Sent copy no account takes) show in it; adding a second account changes the mailbox keys anyway, and the folder then reads its own view with its own `UIDVALIDITY`, so clients resync once. Reads open a missing view, number up to `inline_build` members, then catch it up.
- **Per-user filtering.** A role view holds every user's local places; the members another user keeps there and that no place of the role holds are left out. A drafts view leaves out compose drafts made in the web app; only raw drafts (a client's bytes) are served. Rendering compose drafts with `holtmail-compose` is moved to a later phase (WORKPLAN, Phase 69 log).
- **Places.** Writes plan on a message's places: live locations with open moves applied (where the message shows) and open expunges removed. A held move that a client moves again or deletes is replaced: `replace_held_mail_changes` fails it with `replaced`, dismisses it and records the new move or expunge from where the location is, in one store step, so the store's membership follows the newest decision. When the writeback worker claimed the held move in between, nothing is written and the email is refused (`Cannot`) as a place being sent. A place whose move is already being sent, or that has no UID yet (an open append), cannot be moved or deleted until sync catches up (`Refusal::Cannot`); flag changes there fall back to local flags.
- **Locks.** `holtmail_access::decide` per account and capability, in its order, then `write_consent_missing` (`Lock::Consent`); import accounts allow nothing. A move uses `holtmail_mail_writeback::capability_for` (into the trash it needs `mail.delete` when the account lacks `mail.move`); a delete is a move to the account's trash (`mail.delete`), or an expunge in the trash, without one, or for JMAP destroy (`mail.expunge`). Every recorded change carries the viewer's user and device, and each action writes one audit entry per account and kind with the message ids, plus `device:<id>` when a device made it (the count stays the number of messages).
- **Appends.** Into a folder or role mailbox: the first account by name whose locks are open; the bytes are archived through the `Archiver` (without a folder), then a held `append` is recorded unless the message already shows there. The received time of a client's append is the archive time. Into Sent with no open account: a local place, with the client's flags as local flags, only when the viewer's switch, grant and `write:mail` scope allow appending and every Sent folder is closed by its account alone (capability or consent), or there is none; it writes a `mail_append` audit entry naming the message and `device:<id>`. Otherwise the viewer's lock is the refusal and nothing is archived. A cross-account move or a copy appends with the place's synced and held flags (never the viewer's local flags, never `\Deleted`). Into `Drafts`: a new raw draft each time. **Sent copies of sent mail:** an append into a Sent mailbox (role `Sent`, unified or a Sent-role folder) by a viewer with `write:mail` or `send:mail` whose `Message-ID` matches one of the same user's outbox messages of the last 24 hours that is not failed or cancelled answers `Applied` with the outbox's archived message (archived from the outbox's own bytes when the outbox has not done so yet; archiving is idempotent per bytes, so it is the message the outbox records later) and its UID in that mailbox. The client's bytes are dropped and nothing is appended upstream, because the identity's sent-copy policy already handled that; when no folder of that mailbox holds the message it becomes the user's local place in `Sent`. The same copy again gives the same answer. Bytes that match nothing take the path above.
- **Flags of moved mail.** Effective flags give a held, sending or applied move's target the source location's synced and held flags until sync records the target, so a moved message keeps `\Seen` and `\Flagged` there.
- **Envelopes.** Stored fields, plus `Sender`, `Reply-To` and `In-Reply-To` parsed from the bytes; `mailboxes` from the places and the viewer's local places, not from the served tables, so it costs no catch-up.
- **Structure.** A small MIME walker over the raw bytes (CRLF and bare LF) with byte ranges for headers and bodies. It stays instead of `mail-parser`: it already gives the byte ranges `BODY[n.MIME]` and JMAP part blobs need, and swapping parsers would change every served structure for no gain the cache does not already give. Parsed structures are derived data kept in memory by blob id (`structure_cache`, 10 000 by default, oldest dropped first), so a second `BODYSTRUCTURE` or part fetch reads no bytes; the access check still runs on every call. A cache miss and every search take one of the user's `expensive_per_user` turns (2 by default); further ones wait.
- **Search.** Text conditions on messages go to the index through `SearchIndex::matching`, narrowed to the dates of the mailbox's members; when even that has more than `search_cap` hits the search fails with `TooMany` instead of treating older hits as misses (and inverting them under `Not`); `Header` conditions and drafts are matched on the bytes. The index matches words and word beginnings (and stems), never a piece from inside a word. Flags, dates, sizes, UID sets and `MODSEQ` are filtered on the members.
- **States and changes.** `state` comes from `ChangeStore::archive_heads` with the viewer's own rows: emails from `message`, `place`, `flags`, `draft` and `thread` rows, mailboxes from `mailbox` rows and what changes counts, threads from `message` and `thread` rows. `changes` pages through the log skipping other users' rows: a `message` row with a thread is a created email, without one a destroyed one; `place` and `flags` rows update; a thread is created when all its messages were created in the window and destroyed when none is left; a folder row marks every layout entry the folder is part of (its own mailbox, the unified role mailbox, the tree levels above it) created when all their folders were made after the window began, else updated, and destroys the unified role mailboxes that no longer exist; a folder that is gone, or one of an account whose folders all appeared inside the window (a new account), is `CannotCalculateChanges`, because every path moves; a subscription row updates the mailboxes with explicit choices; a draft row creates the current version when it is raw and destroys the other kept raw versions, and a deleted draft destroys version 1 (raw drafts start there and only raw versions are served). A `since` above the log's head or below `ChangeStore::pruned_through` is `CannotCalculateChanges`.

## Limits

- Counting unseen members reads effective flags for every member; very large views pay for that on `STATUS` and `SELECT`.
- The server prunes the change log to 90 days; older states answer `CannotCalculateChanges` and views behind the mark rescan.
- Mailbox changes cannot destroy tree levels (`node:*`) that vanish, other than through the `CannotCalculateChanges` of a deleted account; single folders are never removed by the store.
