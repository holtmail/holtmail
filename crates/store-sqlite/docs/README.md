# holtmail-store-sqlite

A [`Store`](../../store/docs/README.md) in one SQLite database file. The default for single-machine installs; with message bytes in a blob store, the database stays small (roughly 1 KB per message).

## Usage

```rust
let store = SqliteStore::open("/var/lib/holtmail/holtmail.db").await?;
```

`open` creates the file when missing and applies the migrations in `migrations/` (embedded into the binary).

```rust
store.snapshot("/backups/holtmail.db").await?; // a consistent copy, safe while others read and write
store.close().await;                            // wait for every connection to close
```

`snapshot(path)` writes a copy of the whole database with `VACUUM INTO`: it holds every write committed before it started and none after, other connections keep working meanwhile, and it refuses a path that exists. `holtmail backup` uses it. `close()` closes every connection so the file is complete on disk; calls after it fail.

## Settings

WAL journal, `synchronous = NORMAL`, foreign keys on, a 10 second busy timeout, up to 8 connections.

## Guarantees and limits

- Reads run in parallel. Writes are serialized inside the process, so one database file must be used by one Holtmail process at a time. Use `store-postgres` for several processes.
- Ids are stored as UUID text, times as Unix milliseconds, addresses and flags as JSON text.
- Message lists use the `(archive_id, date DESC, id DESC)` index and keyset pagination; there is no `OFFSET` and no total count per page.
- `message_extras` answers a page with five queries per 200 ids (thread sizes through the `(thread_id, …)` index, locations through `locations_message`, labels, insight kinds by the `message_insights` key, and the kind and list topic by the `message_categories` key). Unread counts read the flags JSON with `json_each`, so they cost one pass over the folder's locations.
- UIDs, sizes and modseqs above `i64::MAX` are rejected with `StoreError::Invalid`.
- `delete_archive` runs in one transaction and checks each of the archive's blobs against every remaining message, attachment, remote copy and derived record before listing it as orphaned. Grants live in `archive_grants` and cascade with users and archives.
- Settings live in `settings`. Migration 0005 adds `archives.save_remote_images_since` (set to the archive's creation for archives that already saved images) and an index on `(archive_id, archived_at)` for scans by age.
- Remote copies live in `remote_images`, keyed by URL key; `message_remote_images` links messages to them and `remote_scans` marks messages already looked at. `delete_archive` removes the links of the archive's messages, then each copy no other message links, and treats its blob like any other: orphaned only when no message, attachment or other copy uses it.
- Labels live in `labels` (unique per `(archive_id, name)`) and `message_labels`, added by migration 0006 together with `folder_cursors.flags_checked_at`. `set_labels` runs in one transaction and deletes labels left without messages; `list_labels` counts per label with one grouped query and reads `\Seen` from the locations' flags JSON; the label filter of `list_messages` joins `message_labels` and keeps the keyset pagination. `set_flags` stores the flags sorted and deduplicated.
- Derived records live in `derived` (migration 0007), keyed by `(source_blob, kind)` with a nullable `blob_id` for "nothing can be made". `delete_archive` drops the records of every blob it orphans and lists their derived blobs too when nothing else uses them; a blob counts as used when a message, attachment, remote copy or derived record names it. `clear_derived` runs in one transaction.
- The ledger lives in `ledger` (migration 0016): `seq` as the integer key, the fields as text, `prev` and `hash` as hex; indexes on `(message_id, event)` and `(archive_id, event, seq)`. Entries are appended under the writer lock inside the transaction of the change (`insert_message`, `delete_archive`), reading the newest row for `seq` and `prev`, so the order is the commit order. `ledger_gaps` runs three `NOT EXISTS` queries, each with a count and a sample. `forget_derived` deletes one `derived` row with `RETURNING` and checks whether its blob is still used.
- Tombstones live in `deleted_blobs` `(archive_id, blob_id)` and `deleted_locations` `(folder_id, uid)` (migration 0017). `delete_messages` works message by message inside one transaction: tombstones, the links it collects (attachment blobs, remote image keys, labels, calendar version links), then the rows; versions read from mail whose blob no other message links to are deleted and the item's versions renumbered from 1 (negated first, so the key never clashes), and an item without versions loses its `pim_index`, series and instances. Orphans go through the same `release` as `delete_archive`. `folder_uids` is a `UNION` of live locations and tombstones.
- Webhooks live in `webhooks` (events as a JSON array, the sealed secret as a blob) and `webhook_deliveries` (migration 0018) with an `AUTOINCREMENT` id for the order, a partial index on `next_at` for due deliveries and one on `(webhook_id, id)`. `prune_deliveries` numbers finished deliveries per webhook with `ROW_NUMBER()`.
- Aliases (migration 0019): `message_aliases` keyed by message (indexed by `(archive_id, alias)` and, partially, by `(archive_id, reverse_alias)`), `alias_services` (the key as a sealed blob) and `aliases` keyed by `(archive_id, address)`, mailboxes as a JSON array. The view `resolved_addresses` is `message_addresses` with each reverse alias replaced by the sender recorded for it (one per reverse alias, `MAX`), and `mail_addresses` reads it instead of the table; `correspondence` stays on the indexed table and adds the reverse aliases of the wanted senders. `aliases(archive)` merges the known aliases with two grouped queries: messages forwarded to an alias or addressed to a known one (dates from `messages`, senders from the recorded sender or `From`), and per alias the accounts through `locations` and `folders`. `delete_messages` and `delete_archive` remove the rows.
- Insights (migration 0020): `message_insights` keyed by message, `WITHOUT ROWID`, indexed by `(archive_id, fingerprint)`; the outcome as text with a `CHECK`, `signals` and `kinds` as the bit pattern of the `u64` in an `INTEGER` (so all 64 bits round-trip), `auth` and `items` as opaque JSON text. `set_message_insights` checks the message and its archive and runs `INSERT OR REPLACE` in one transaction. `messages_needing_insights` walks `messages` by primary key with a `LEFT JOIN` on the row and `i.message_id IS NULL OR i.fingerprint != ?`; `count_needing_insights` is the archive's message count minus its rows with the current fingerprint (index only). `insight_views_among` and `insights_among` read 200 ids per query. `delete_messages` and `delete_archive` remove the rows before `messages`.
- Categories (migration 0021): `message_categories` keyed by message, `WITHOUT ROWID`, with the trust as text with a `CHECK` (`trust_domain` holds the aligned domain or the relaying provider), `derived_topics` as the bit pattern of the `u64`, `derived_sources` as a JSON object of topic name to source name (unknown names are skipped on read), the effective `kind` and `list_topic`, and `override_ids` as JSON `{kind?, topics?}` (`NULL` when no override applies); indexed by `(archive_id, derive_fp)`, `(archive_id, kind, message_id)`, `(archive_id, sender_address)` and `(archive_id, sender_domain)`. `message_topics (message_id, archive_id, topic)` holds the effective topics by name, keyed by `(message_id, topic)` and indexed by `(archive_id, topic, message_id)`. `category_overrides` is unique per `(archive_id, scope, key)`, with `kind` as a name and `topics` as bits, both nullable. `account_authserv (account_id, ids)` holds each account's trusted authserv-ids as a JSON array; it is a table of its own so `Account` and `NewAccount` keep their fields. `derive_inputs` walks `message_insights` by primary key (the archive term is written `+i.archive_id` so SQLite does not pick the fingerprint index and sort) with a `LEFT JOIN` on the categories row, and reads alias rows and accounts (through `locations` and `folders`) for the page with `json_each` id lists. `set_message_categories` takes the writer lock per batch of 500: it reads the messages' archives, the old effective kinds and topics and the archive's overrides, then `INSERT OR REPLACE`s each row and rewrites `message_topics` only when the effective topics changed. Override edits read the rows matching the key through the sender index, compute the effective values in Rust and write them with one `UPDATE … WHERE message_id IN (json_each(?))` per distinct result and per 5,000 rows, then rewrite the topics of rows whose topics changed. `category_counts` is two `GROUP BY` queries over `message_categories_kind` and `message_topics_filter`. `list_messages` joins `message_categories` (kind) or `message_topics` (topic) and keeps the keyset pagination. `insight_view` reads the insights row, the categories row with its topics (`group_concat` subquery) and, when any applies, the overrides by id: at most three queries. `recent_auth_facts` walks `messages_archived` newest first with an `EXISTS` on the account's locations. `delete_messages` removes the rows and topics before `messages`; `delete_archive` removes the rows, topics and overrides by `archive_id` before `messages`, and the trust lists of its accounts before `accounts`; `delete_account` removes its trust list. `set_message_categories_queued` and the override edits run the queue upsert inside the transaction of their write.
- Reindex queue (migration 0022): `insight_reindex (message_id, archive_id, seq)` keyed by message, `WITHOUT ROWID`, indexed by `(archive_id, message_id)` for the keyset page and the count. `queue_reindex` and the queued writes run `INSERT … SELECT id, archive_id, 1 FROM messages WHERE id IN (json_each(?)) ON CONFLICT DO UPDATE SET seq = seq + 1`, so unknown ids drop out and the archive comes from the message. `dequeue_reindex` deletes `(message_id, seq) IN (json_each(?))` per 500 entries. `delete_messages` and `delete_archive` remove the entries before `messages`.
- Unsubscribe requests (migration 0023): `unsubscribe_requests (id, archive_id, message_id, list_key, requested_at, requested_by, outcome, status)` keyed by id, the outcome as text with a `CHECK`, indexed by `(archive_id, list_key, requested_at)`. `message_id` has no foreign key: `delete_messages` sets it to `NULL` in its transaction before deleting `messages`, so the audit row stays; `delete_archive` deletes the archive's rows before `messages`. `record_unsubscribe` checks the archive and the message's archive and runs `INSERT OR IGNORE` in one transaction, refusing a taken id. `last_unsubscribe` is one `ORDER BY requested_at DESC, id DESC LIMIT 1` read on the index; `last_unsubscribes` picks the newest per key with `ROW_NUMBER()` over 200 keys per query.
- Write foundation (migration 0024): `archive_grants.role` (text with a `CHECK`, default `reader`, so earlier grants read as readers); `set_grants` deletes only the archives not in the new list (`NOT IN json_each`) and inserts the rest with `INSERT OR IGNORE`, keeping their roles. `account_capabilities (account_id, capability)` `WITHOUT ROWID` with `ON DELETE CASCADE`, also deleted explicitly by `delete_account` and `delete_archive`; unknown capability names in it are skipped on read. `audit_log` with an `AUTOINCREMENT` `seq`, ids as text without foreign keys so entries outlive users, archives and accounts, `targets` as a JSON array, indexed by `(archive_id, seq)`; `list_audit` is one keyset query capped at 500. `idempotency_keys (user_id, key, route)` `WITHOUT ROWID`, cascading with the user, indexed by `created_at` for pruning; a held key has `status` `NULL`. `claim_idempotency_key` reads and upserts in one transaction under the writer lock.
- Sending (migration 0025): `transports` (nullable `archive_id` for instance scope, `kind` with a `CHECK`, settings and `allowed_from` as JSON, the limits as nullable columns), `transport_grants (transport_id, archive_id)` cascading with the transport, `identities` (the sent-copy policy as text, `created_by` without a foreign key), `identity_users` and `identity_defaults` cascading with the identity and the user. Drafts are `drafts` (the current `version`, `saved_at` for the list order) and `draft_versions (draft_id, version)` with the payload and blob list as JSON, plus `draft_blobs (draft_id, version, blob_id)` indexed by blob, all cascading from the draft; `save_draft` reads the version, inserts the next and deletes versions older than the newest 50 in one transaction. `outbox` keeps the recipients with their states as one JSON array, `queued_state` (what it started as), ids of identity, transport, user and message as text without foreign keys so rows outlive them, indexed by `(archive_id, id)`, `(transport_id, state)`, `blob_id` and `(archive_id, rfc_message_id)`, with a partial unique index on `(user_id, idempotency_key)`. `change_outbox` checks the state and updates in one transaction under the writer lock; `claim_outbox` is one `UPDATE … WHERE id = (earliest due) AND NOT EXISTS (a sending row of the transport) RETURNING id`. `delete_archive` collects outbox and draft blobs into the blobs it releases and deletes outbox rows, drafts, defaults, identities, grants to the archive and its transports; `delete_account` clears `account_id` on transports and identities. `blob_used` and `referenced_blobs` count `outbox.blob_id` and `draft_blobs`.
- Sent copies and bounces (migration 0026): runs without sqlx's transaction (`-- no-transaction`) so it can turn foreign keys off and rebuild `transports` with `kind` in `smtp`, `jmap`, `graph`, `account` inside its own transaction (SQLite cannot change a `CHECK`; references from `identities` and `transport_grants` keep pointing at the table by name), then turns them back on. `outbox` gains `synced_copy` and `note`, with partial indexes on `message_id` and `synced_copy` for `outbox_for_message` (a `UNION` of the two lookups); `identities` gains `rewritten_from` and `rewritten_at`, cleared by `update_identity` when the address changes (compared case-insensitively). `link_outbox_copy` checks the message's archive in the same transaction.
- Alias reply strategies (migration 0027): `alias_strategies (archive_id, scope, key)` `WITHOUT ROWID` with `scope` in `alias`, `domain`, `service` (a `CHECK`) and the strategy name as text; `set_alias_strategy` checks the archive and upserts or deletes under the writer lock; `delete_archive` deletes the archive's rows.
- Made reverse aliases (migration 0028): `reverse_aliases (archive_id, reverse_alias)` `WITHOUT ROWID` with `alias`, `contact` and `created_at`; `put_reverse_alias` checks the archive and upserts under the writer lock. The migration recreates `resolved_addresses` with these pairs `UNION ALL`ed to the `message_aliases` pairs, skipping a reverse alias `message_aliases` already maps to a sender, and `correspondence` matches their reverse aliases too; `delete_archive` deletes the archive's rows.
- Mail changes (migration 0029): `mail_changes` keyed by id (UUIDv7, so id order is enqueue order), `account_id` and `folder_id` with foreign keys, `message_id`, `user_id` and `outbox_id` as text without foreign keys, `kind`, `origin` and `state` with `CHECK`s, the `MailOp` as JSON in `payload` and an append's blob in `blob_id`; indexed by `(account_id, id)`, and partially by `(account_id, state, id)` and `(folder_id, uid)` for open rows, `(message_id, id)` and `blob_id`. `enqueue_mail_change` checks the account, folders and the message's archive in its transaction under the writer lock. `claim_mail_change` is one `UPDATE … WHERE id = (oldest due held row with no sending or older held row of the same message and account) RETURNING id`, and `due_mail_accounts` uses the same condition; the other state changes are `UPDATE`s guarded by the expected state, so `rows_affected() == 0` means `None`. `confirm_mail_flags` reads the location's open flags and labels rows through the partial index and decides them in Rust oldest first, stopping at the first that stays open. `applied_move_from` reads through the `(message_id, id)` index; `retarget_mail_change` checks the folder's account in its transaction. `delete_account` and `delete_archive` delete the rows before `folders`, and `delete_archive` adds their blobs to the ones it releases; `blob_used` and `referenced_blobs` count `mail_changes.blob_id`.
- Sent copies and retention (migration 0030): a partial index on `mail_changes (outbox_id, id)` for `outbox_mail_changes`. `retention_candidates` joins `locations`, `folders` and `messages` (live located UIDs of the account, `COALESCE(received_at, date)` before the cutoff, optionally no `trash` folder) and skips locations with an open row through the `(folder_id, uid)` partial index and locations with any `retention` row through the `(message_id, id)` index.
- Dismissed failures (migration 0031): `mail_changes.dismissed_at`, set by `dismiss_mail_change` through a state-guarded `UPDATE`, and a partial index on `(message_id, id)` for failed rows not dismissed, read by `failed_mail_changes`.
- Item changes (migration 0032): `collections.write_mode` (text with a `CHECK`, added as `read_only` and set to `held` for collections with an account; `upsert_collection` picks it on insert, `delete_account` resets its collections to `read_only`), `items.dav_name` with a partial unique index on `(collection_id, dav_name)`, and `item_versions.origin` (`upstream` by default, `writeback`) and `change_id`. `item_changes` keyed by id (UUIDv7, so id order is record order), `collection_id` and `archive_id` with foreign keys, `item_id` and `supersedes` as text without foreign keys, `op`, `class`, `origin` and `state` with `CHECK`s, a row needs an item or an href; the patch as JSON text; indexed partially by `(item_id, id)`, `(collection_id, href, id)`, `supersedes`, `blob_id` and, for open rows, `(collection_id, state, id)` and `(archive_id, id)`. An href resolves to the item with that `dav_name`, else that `remote_id`, else the rows under it with no item. `record_change` resolves the target, reads the open rows and the item's version count and compares the precondition in one transaction under the writer lock. `claim_change` is one `UPDATE … WHERE id = (oldest due row of a write_through collection: held, sent class, no flag, past next_attempt_at, no successor row, no sending row of the same item or href) RETURNING id`, and `due_change_collections` uses the same condition; the other state changes read the row, check its state in Rust and update it in the same transaction. Upstream flags are set in the transactions of `record_version`, `record_mail_version`, `mark_items_removed` and `mark_collection_removed`. `changes` is the change log with an `AUTOINCREMENT` `seq` (ids as text without foreign keys), indexed by `(archive_id, seq)`; every insert and state change of `item_changes` appends a row in its transaction. `delete_archive` adds the changes' blobs to the ones it releases and deletes `item_changes` and `changes` of the archive; `blob_used` and `referenced_blobs` count `item_changes.blob_id`. `delete_messages` leaves `item_changes` alone: it only removes items of the "From mail" collection, which has no account and so no changes.
- Imported collections read-only (migration 0033): collections of import accounts go back to `read_only` (0032 had made every collection with an account `held`). `upsert_collection` now picks `held` only for an account that is not an import account, and `set_write_mode` refuses any other mode for an import account's collection with `Invalid`, as for one no account owns.
- Invitation recovery (migration 0034): `item_change_messages` (`outbox_id` primary key, `change_id` indexed, text without foreign keys) is written in the transaction of `record_change`, so a held outbox message either belongs to a recorded change or to nothing; `held_change_messages` joins it with `outbox` rows in `draft`. `deferred_replies` (keyed by `message_id`, indexed by `next_attempt_at`) keeps incoming iMIP replies that wait for another try; `defer_reply` is an upsert that counts attempts and keeps `since`. `delete_archive` removes both; a deferred reply whose message is gone is dropped by its caller.
- Devices (migration 0035): `devices` with `secret_hash` a nullable unique `BLOB`, so `find_device_by_secret` is an index lookup and a device without an app password has none; `protocols` and `scopes` are JSON arrays of names. `all_archives` is 1 for "every archive the user can read"; otherwise `device_archives (device_id, archive_id)` lists them, both foreign keys cascading, so an empty list stays different from every archive. `mail_archive` is `ON DELETE SET NULL`, and `user_id` cascades. `last_used_day` is the UTC midnight in milliseconds. `mail_changes.device` and `outbox.device` are text without a foreign key, like `item_changes.device`, so the record of who wrote stays when a device goes with its user.
- Migration 0036 adds `transports.smtputf8` (`update_transport` never writes it; `set_transport_smtputf8` does) and the partial index `outbox_device_sends (user_id, created_at) WHERE device IS NOT NULL`, which `device_sends_since` reads with a `SUM(json_array_length(recipients))` over the window. `messages_by_rfc_id` reads the existing `messages_rfc` index through `json_each`.
- Migration 0037 adds `devices.raised_at`, the moment of the device's last raise of rights, which `update_device_settings` sets only when given one (`COALESCE`).
- Migration 0038 is the change feed and the mail view's own state. `changes` gains `kind` (existing rows are `item`), `message_id`, `folder_id`, `user_id`, `thread_id`, `outbox_id` and `draft_id`; every writer inserts through one helper in its own transaction under the writer lock, so `seq` (AUTOINCREMENT) order is commit order and visibility order. `latest_seq` reads `sqlite_sequence`, which never goes down when an archive's rows are deleted. The writer lock's guard ticks a `tokio::sync::watch` channel when released (after the commit); `watch_changes` waits on it or on a 30-second sleep (`set_change_poll` shortens it in tests) and then compares `latest_seq` with what it returned. `locations_folder_removed (folder_id, removed_at)` serves `folder_counts` and live-place lookups. `local_flags (user, message, flag_key)` keeps each flag's `present` with its first spelling, `local_places (user, role, message)` and `served_subscriptions (user, archive, mailbox)`; the first two cascade with their user and message, subscriptions with their user and go explicitly with their archive. `draft_versions.raw_blob_id` marks a raw draft version; its blob is also in `draft_blobs`, so inventory and archive deletion already cover it. `effective_flags` reads locations, open `flags` mail changes and local flags in one read transaction, 200 messages per query, and merges in Rust.
- Migration 0039 adds the served tables. `served_mailboxes` holds one row per view, unique on `(archive_id, key, IFNULL(user_id, ''))`, cascading with its archive and user; `uidvalidity` comes from SQLite's `random()` at creation. `build_ord`, `build_member` and `build_total` keep the build cursor `(archived_at, member)` and the count at its start, and `stale` marks a view `prune_served` left behind. `served_uids (mailbox_id, uid)` keeps `member` as text (a message id, or `<draft id>.<version>`), `modseq` and `expunged_modseq`; a partial unique index on `(mailbox_id, member)` covers live rows only, so a member that left keeps its tombstone while coming back under a new UID (SERVE.md's plain unique key could not keep both). Partial indexes serve `CHANGEDSINCE` and `VANISHED`, and `messages_served (archive_id, archived_at, id)` lets a build step walk an archive in UID order. Membership is one SQL query per key over `messages`, `locations`, `mail_changes` (by `json_extract` of the payload's `target` and `expunge`) and `drafts`; a catch-up runs under the writer lock in one transaction, reads the archive's rows since `synced_seq` and diffs only the members they name, 200 per query, while a folder row, a stale view or a backlog over 100 000 rows diffs everything in three statements (tombstones, `modseq`, an `INSERT … SELECT` numbering joiners with `ROW_NUMBER()`). A catch-up with nothing new reads one row and takes no lock. A test times it on a generated archive: in debug builds, a 25,000-member folder view of 50,000 messages builds in five steps in about 0.9 s, `Kept` in one step in 0.7 s, a catch-up of 100 flag changes takes 17 ms and a rescan 0.34 s.
- Migration 0040 adds `changes_archive_kind (archive_id, kind, seq)`, so `archive_heads` is one short index read per kind: `MAX(seq)` with `user_id IS NULL OR user_id = ?` walks back from the newest row of the kind. Role views also take members from `local_places` (any user's places of the role), and a `place` row of a user's own wakes role views, so a local place joins and leaves its role view at the next catch-up. `effective_flags` reads open `append` changes as places in their folder with the payload's flags, and held, sending or applied `move` changes not yet seen at their target as places there with the source location's flags.
- Migration 0041 adds `collections.write_mode_changed_at` and `previous_write_mode`, both empty until `set_write_mode` changes a mode; the update runs only when the mode differs, so setting the same mode keeps the time of the real change. serve-dav reads them for the 24-hour grace after `held` → `read_only`. `delete_messages` also writes `item` change-log rows: the item alone when it lost versions read from the deleted mail, and the item with `COALESCE(dav_name, remote_id)` as `href` when it is deleted for good, so a DAV client's next `sync-collection` reports it removed. `open_changes` takes `after` (`id > ?`) for paging.
- Migration 0042 adds `items.schedule_tag` and the tables `schedule_inbox` (one row per message and calendar part, keyed by both, indexed by archive and time) and `schedule_inbox_hidden` (message, part, user). It rebuilds `item_changes` with `itip` allowed in `origin` (SQLite cannot change a `CHECK`), keeping every row and recreating its indexes. `record_change` clears `schedule_tag` in its transaction unless the origin is `itip`; `delete_messages` and archive deletion remove the inbox rows of what they delete.
- Migration 0043 adds `flows` (one row per flow with its current version, trigger, mode, pause and `saved_by`, indexed by archive and position), `flow_versions` (keyed by flow and version), `flow_runs` (unique on flow, version and event id, so `claim_flow_run` is one `INSERT OR IGNORE`; indexed by flow and id, by flow and start, and the running ones), `flow_actions` (indexed by flow and time, by identity and time, and replies by flow, recipient and time) and `rule_events` (keyed by archive and id, handed out by a `seq` counter). Positions are renumbered in the transaction that moves or deletes a flow. `set_flow_run_result` reads, checks and writes a run's `results` JSON under the writer lock, so a compare-and-set on one element never races another write. Deleting an archive removes all five.
- No migration for pruning: `prune_changes` keeps its mark under `change_log_pruned_through` in `settings`, raised before any row goes, and deletes rows in chunks of 5 000 under the write lock, so writers wait at most one chunk. `replace_held_mail_changes` runs its cancels and inserts in one transaction under the write lock, so it cannot interleave with a claim.
- A test times `category_counts` on a generated archive (500,000 messages in release builds, 100,000 in debug) together with an override on a 50,000-message domain and a 500-row write, and prints the times: about 75 ms, 1.9 s and 40 ms in release on the dev machine.
- Tasks live in `tasks` and `task_log` (migration 0009), the log keyed by `(task_id, seq)` with a per-task counter `tasks.log_next`; `append_task_log` inserts the lines and deletes those between the first 50 and the last 450 in one transaction, so a log never grows past 500 rows. `recent_tasks` reads one page of `tasks` by `started_at` and each task's log by key; `interrupt_tasks` is one `UPDATE … RETURNING`; `prune_tasks` drops finished tasks past `keep` with their logs in one transaction. Each account's last run is one row in `account_runs` (same migration), removed with the account and with its archive.
- Contacts and calendars live in `collections`, `items`, `item_versions` and the derived `pim_index` (migration 0010). A collection is found by `(archive_id, account_id, kind, remote_id)` under the writer lock (`account_id IS ?`, so collections whose account was removed still match each other). `items` is unique per `(collection_id, remote_id)` and carries `archive_id` for listing and access checks and `versions`, the latest version's number; `item_versions` is keyed by `(item_id, number)` with indexes on `blob_id` and `photo_blob_id`. `record_version` compares with the latest version's blob, inserts the version, updates the item and replaces its `pim_index` row in one transaction. `pim_index` keeps the fields as columns, with `title_key` (trimmed, lowercased title) and `starts_at` indexed for the two list orders, and emails, phones and the normalized view as JSON text. Lists page by `(IFNULL(title_key, U+10FFFF), id)` or `(IFNULL(starts_at, i64::MAX), id)`; the cursor is `<item id>|<sort value>`. A blob counts as used by `delete_archive` when an item version or its picture names it too.
- Versions found in mail (migration 0011) set `item_versions.from_mail` and keep `method`, `sequence`, `dtstamp` and `sent_at`; `item_version_messages` links `(item_id, blob_id)` to `message_id`, indexed by message, so the link survives renumbering. `record_mail_version` reads the item's versions in its transaction, finds the new one's position by the order key, moves the later numbers up in two statements (negated first, so the primary key never collides) and inserts the version and its link.
- Migration 0012 adds `collections.ctag` and `collections.synced_at`, and `items.etag`, the source's current ETag, filled from each item's latest version. `record_version` writes `items.etag` on every call, also when the bytes are the same; `item_etags` reads it for live items through the `(collection_id, remote_id)` key.
- Migration 0013 adds `message_addresses (message_id, archive_id, field, email, name, date)`, one row per address of a message's `From`, `To`, `Cc` and `Bcc` (`field` is `from`, `to`, `cc` or `bcc`), keyed by `(message_id, field, email)` and indexed by `(archive_id, email)`. `insert_message` writes the rows in its transaction; the migration fills them from the stored address JSON of older messages with the same rule (trimmed of Unicode whitespace as Rust's `str::trim` does, which the migration spells out as the list of `White_Space` code points for SQLite's `trim`; ASCII-lowercased; at least one character before `@`; a test runs the migration's statement against a message and compares). `mail_addresses`, `correspondence` and `people_by_email` read only this table, `messages`, `attachments`, folders and labels, with `GROUP BY` aggregates; addresses given to them are ASCII-lowercased the same way. The derived people live in `people` (the `Person` as JSON in `data`, with `name_key` for the order, `search` (lowercased name, addresses and phones joined by newlines) for `instr` matching, `cards` and `differences` for the filters), `person_emails` (`(archive_id, email)` → person, for the reader's lookup) and `person_collections` (person × address book, for the source filter); `replace_people` deletes and inserts all three for the archive under the writer lock in one transaction. Lists page by `(name_key, id)` with nameless people under `U+10FFFF`; the cursor is `<person id>|<name key>`. `items_by_email` matches `pim_index.emails` through `json_each`. `delete_archive` deletes all of these.
- Migration 0014 adds the derived calendar: `event_series` (one row per event item: `archive_id`, `group_id` indexed for the event page, `sequence`, `stamp`, `starts_at`, `ends_at`, `recurring`, `window_from`/`window_to`) and `occurrences` (one row per stored instance, indexed by item and by `(archive_id, ends_at, starts_at)`, so a span reads only instances ending after its start). `replace_series` deletes and inserts an item's rows in one transaction under the writer lock. The collection filter is a JSON array bound once and read through `json_each`. The migration also sets the setting `index_rebuild`, so the next `serve` rebuilds the search index (whose schema changed) and with it every item's calendar rows; a fresh database rebuilds an empty index once. `delete_archive` deletes both tables' rows.
- Migration 0015 adds `person_overrides (id, archive_id, kind, keys, from_keys, created_at, created_by)` with the keys as JSON arrays, indexed by `(archive_id, id)`. `add_person_override` checks the archive and inserts under the writer lock (`INSERT OR IGNORE`, an existing id is `Invalid`); `delete_archive` deletes the archive's rows. Nothing derived refers to it, so `replace_people` and `reindex` leave it alone.
- `referenced_blobs` takes the next `limit` distinct ids above `after` from each of `messages`, `attachments`, `remote_images`, `derived`, `item_versions.blob_id` and `item_versions.photo_blob_id` through their indexes (migration 0008 adds the one on `messages`), merges them and keeps the first `limit`, so each page costs six short index range scans whatever the database size. Pages hold at most 10 000 ids.
- User emails are unique through an `email_key` column holding the trimmed, Unicode-lowercased email. Sessions are keyed by the 32-byte token hash and are deleted with their user.
