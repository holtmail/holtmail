# Integration test plan

Unit tests prove each module against in-process fakes. This plan adds a second tier that runs Holtmail against real servers in local containers: IMAP, JMAP, CardDAV/CalDAV, an OAuth provider, S3, HTTP and SOCKS proxies, and a TLS reverse proxy. It covers the items in [VERIFY.md](VERIFY.md) that a local server can prove, plus negative cases: wrong passwords, servers that die mid-sync, broken data, expired tokens and refused access.

The plan is written so that work can resume from this file alone after a break or a context reset. Tick each step as it lands and add a line to the Log at the end.

## How to resume

1. Read [AGENTS.md](../AGENTS.md), this file, [VERIFY.md](VERIFY.md) and the Log at the end.
2. `git status` shows work in progress. Finish and check it before starting the next unchecked step.
3. After each step:
   - run `mise run check`, which must stay network-free and green;
   - run `mise run it` for the suites that step added;
   - tick the step, tick or annotate the VERIFY.md items it proved, and add a Log line.

Rules for this run:

- No commits and no pushes; the maintainer reviews first.
- Never open the web app in a browser. The interface stays verified by types, lint and unit tests; VERIFY.md keeps its "by eye" items.
- Disk is tight: about 14 GiB free at the start.
  - Prefer small images. Nextcloud is an optional profile, off by default.
  - Before pulling, check `df -h ~`. Stop pulling below 5 GiB free.
  - Never prune Docker data this run did not create.

## Decisions

| Topic | Decision | Why |
| --- | --- | --- |
| Where | New workspace member `tests/integration` (package `holtmail-integration`, `publish = false`) with one test file per area, plus `tests/integration/compose.yaml` and seed files | Keeps the network out of every other crate; one place composes real implementations, like `apps/server` |
| Default runs | Every integration test returns early unless `HOLTMAIL_IT=1`, so `cargo test --workspace` and `mise run check` stay network-free | AGENTS.md: unit tests never touch the network |
| Runner | `mise run it` brings the compose stack up with `--wait`, seeds it, runs `cargo test -p holtmail-integration -- --test-threads=…`, and leaves the stack up; `mise run it-down` stops it and removes its volumes. `IT_PROFILES` selects optional servers | Fast re-runs; one command for the maintainer |
| Black box | Most scenarios run the real `holtmail` binary (built once by the test harness) in a temp data dir and drive it through the CLI and the HTTP API with reqwest; library-level checks call the implementation crates directly where a flow is easier to provoke there | Tests what users run, including config and composition |
| Isolation | Each test gets its own data dir, its own mailbox user or a uniquely named folder on the shared servers, and a random port | Tests run in parallel without stepping on each other |
| Data | Invented messages, contacts and events generated by the harness (example.com/example.org, made-up names), never real mail | AGENTS.md |
| TLS | A throwaway CA generated at stack start signs the servers' certificates. Holtmail gains a `tls_ca_file` config option (also useful for self-hosted servers with a private CA) so TLS paths are tested without disabling verification | Real TLS, no "accept any certificate" switch |
| Private addresses | The image fetcher's refusal of private addresses stays on. Positive image tests go through a proxy (`socks5h`, HTTP CONNECT) that resolves names inside the test network; direct fetching is only tested for refusals | No test-only weakening of SSRF protection |
| Network | Containers only; nothing reaches the internet during a run, except pulling images | Repeatable and private |
| TLS roots in code | `holtmail_core::TlsRoots` (DER certificates read from PEM). IMAP adds them to the Mozilla roots; the reqwest clients (JMAP, DAV, Graph, OAuth, images) and S3 merge them with the system's roots (`tls_certs_merge`, `ClientOptions::with_root_certificate`). Clients take them through `with_roots`, `fetch_http::Options::roots` and `S3Config::roots`; the server reads `tls_ca_file` (`HOLTMAIL_TLS_CA_FILE`) in `Config::load` and hands the roots to every client it builds from one process-wide value in `apps/server` | Libraries stay explicit and keep their constructors; only the composition root holds the setting, and threading it through every sign-in check and sync path would touch dozens of signatures |
| TLS test helpers | `holtmail-core`'s `testing` feature has `TestCa` (rcgen) with a TLS acceptor and a one-answer HTTPS server; each client crate proves the CA is trusted only through its roots option | One CA helper instead of eight |
| CA for the stack | A `ca` compose service runs `seed/ca.sh` with the `openssl` of the Dovecot image (no extra image) and writes `ca.crt`, `server.crt` and `server.key` into `tests/integration/.state/` (gitignored), kept until `mise run it-down`. The server certificate names `localhost` and the service names but not `127.0.0.1` | The host tests read the CA from a plain path; connecting to `127.0.0.1` gives the wrong-host-name case for free |
| Dovecot users | A `static` passdb: any user name signs in with `it-imap-password` and gets a fresh mailbox, instead of a passwd-file with a few users. Plain `LOGIN` is allowed without TLS for seeding | A fresh user per test isolates tests without editing a user list; a passwd-file can be added for locked-account cases in step 2 |
| GreenMail users | Authentication off for now (any user name and password) | Users appear on first use; wrong-password cases use Dovecot or Stalwart, or turn auth on in step 2 |
| Ports | Fixed host ports on `127.0.0.1`: Dovecot 41143/41993, GreenMail 42143/42993; later services take 43xxx and up | Stable addresses for tests and for a person debugging |
| Binary and config | `it.sh` builds `holtmail` and sets `HOLTMAIL_BIN`; the harness builds once per test process when it is not set. Each instance gets `sync_interval_minutes = 0` (only requested syncs) unless a test says otherwise, `RUST_LOG=info` (`IT_RUST_LOG` overrides) and no inherited `HOLTMAIL_*` variables | Deterministic runs; logs are scanned at the level users run |
| Filters | `mise run it -- <area> [filter]` runs `tests/<area>.rs` when that file exists, else passes everything to libtest as a filter; `IT_THREADS` (default 4) sets `--test-threads` | One command for one suite |
| Stalwart for IMAP | Not in the stack for step 2; set up in step 3, and the step 2 suite (`imap.rs`: first and incremental syncs, folders, expunge and moves, renumbering, CONDSTORE flags) then ran on it too | Stalwart 0.16 keeps its configuration in its database; see the next rows |
| Stalwart setup | `stalwartlabs/stalwart:v0.16.27-alpine` with `config.json` naming only RocksDB. A one-shot `stalwart-seed` service on the same volume starts it in recovery mode (`STALWART_RECOVERY_MODE=1`, management on 8080 only), sends `seed/stalwart/plan.json` as one JMAP request with the `x:` management objects (`Domain`, `Certificate` from files in `/certs`, `NetworkListener` ×4, `Imap.allowPlainTextAuth`, `Security` bans off, `Http` rate limits off, `SpamPyzor` off), disables the `webui` `Application`, stops it and marks the volume; `stalwart` then starts normally with `STALWART_PUBLIC_URL=https://localhost:43443` | `stalwart-cli` is not in the image and its `apply` only sends the same `x:Object/set` calls; listeners and certificates take effect only at start, so they are written before the server starts, which is the documented declarative flow. The marker makes a second `up` a no-op instead of fighting the running server for the RocksDB lock |
| Stalwart users | Created per test through `x:Account/set` by the recovery administrator (`STALWART_RECOVERY_ADMIN` stays set on the running server; accepted in every mode), all with the password `it-stalwart-password`; API keys through `x:ApiKey/set` signed in as the user (the secret is in the create answer) and used as bearer tokens | A fresh user per test, like Dovecot's static passdb; Stalwart has no "any user" mode |
| Stalwart offline | Both Stalwart services get `dns: [127.0.0.1]`: Docker's resolver still answers service names but cannot resolve anything outside, so the web UI download (GitHub) and Pyzor (`public.pyzor.org`) fail at once and nothing leaves the machine. The one failed web UI download happens in the seed's recovery start (logged as `resource.error`); Pyzor has to be off or `ReloadSettings` fails with "Invalid address" | An `internal` network cannot publish ports; Stalwart works without the web UI and without Pyzor |
| Stalwart bans | `authBanRate`, `abuseBanRate`, `loiterBanRate` and `scanBanRate` set to `null`, HTTP rate limits off | The wrong-password tests and parallel suites all come from one address; a ban would fail every later test |
| JMAP state expiry | `cannotCalculateChanges` provoked by rewriting the stored collection states to `szzzzzz` (`Holtmail::rewrite_collection_tokens`), a state ahead of Stalwart's change log; Stalwart answers a state older than its log as "from the start", so a forgotten state cannot be provoked without months of changes | The server's own answer to a state it cannot use, at the same step every run |
| Redirect checks | `redirect::Redirect`, a plain HTTP server on `127.0.0.1` in the test process (Holtmail allows plain http only to loopback) that answers with a `307` or a fixed JSON session, and records whether each request carried `Authorization`. Two of them chained give two foreign origins before Stalwart | Proves where credentials went without a proxy in the stack |
| Faults | A TCP relay in the test process (`relay::Relay`: pass, stall after N bytes, cut after N bytes) instead of `docker compose pause/kill` | The failure lands at the same byte every run, and other tests keep the server |
| Locked account | Dovecot has a second passdb, `passwd-file` with `deny = yes` on `.state/dovecot-locked-users`; `services::lock_dovecot_user` appends to it and waits until Dovecot refuses the user (the file reaches the container after a moment) | Locks one fresh user while the static passdb keeps serving every other |
| Unselectable folders | `CREATE Parent/Child` gives a `\Noselect` parent on Dovecot; a folder listed as selectable whose `EXAMINE` fails comes from Dovecot's ACL plugin (`SETACL <folder> owner la`) | Both cases with stock Dovecot and no files edited inside the container |
| Slow servers | The two-minute IMAP command timeout is proven at library level: `ImapSource::with_timeout` (new, public) against the relay in stall mode, 5 s. Through the binary, a stalled sync is used only for the kill and resume case | A black-box timeout test would wait two minutes |
| Flag scan on GreenMail | GreenMail 2.1.14 has no CONDSTORE; the daily scan is reached by moving `flags_checked_at` back 25 hours in the instance's SQLite (`Holtmail::age_flag_checks`) between syncs, after checking that a sync before that reads no flags | Time travel instead of a test-only config knob |
| Minimum age | Seeded with `APPEND` internal dates; "ageing" is shown by lowering `min_age_days` (3, then 1, then off) instead of waiting days | Same cutoff arithmetic, no clock tricks |
| Scale | 5 000 messages of about 1.8 KiB, appended with `LITERAL+` in pipelined chunks of 200, first sync through the debug build; peak RSS sampled with `ps` every 100 ms | Measures what `mise run it` runs; a release build would be faster |
| DAV servers | Radicale `tomsquest/docker-radicale:3.8.3.0` with its own TLS (key from `server-shared.key`, a copy `ca.sh` writes readable for Radicale's user); Baïkal `ckulka/baikal:0.10.1-nginx` with a mounted nginx config listening with TLS on 45443 inside and out (its absolute well-known redirect then names the published port) and an entrypoint step writing `baikal.yaml` and an empty database from Baïkal's schema; Stalwart's own CardDAV/CalDAV on 43443 | The servers' own TLS or their own web server, no terminator image; reproducible at every `up` |
| DAV users | A DAV account is an IMAP account with contacts and calendars on, signing in to DAV with the mail user and password. Radicale and Baïkal users get Dovecot's password (Dovecot signs any user in); Radicale's from `.state/radicale-users` (re-read on every sign-in; the harness waits until the line reaches the container), Baïkal's as rows written by PHP in the container; Stalwart's through its management API | A fresh user per test on every server, as in steps 2 and 3 |
| DAV faults | `proxy::Proxy`, a plain HTTP reverse proxy in the test process in front of Baïkal (Holtmail allows plain http to loopback): `NoSync` answers `sync-collection` with `501` for the ETag listing path, `Status(500)` for a failing server, `Rewrite` for data the server sends broken. A card sabre/dav itself cannot parse is written into Baïkal's database (`baikal_insert`) | The same failure at the same request every run, without reconfiguring the servers; Baïkal and Radicale refuse broken data over DAV |
| DAV token expiry | The stored sync tokens rewritten to `szzzzzz` (`Holtmail::rewrite_collection_tokens`). Radicale, Baïkal and Nextcloud refuse it (`valid-sync-token`) and the collection is read in full by ETag; Stalwart never refuses a token (an unknown one lists every item, one ahead of its log lists nothing), so there the check is that nothing is lost or doubled | The servers forget tokens only after long times or many changes |
| Nextcloud | Profile `nextcloud`, `nextcloud:35.0.1-apache` with SQLite, `mod_ssl` from a mounted Apache config, a post-installation hook that turns off the internet check, brute-force protection, rate limits and the password policy; `it.sh` leaves the profile off below 20 GiB free. `dav.rs` and `dav_calendar.rs` run on it when `IT_PROFILES` names it | 2.1 GB image and a 1.1 GB volume; installs in about 10 s here |
| JMAP `apiUrl` for contacts | `holtmail-collection-jmap` now follows `holtmail-source-jmap`: credentials go to the session address and to the `apiUrl` the authenticated session names on any host, https only (http only to loopback), and no redirect is followed with them (lead's request after step 3) | One rule for a JMAP account's mail and contacts; Fastmail names API hosts other than the session's |
| Multiget `5xx` | `holtmail-collection-dav` reads a batch whose multiget answers `5xx` one `GET` per item and leaves out an item whose `GET` fails too; `holtmail-pim-sync` counts an item listed but not sent as failed, so the token is dropped and it is asked again | sabre/dav answers the whole multiget `500` when it cannot parse one stored card; before, that card stopped the whole address book on every sync. Counting it as failed keeps a passing server error from losing an item |
| OAuth provider | `ghcr.io/navikt/mock-oauth2-server:6.1.2` over TLS from a PKCS#12 copy of the stack's certificate (`ca.sh`), in Dovecot's network namespace (`network_mode: service:dovecot`, port `47443` published by `dovecot`); one issuer whose access tokens live 60 s, refresh tokens rotated on every refresh, `sub` = the client id | The provider names its issuer after the host it was asked on and introspection refuses tokens of another issuer; sharing the namespace lets Holtmail (on the host) and Dovecot both say `localhost:47443`. 60 s is below Holtmail's two-minute margin, so every use refreshes and "refresh before sync" and rotation are seen on every sync |
| OAuth users | Each test's own client id is a fresh `<unique>@example.com`, which is also the Dovecot user: the provider puts the client id into `sub`, Dovecot's `oauth2` passdb signs in the user named by `sub` | A fresh mailbox per test without a user list at the provider; a sign-in for another address is refused by Dovecot, which gives the "token refused" case |
| OAuth browser step | The harness plays the browser with reqwest: follows Holtmail's authorize address with `openid` added to the scope (the provider is OpenID Connect and refuses requests without it), submits the provider's sign-in page as the `login_hint` when it shows one (it does for Google's `prompt=consent`), and opens the callback without following Holtmail's `303` | No browser; everything Holtmail sent is asserted before the change |
| XOAUTH2 in Dovecot | A third passdb, `driver = oauth2` with `mechanisms_filter = xoauth2 oauthbearer`, introspecting at `https://localhost:47443/default/introspect` (Basic sign-in in the URL, `ssl_client_ca_file` = the stack's CA, `username_attribute = sub`); the static password passdb gets `mechanisms_filter = plain login` | Password tests are unaffected and a token is never accepted as a password; introspection works with the stock image, local JWT validation would need the provider's changing key in a dict |
| OAuth IMAP server | New config `[oauth.<provider>] imap_host` and `imap_port` (`HOLTMAIL_OAUTH_<P>_IMAP_HOST`/`_PORT`): the IMAP server new OAuth accounts connect to over TLS, the provider's own by default | OAuth IMAP accounts were fixed to `imap.gmail.com` and `outlook.office365.com`, so an own client could not be tested against a local server, and Microsoft's national clouds (GCC High: `outlook.office365.us`) could not use IMAP although Phase 18 added their sign-in and Graph addresses. Same pattern as `authorize_url`/`token_url`/`graph_url` |
| Revoked sign-in | The refresh token is read from the instance's database and opened with its `secret.key` (`Holtmail::open_secret`), then revoked at the provider's `/revoke` | What removing an app's access does at a real provider; nothing in Holtmail is touched |
| Image server and proxies | nginx serves `.state/images` (files written by the tests) on an internal network `11.88.77.0/24` at `11.88.77.10`, also `images.it.test`; squid (`ubuntu/squid:6.6-24.04_edge`) and two `serjs/go-socks5-proxy:v0.0.4` (with and without a password) sit on both networks at fixed addresses. `socks5h` uses the name, `socks5` and HTTP the address | `11.0.0.0/8` is public (not refused by the fetcher) but not announced on the internet; with `socks5` and an HTTP proxy Holtmail resolves names itself, so only an address works there. The private-address refusal stays on |
| Proving the proxy | nginx's access log (`docker compose logs images`) gives the proxy's fixed address for every request | On OrbStack the host reaches container addresses, `11.88.77.10` too, so a direct fetch would also succeed; the log shows which way it went |
| Image limits | An 11 MiB file (size refused from `Content-Length`), a page served as `text/html` from a `.png` path, 64 KiB at 2 KiB/s (Holtmail's 15 s limit), a `404` written later; older mail paced at 16 KiB/s so the task can be killed mid-run | The product's limits as configured, no test-only knobs |
| S3 server | `pgsty/minio:RELEASE.2026-08-04T00-00-00Z` with TLS from the stack's CA, bucket made by `mc` at start, keys only in Holtmail's environment, one prefix per test | `minio/minio` on Docker Hub refuses pulls (MinIO stopped publishing images) and `quay.io/minio/minio` has no current tags; Pigsty's build is MinIO's server, pinned and arm64. TLS proves `tls_ca_file` for S3 |
| Restore target | A second instance started once (for its config with filesystem blobs), stopped, its data directory removed, `holtmail restore --data-dir` into it, started again | The CLI as an operator runs it, without a harness option for an existing data directory |
| Missing blob in a backup | Expected as documented: the backup is written without it, names it and fails | apps/server docs: "makes the command fail after the file is written"; the backup of everything else stays useful |
| Access matrix | One table of expected statuses per OpenAPI operation for owner, admin, member with the archive granted, member without it and anonymous; the operations are read from `holtmail openapi`, so a new route without a row fails the test, and every answer must also be declared by its operation. Destructive requests get their own target per role (a fresh archive, import account, user, override); members are refused before anything is looked up, so they get any id | A route added later cannot slip past the matrix, and the description stays truthful |
| Session expiry | No config option shortens sessions (30 days fixed in `holtmail-auth`); the test moves the member's first session's `expires_at` into the past in SQLite (`Holtmail::execute`) | No test-only knob in the product |
| Large archive | 20 000 messages (every 25th with a 16 KiB attachment) uploaded as one 43.6 MiB mbox through the API, debug build; peak RSS sampled every 100 ms on the process doing the work (`serve` for API exports, the CLI process for CLI exports, backup and restore), bound 300 MiB | Measures what `mise run it` runs; the bound is twice the observed peak and well under what buffering a whole export would need with headroom for the debug build |
| Images for upgrade and Docker | Profile `docker` (off by default, no services): `it.sh` builds `holtmail:dev` from the checkout and `holtmail:it-old` from `fed635b` in a temporary `git worktree` when missing. Containers run on `holtmail-it_default`, IMAP to `dovecot:31143` in plain text (the old image has no `tls_ca_file`) | Image builds take minutes and gigabytes of build cache; the default run stays quick |
| Migrations check | After the new image stops, `holtmail.db` (with `-wal`/`-shm`) is copied out with `docker cp` and `_sqlx_migrations` read: versions 1–15 applied | The image has no `sqlite3`; the server does not log migrations |
| Caddy | `caddy:2.10.2-alpine` in the stack, TLS from the stack's certificate, `reverse_proxy host.docker.internal:49480` (`extra_hosts: host-gateway`); `caddy.rs` starts the binary on that fixed port (`Options::port`) with `public_url = "https://localhost:49443/"` | The binary under test, not an image, behind a real proxy; one fixed port, one test |
| CLI next to `serve` | `archives`, `import`, `sync`, `reindex` and `account add-*` open the search index `serve` holds and cannot run beside it (documented in `holtmail-index-tantivy`); the error now says so instead of Tantivy's lock message, and the server docs list which commands work beside `serve` | Found through `docker exec`; making them work beside `serve` would mean going through the API |
| Remote images at once | `holtmail-remote` looks at up to four messages of a batch of 50 together, with the six-download limit shared across them (a semaphore) and one lock per URL so a URL two messages link is still fetched once. A slow image still holds up the end of its batch. The resume-after-kill test now allows as many re-fetched images as messages in flight (four) | Step 5 found one slow sender stalled all saving; batches stay because the store lists unscanned messages without a cursor |
| Not covered here | Gmail labels (`X-GM-EXT-1`), real Google and Microsoft sign-in, Microsoft Graph, iCloud quirks, the web app by eye | No local server implements them; they stay in VERIFY.md |

## Steps

### 1. Harness

- [x] `tests/integration` crate, `compose.yaml` with profiles, CA generation, `mise run it` / `it-down`, `HOLTMAIL_IT` gate
- [x] Shared helpers:
  - build and run `holtmail` in a temp data dir on a random port, wait for ready, collect logs;
  - an API client with setup, sign-in, cookies and Origin;
  - generators for invented messages, mbox files, vCards and iCalendar objects;
  - IMAP APPEND, DAV PUT/DELETE and JMAP set helpers for seeding;
  - a log scanner that fails a test if a seeded secret, address or subject appears in Holtmail's logs.
- [x] `tls_ca_file` config option in the server and the IMAP, JMAP, DAV and fetch clients (with unit tests and docs)
- [x] Docs: `tests/integration/docs/README.md`, link from docs/README.md; AGENTS.md notes the second tier and its commands

### 2. IMAP

Run against Dovecot, GreenMail and Stalwart where the feature exists.

Stalwart was left for step 3 (see Decisions); every item below ran on Dovecot, and on GreenMail where it applies. In step 3 first and incremental syncs, folders, expunge and moves, renumbering and CONDSTORE flags also ran on Stalwart.

- [x] First sync and incremental sync: counts, folders with UTF-7 and nested names, special-use roles, a message in two folders stored once
- [x] Expunge on the server keeps the message in the archive and marks the location removed; a moved message gains a location
- [x] UIDVALIDITY change (folder deleted and recreated) renumbers without duplicates
- [x] Flags:
  - CONDSTORE `CHANGEDSINCE` picks up read and flagged changes (Dovecot);
  - the full flag scan path on a server without it (GreenMail).
- [x] Minimum age: young mail waits, then arrives after its `INTERNALDATE` ages (seed with old and new dates)
- [x] TLS, STARTTLS and plain:
  - a certificate from the test CA works only with `tls_ca_file`;
  - a wrong host name is refused.
- [x] Negative:
  - wrong password, a locked account, a server that closes mid-fetch (container paused or killed during a sync) leaves a resumable cursor;
  - a slow server hits the timeout;
  - a malformed message is archived raw;
  - a 20 MB message;
  - a folder that cannot be selected.
- [x] Connection change:
  - to another server with a new password works;
  - without the password it is refused;
  - an OAuth account cannot change its host: moved to step 5, which brings the OAuth provider (creating an OAuth account needs it; the refusal itself is unit-tested in `apps/server`); done there in `oauth.rs` (host, port, security and password refused, other settings accepted).
- [x] Scheduler: a short interval syncs on its own; tasks and last runs survive a restart of the binary; an interrupted sync (binary killed) shows as interrupted and resumes
- [x] Scale smoke: 5 000 messages in one folder; measure time and peak memory, record them in the Log

### 3. JMAP (Stalwart)

- [x] Mail: password and token sign-in, first and incremental sync, an email in two mailboxes stored once, moves, deletes kept in the archive, keyword flags, wrong credentials
- [x] Contacts and calendars over JMAP (RFC 9610, and calendars if offered): first sync, change, removal, state expiry
- [x] Session URL discovery through `/.well-known/jmap`; an off-origin redirect refused

CardDAV and CalDAV on Stalwart are left for step 4 (Stalwart serves them on the same HTTPS port 43443).

### 4. CardDAV and CalDAV (Radicale, Baïkal, Stalwart; Nextcloud optional)

- [x] Discovery (well-known, principal, home sets), first sync of address books and calendars, changes, removals, a removed collection
- [x] `sync-collection` token expiry or loss, and the ETag listing fallback (Baïkal with sync disabled, or a token rewritten by the test)
