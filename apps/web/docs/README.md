# @holtmail/web

The Holtmail web app: a calm, keyboard-first mail client for an archive, and the place where the owner sets everything up: archives, mail sources, uploads and people. Vite, React 19, TypeScript, Tailwind CSS v4, TanStack Router, Query and Virtual, Motion. It talks to the server only through [`@holtmail/api-client`](../../../packages/api-client/docs/README.md), takes components from [`@holtmail/ui`](../../../packages/ui/docs/README.md) and every color, size and duration from [`@holtmail/tokens`](../../../packages/tokens/docs/README.md).

## Commands

From the repository root:

- `bun run dev:web` — dev server; `/api` is proxied to `HOLTMAIL_SERVER` (default `http://127.0.0.1:8080`)
- `bun run build` — production build into `apps/web/dist`
- `bun run typecheck`, `bun run lint`, `bun run test`

## Sign-in

The mail routes check `GET /api/session` before they load (cached for the visit). On `401` the app asks `GET /api/setup`: while the instance has no users it goes to `/setup`, otherwise to `/login?next=<the requested path>`. `/setup` without a token explains that the setup link is in the server log; `/setup` once users exist goes to `/login`, and `/login` while signed in goes straight to `next`. A `401` from any data query later (an expired session) clears the cached session and goes to `/login?next=<current path>`; queries are never retried on a `4xx`.

Both screens are one narrow centered column: the wordmark with a hairline that draws itself, then title, lead and form rising in one after another with the expressive curve (fades only under reduced motion). Fields are Carbon-style (label above, filled field with a bottom rule), focus starts in the first field, `Enter` submits, the password has a visibility toggle, and the autocomplete hints are `username`, `current-password` and `new-password`. Setup shows a live hint until the password has 10 characters. Errors from the API show under the form and move focus back to the field to fix; a `429` reads "Too many attempts, try again in N minutes" from `Retry-After`. `next` is accepted only as a same-site path that is not `/login` or `/setup`.

The user menu at the right of the top bar shows the name and email, the theme (light, dark, system) and Sign out, which posts `/api/logout`, drops every cached query and goes to `/login`.

## Setting up

Nothing needs the command line. After the owner account is created, `/` finds no archive and opens `/welcome`: an archive name (prefilled "Personal") and two large choices, Connect a mailbox and Import files, with a hairline that draws under the hovered one. Each step slides in from the right.

- **Connect a mailbox** asks only for the address and password. The domain picks a preset (Gmail, Outlook, iCloud, Yahoo, Fastmail, Yandex, Mail.ru, GMX, Proton Mail Bridge; `src/lib/providers.ts`), or `imap.<domain>` otherwise, and the password field explains where to get an app password, with a link. Server settings (host, port, TLS / STARTTLS / none, user name, sidebar name) fold open on demand and open by themselves when signing in fails for an unknown provider. The server signs in before saving, so a wrong password shows its reason under the form.
- **JMAP**: _Connect over JMAP instead (Fastmail and others)_ under the IMAP form switches to the JMAP form, and _Connect over IMAP instead_ back (`src/manage/connect-mailbox.tsx`). The JMAP form (`connect-jmap.tsx`, request built by `src/lib/jmap.ts`) starts with a provider choice: _Fastmail_ asks only for an API token (sent to `https://api.fastmail.com/jmap/session` as a bearer token, with a hint where Fastmail creates one) and an optional name (`Fastmail` when empty); _Other JMAP server_ asks for the JMAP address (session address or the server's address), _Password_ or _API token_, the user name for a password, the secret and a name. Empty fields are named under the form before anything is sent; the server signs in before saving and its reason shows under the form.
- **Gmail and Microsoft** addresses (`gmail.com`, `googlemail.com`, `outlook.com`, `hotmail.com`, `live.com`, `msn.com`, `office365.com`; `src/lib/oauth.ts`) get Sign in with Google / Microsoft instead of a password, with an optional sidebar name and a quiet note that the consent screen names Thunderbird, whose public sign-in Holtmail borrows unless the server owner registered their own. Only providers `GET /api/oauth/providers` lists are offered (`useOAuthProviders`, all of them until the list arrives): an address of a provider the server turned off gets the password form, and neither the Graph link nor the switch to OAuth on an account appears without Microsoft. _Use an app password instead_ switches back to the IMAP form, and back again. Signing in calls `startOAuth` with the current path as `return_to`:
  - when the server needs a paste (Thunderbird's client, the default), the provider page opens in a new tab and the form becomes _Finish signing in_: a link to open the page again, the instruction to copy the address of the page that cannot be opened after allowing access, a field for it with a hint until it contains `code=` and `state=` (or `error=`), the time the sign-in expires, the server's error on failure, Start again, and Finish, which calls `finishOAuth` and then continues exactly like a connected IMAP account;
  - with the owner's own client the tab itself goes to the provider and comes back to the same page with `?oauth=done&account=<id>` or `?oauth_error=<reason>`. `useOAuthReturn` reads and strips those params. The first-run screen finds the archive of that account and shows the progress step, or returns to Connect with the error; Archives settings show a dismissible confirmation or error above the archives.
- **Microsoft Graph**: _Connect Microsoft 365 or Outlook.com through Microsoft Graph instead_ under the IMAP form (above the JMAP link, shown for every address, since Microsoft 365 mailboxes mostly use their own domains) switches to the Graph form (`connect-graph.tsx`), and _Connect over IMAP instead_ back. It asks for the address and an optional sidebar name, says it suits Microsoft 365 work and school mailboxes where IMAP is turned off as well as Outlook.com and Hotmail, shows the Thunderbird note, and Sign in with Microsoft calls `startOAuth` with `kind: 'graph'` (request built by `graphSignIn` in `src/lib/oauth.ts`, which refuses anything that is not an address). The paste step, own-client return and progress are the same as for Microsoft IMAP sign-in.
- **Import files** takes files dropped or chosen (`.mbox`, `.eml`, `.zip`, and address books and calendars as `.vcf` and `.ics`, alone or in a Google Takeout zip; files without an extension are tried as mbox). Contacts show up in Contacts, events in the Calendar. They upload one after another, each with a thin progress bar that turns green when the server has it.
- The last step lists the sources with a live status: a pulsing accent square while syncing with the count of new messages, then "Synced 2 minutes ago". The archive can be opened right away; folders and messages appear while the sync runs.

- **Rules** (`rules-page.tsx`, the editor in `src/rules/`, logic in `src/lib/rules.ts`), for every user with an `editor` or `sender` grant on the shown archive (`mayWriteRules`; others see a line saying who can give the right, and the server still answers `403` when the `[write] rules` switch is off). Per archive (a picker when there are several; the choice is the `archive` search param, so the editor's back link returns to it). The flows in run order (`inRunOrder`: position, then creation), each with its number, name (a link to the editor), trigger title from the catalogue, version, when it was saved, a mode select (_Test_, _On_, _Off_; `PATCH /api/flows/{id}`) with what the mode does, a warning badge while the circuit breaker holds it (choosing a mode runs it again), _Edit_, and a menu with _Run earlier_, _Run later_ (`PATCH` with the neighbour's `position`) and _Delete_ (confirmed). _New flow_ asks for a name and the trigger (with its summary from the catalogue), creates the flow with only its trigger (it starts in test mode, as the server makes every new flow) and opens the editor. See [Rules editor](#rules-editor).
- **Devices** (`devices-page.tsx`, helpers in `src/lib/devices.ts`), for every user's own devices. _Connecting_ shows the server, port and security of each configured listener from `deviceSetupQuery` (a listener without a configured name shows the page's own host; JMAP and CalDAV and CardDAV show the full address their clients ask for, from `url`, in place of the host) and the user name, or a line that the server does not serve mail apps yet. _New device_ (hidden when `can_create` is false): name, how it connects, the mail archive (only for IMAP and SMTP), the archives it sees (only for JMAP, DAV and the API; a device with none of those gets an empty list), what it may do with each consequence spelled out, and for IMAP whether opening marks read. A protocol without a listener on this server (every one but the API, `unservedProtocols`) says it is not turned on yet, and a device row using one says the device cannot connect that way until the server offers it. It starts with `read` only; ticking SMTP adds `send:mail` and any other protocol adds `read`, because a device cannot sign in without them, and unticking them is refused with the reason. The app password is shown once in a dialog with no close control, with the servers and Copy; it is kept only in page state, and the mutation has `gcTime: 0` so it leaves no copy in the mutation cache. Rows show the protocols, the rights in words, the archives, last use (a UTC day and protocol) and when it was added; the menu has _Change_ (the same form, which sends only what changed, so a rename needs no fresh sign-in) and _Revoke_ (confirmed). Revoked devices stay listed below. _Before you add an account_ (`SetupNotes`) says to use Holtmail or the upstream account on a device, not both, that iOS Mail polls such accounts every 15 minutes (Web Push from the installed app notifies at once), and that the new Outlook and Gmail reach the server through Microsoft's and Google's servers; with `davx5` from `deviceSetupQuery` it links to DAVx5 with the server filled in. When `autoconfig` lists mail domains it adds that Thunderbird finds the server by itself for addresses there (`domainList` joins them for the locale). When `apple_profile` is true, a device whose protocols fit a profile on this server (`fitsProfile(protocols, servers)`: IMAP with SMTP, or DAV, and every part the profile would carry has a listener, as the server decides it) has _Profile for iPhone, iPad or Mac_ in its menu, and the app password dialog of a new one offers it too: the dialog explains that opening the link gives the device a new app password, works once for 10 minutes and is unsigned, then _Make link_ calls `deviceProfileLink` (a `428` opens _Confirm it's you_ and repeats) and shows _Download profile_ (opens the server's confirmation page in a new tab; after a click the buttons give way to a note that the link works once the profile is downloaded there), _Copy link_ and the expiry time. Opening the link changes nothing on the server; only the confirmation page's button issues the profile. As an app on the iOS or iPadOS home screen (`runsOnIosHomeScreen`: Safari's `navigator.standalone`, so desktop and Android installed apps are not meant) _Download profile_ is left out, _Copy link_ is the main action, and a note says iOS takes a profile only from Safari. The link is kept only in the mutation (`gcTime: 0`). A `428` opens _Confirm it's you_: a password goes to `POST /api/login` and the same save repeats, with the form untouched. An archive the user can no longer read is left out of the edit form and of the list it sends. _In mail apps_ (`serving-section.tsx`, helpers `buildState` and `sortedFlagWords` in `src/lib/devices.ts`) appears once `servingQuery` lists an archive: per archive, the build of its served mailboxes as a hairline bar with "Preparing for mail apps: N% (assigned of total messages)" (never 100% until every mailbox is built; the query polls every 3 seconds while one builds), then "Ready in mail apps: N mailboxes"; and when the user has local flags there, how many messages carry them, _Show_ (the newest 200 from `localFlagsQuery` with subject, sender, date and the flags in words: Read and Unread, Flagged and Not flagged, Answered, Draft, keywords as written, system flags first) with _Clear_ per message, and _Clear all_ behind a confirmation. Clearing calls `dropLocalFlags` and refreshes everything under `['devices']`. With `[serve] local_flags = false` a note says mail apps do not see these marks. Drafts saved by mail clients need nothing of their own: the server hands them to compose like "Edit as new".
- **Device notices** (`device-notices.tsx`): a hairline line under the top bar of the mail and settings layouts for seven days after a device is made or its rights raised (`recentDeviceNotices`, from `created_at` and `raised_at`), with _Review_ and _Dismiss_. It is shown in every browser, also the one that did it, so that a device made through a stolen session is seen; _Dismiss_ is per browser (`localStorage`, `holtmail.device-notices`, holding only keys still inside the window), and a later raise is a new notice.
- **Reading**: remote images, kept in this browser (`localStorage`, `holtmail.remote-images`), because the address a sender sees depends on the device. _Hide, and ask each time_ (default), _Always show, through Holtmail_ (the server fetches them; senders see its address) or _Always show, directly_ (with a warning that senders see your IP address, rough location and when you open each message). Saved copies always show. _Mark as read when opened_ is a switch kept in this browser (`holtmail.read-on-open`, `on` or `off`, off unless set; `src/hooks/use-read-on-open.ts`): opening a message then marks it read on the server, only on accounts whose `writable` has `mail.flags` and only where it is unread with no open change to its read state (`planReadOnOpen`).
- **Profile**: name and email, and a password change that keeps this browser signed in and signs out the others.
- **About** (`about-page.tsx`, helpers in `src/lib/about.ts`), for every user: the Holtmail version from `insightsDataQuery`, then the category data files the server loaded, each with its name, data version, rows, license, file name and a _Bundled with Holtmail_ or _Downloaded_ badge. Under them the attribution lines: the server's `attribution` text, and "Contains data from UT1 (Université Toulouse Capitole), CC BY-SA 4.0" whenever a `ut1` file is loaded, even if the server sent none. In muted text, whether updates are on (with the downloaded tables) and the last check with its outcome. With no files (insights or the domain categorizer off) a note says so.

While any source of the shown archive syncs or imports, the app refreshes its archive totals, folders and message list every four seconds, and everything once more when the run ends. An archive without messages shows "This archive is empty" with an Add mail button, or "Archiving mail…" while its first sync runs. The sidebar lists the archive's sources with their status squares. Under the labels, _Categories_ lists the kinds and topics that have messages, with counts from `GET /api/archives/{id}/categories` (never Health, hidden when the server has no insights), each linking to `/a/$archiveId?category=`. Below them, and in the search results header under the field, a muted _Some messages are still being read (N left)_ (`src/mail/still-reading.tsx`, a polite `status` region) shows while `GET /api/archives/{id}/insights/status` reports messages left, with N = `pending + categorize + reindex` (`stillReading` in `src/lib/reading.ts`); it polls every five seconds while N > 0 and shows nothing when insights are off (`404`) or caught up.

## Layout

Three panes: folders, message list, reader.

- From `68.75rem` (1100px): all three side by side.
- From `45rem` (720px): folders and list; the reader slides over the list and has a back button.

## Contacts

_Contacts_ sits under _All mail_ in the sidebar (`g c`, or the command palette) and uses the same three panes: the people list where messages are listed, the person where the reader is. The selected person is `?p=` in the URL, so `j`/`k`, `Enter`, `Esc` and `/` work as in mail and a person page is a link.

- **List.** People from [`/api/archives/{id}/people`](../../../crates/api/docs/README.md), by name, virtualized and loaded page by page like messages, as a `listbox` with the same gliding selection bar. Each row: a square with the initials (an icon when there is no name), the name (struck through when the person was removed) and, in mono, the first address or phone; at the right a hairline `≠` when the sources disagree, `×N` for several cards, a mail icon for people from mail alone, and the message count. The header shows the total, a download menu (_.vcf file_ with the latest version of each card, _Zip of every version_ with a manifest, for every contact or, while an address book filter is on, that address book; _Removed contacts too (.vcf)_ adds removed cards; plain links to `/api/archives/{id}/contacts/export`, `contactsScope` in `src/lib/export.ts`), a filter menu (source: everyone, with a contact card, from mail only, or one address book; _Sources disagree_; a small accent square on the button while filters are on) and a search field that filters as you type (200 ms) and keeps the text in `?q=`. When some people's sources disagree, a _≠ Differences N_ toggle under the title counts them for the current search and source and turns `?diff=` on or off (pressed while on); the count is the `total` of the same list with `has_differences`, so turning it on reuses the cached page.
- **Empty.** No people at all explains how to get some: import a `.vcf`, or turn on contacts and calendars for an account; owners and admins get buttons to both. No match offers _Clear filters_.
- **Person.** The initials, the name, the first address and phone as `mailto:` and `tel:` links, marks for the number of cards (or _From mail_), _Removed_ and _Sources disagree_, and which fields disagree. _Details_ lists every field: where the sources agree the value is shown once with small hairline source marks (account · address book); where they disagree each value is on its own line with its source and when it was last seen ("Work · work, seen today · Home · home, last seen 2024"), and the field has a `≠`. _Contact cards_ lists each source card with its address book, version count and last seen, linking to its history at `/items/$itemId`, and under it why the cards are one person ("same email ada@example.com: Ada Quill ↔ Ada Q."). _Correspondence_ gives the message counts (from them, to them), the first and last message, a hairline bar per year from the first to the last year, the conversations most recently active first (each opens its newest message in mail) and the files exchanged as attachment tiles. _Meetings_ lists events they organize or attend, newest first, with their answer, linking to the event. People from mail alone get a note on why they are listed instead of details. Under the marks, splits and joins made by hand that touch the person show as _Joined by hand_ or _Split by hand_ with the date, _Show the other person_ for a split, and _Undo_ for owners and admins (`overrideNotes` in `src/lib/people.ts`); a join also shows among the reasons as "joined by hand". Owners and admins get _Split…_ (with two or more cards: a dialog with a checkbox per card, enabled while at least one card stays on each side, `canSplit`) and _Join with…_ (a dialog that searches people as you type and joins with the one picked, `joinCandidates`); after either the lists refetch and the person shown is the one the server names (the rest after a split, the joined person after a join). A refused join (a split keeps them apart) shows the server's reason in the dialog. _Export cards_ downloads the person's cards as a `.vcf`, removed ones included.
- **Reader.** In an expanded message, every address that belongs to a person (`MessageDetail.people`) is a quiet underlined link to that person in Contacts; when the sender has a person, a _From_ line joins To and Cc so the sender can be followed too.

## Calendar

_Calendar_ sits under _Contacts_ in the sidebar (`g e`, or the command palette) and takes the whole space of list and reader. Instances come from [`/api/archives/{id}/calendar`](../../../crates/api/docs/README.md) for the span of the view in the viewer's zone (midnight to midnight, so a week across a daylight saving change is 167 or 169 hours); copies of one event in several calendars are one instance with a hairline "3 copies" mark (`×3` in the grids).

- **Header.** The span's title, _Today_, previous and next (a week in the week view, a month otherwise), a date field to jump to a day, the view toggle (Agenda, Week, Month) and a _Calendars_ menu: one checkbox per calendar with its color swatch and account ("From mail" for events found in invitations), _Show removed events_ and _Show all calendars_; a small accent square on the button while some are hidden or removed events are shown. Everything is in the URL.
- **Agenda** (the default, the most useful for an archive): the month's days that have events, each under a sticky mono day header (today marked in accent), each event a row with its time span in your zone (or _All day_), the calendar's color as a small square, the title (struck through when cancelled or removed) with the location under it, and the copies, _Cancelled_ and _Removed_ marks. An empty month says so.
- **Week**: a header of days (a click opens that day's week), an all-day row, then a 24-hour grid scrolled to 07:00 with hairline hour lines, a red hairline at the current time today, and events as blocks with the calendar color as a 2px left border; overlapping events share the day's width in columns (`layoutColumns`), events shorter than 15 minutes still get a 15-minute block, and events crossing midnight are cut per day.
- **Month**: whole weeks around the month, days outside it on the subtle background, today's number in an accent square, up to three events per day (all-day first) and "+N more", which opens that week.
- Dates stay on their dates in every zone, floating times read the same everywhere, and timed events are placed by their instant in your zone. Calendar colors are taken only when they are hex colors; a calendar without one gets a neutral swatch.
- **Event page** (`/events/$groupId`, a page of its own like the item page): the title with the number of copies and _Cancelled_; _When_ in your zone with the original zone underneath when it differs; _Repeats_ in words ("Every 2 weeks on Tuesday and Thursday, 5 times", `describeRecurrence` in `src/lib/recurrence.ts`), the rule as written, its exceptions, extra dates and changed dates; where; the organizer; the description. _Attendees_ is a table of people (linked to Contacts when a person has the address) with one answer column per copy, or one column for a single copy. _Copies_ lists each calendar with its swatch, account, _Shown_ on the leading copy (highest sequence, then the latest change), sequence, version count and a link to that copy's own history (`/items/$itemId`). _Differences between copies_ is a table of the fields that differ, one column per copy. _Mail_ lists the messages the event came in, each opening in the reader. _History_ merges every version of every copy, newest first, with the copy's calendar, method, date, raw download and changes.
- **Export.** A download button at the end of the calendar header offers _.ics file_ (the latest version of each event) and _Zip of every version_ for the events of the shown span (the shown calendar only when one is left on; removed events when _Show removed events_ is on), or for every calendar item of the archive. Plain links to `/api/archives/{id}/calendar/export` with `download`.
- **Links.** The invitation card's _Open event_ and a person's _Meetings_ open the event page (the card keeps _Mail history_ to the item page); meetings list copies of one event once.

## Rules editor

`/rules/$flowId` (`src/rules/flow-editor.tsx`), lazy, with `@xyflow/react` 12.12.0 (MIT) in its chunk. Everything it knows about steps comes from `GET /api/rules/catalogue` (`rulesCatalogueQuery`, read with the guards of `readCatalogue`), so the palette, the inspector and the docs match what the engine accepts; a step type the catalogue does not know is drawn dashed and can only be removed.

- **Top bar:** back to _Rules_ (keeping the archive), the flow's name and mode, the number of problems, _Saved_ or _Not saved_ and _Save_. Saving is `PUT /api/flows/{id}` with the version the editor started from: a `422` puts each validator issue (`flowIssues`) on its step (red border, the code and detail in the inspector) or, for the whole flow, under the top bar; a `409` says someone saved meanwhile and offers _Open again_, which loads their version. Leaving with unsaved changes asks first (`useBlocker`, and the browser's own prompt on reload).
- **Palette** (`src/rules/palette.tsx`): a search over the steps that may follow the flow's trigger (`palette`: the catalogue's `triggers` list), conditions then actions, each by title in the page's language. Clicking a step adds it right of the selected step (or the trigger), below the steps already linked from it, and links it from the first free port (`placeAfter`), so the whole flow can be built from the keyboard; dragging a step onto the canvas drops it there. Steps that send mail (`capability: mail.send`) are disabled with "Needs a sender grant on this archive" unless the archive's `rights.role` is `sender` (`mayUseType`), since the server refuses to save them otherwise.
- **Canvas** (`src/rules/canvas.tsx`): restyled to [design.md](../../../docs/design.md) with `base.css` only and the `.hm-flow` rules in `src/app.css`: square boxes with hairline borders (accent when selected, danger with problems), square handles, one-pixel step edges, the subtle background, tokens only. Each box shows its role, title, a one-line summary of its parameters (`paramSummary`) and one labelled output port per catalogue port (_Yes_, _No_, _Then_). Dragging from a port to a step links them (a port has one target, so the old link is replaced); a link to the trigger or to itself is ignored. Delete or Backspace removes the selected link or step (the trigger cannot be removed). Positions snap to a 16-unit grid and are saved in the flow (`position`, ignored by the engine); steps without one are laid out by distance from the trigger (`layout`). Zoom in, zoom out and fit sit bottom left. Node and edge state is fully controlled from the flow JSON (`toGraph`); only measured sizes are kept by the canvas.
- **Inspector** (`src/rules/inspector.tsx`, fields in `src/rules/fields.tsx`): _Settings_ is generated from the step's JSON Schema (`fieldsOf`: required fields first, `$ref`s into `$defs` resolved, the `x-holtmail` hint picking the input): text, number with the schema's bounds, switch, select for a `oneOf` of constants, checkboxes for an array of them (a `fieldset` whose legend is the field's label), a comma-separated list for addresses, a time input, a time zone field with the browser's zones, a folder field with the archive's folder paths, selects of the archive's identities (with _Automatic_ for `auto`), transports, calendars, address books and webhooks (a text field when that list cannot be read), and the query and template fields below. Labels come from `strings.rules.fields` and choices from `strings.rules.options` in both languages; the schema's English description shows under a field in English only, with _Optional_ and the default. Setting a field to empty removes the parameter, so the server's default applies. New steps get only the defaults the validator would otherwise ask for (`defaultParams`). The trigger's inspector can change the trigger type (the start link stays, parameters start over). Actions with a capability offer _Wait for confirmation_ (`confirm`) and say what they need; local actions say they change only Holtmail.
- **Docs panel** (_About_): the step's title and summary from the catalogue in the page's language and then the other one (each marked with its `lang`), its id and version, ports, the capability it needs, its template fields and the triggers it may follow.
- **Query field:** the search box's operator buttons (`operators`, `insertToken`) and, 400 ms after typing stops, how many archived messages the search finds now (`searchInfiniteQuery`'s first page `total`, from the index the rule matcher agrees with) or the parser's error.
- **Template fields:** a monospace text area (one line for subjects and titles, five for bodies, notes and comments), buttons that insert each variable as `{{ name }}` at the caret (`templateVariables`, `insertVariable`), and a live preview 400 ms after typing stops from `POST /api/archives/{id}/flows/preview` with the flow's trigger: the rendered text, _(empty)_, or the sandbox's error. A _Preview with_ picker above the inspector (shown for steps with template fields) searches the archive for the message the preview uses; without one, message fields render empty.

- **Mode line:** under the top bar while the flow is in test mode or off ("Test mode: runs are logged and nothing is carried out") with _Turn on_ (`PATCH /api/flows/{id}` with `mode: on`; disabled while there are unsaved changes, because turning on runs the saved version), or while the circuit breaker holds it with _Run again_ (the same mode again, which clears the pause). The mode badge in the top bar and the Settings → Rules list follow.
- **Tabs:** _Flow_ (the editor), _Runs_, _Versions_ and _Import and export_, a toggle group under the top bar. On _Flow_, a _List_ / _Canvas_ switch (hidden on phones).
- **List mode** (`src/rules/list-view.tsx`, logic in `src/lib/rules-list.ts`): for a linear flow (`chainOf`: from the trigger each condition continues only through _Yes_ with _No_ unlinked, each action through _Then_, a step without ports such as Stop only last, every step reached once, every step type known) one row per step, "When" for the trigger, "If" for the first condition of a run and "And" for the next, "Then" for the first action of a run and "And" for the next (`chainWords`), with the step's title, parameter summary, problems and, for conditions, "Otherwise the flow ends here". A row opens the inspector under it. _Move up_ and _Move down_ re-link the chain (`moveStep`, `canMove`: a closing Stop stays last), removing a step closes the gap (`removeStep`), and the palette under the list adds a step at the end or before a closing Stop (`appendStep`). Every list edit lays the steps out in one row (`withChain`), so the canvas shows the same order. A linear flow opens in the list and a branching one on the canvas; _List_ is off for a branching flow. Below `45rem` (`useLayout() === 'narrow'`) the list is the only mode, and a branching flow shows a line to open it on a wider screen while testing, runs, versions and export still work.
- **Test with a message** (`src/rules/test-panel.tsx`): on the canvas a _Step_ / _Test_ switch at the top of the right panel, in list mode a panel under the palette. A message picker (the archive's search), _As new mail_ (off tests as an imported message, which rules ignore) and _Test_, which sends the editor's flow, unsaved changes included, to `POST /api/flows/{id}/test` (`testFlow`): nothing is carried out or logged. The result (`readPlan` in `src/lib/rules-plan.ts`, drawn by `PlanSteps` in `src/rules/plan-view.tsx`): why the flow did not run (another trigger, not new mail), or the path with each step's outcome (_Yes_, _No_, _Action_, _Skipped: <reason>_ from `strings.rules.skip`, _Stop_), the actions with their rendered fields (`actionSummary`, without message ids) and _Waits for confirmation_, and whether later flows stop. The path is drawn on the canvas (`highlightOf`: the trigger, each visited step with the selected background and accent border, each port taken as a 2px accent edge) and marked in the list (accent left border and the outcome). Once the flow changes the result says it is stale and the highlight goes. A `422` puts the problems on the steps as Save does.
- **Runs** (`src/rules/runs-panel.tsx`): `GET /api/flows/{id}/runs` newest first, 50 at a time with _Older runs_ (`flowRunsInfiniteQuery`, `before` = the last run's id). Each row shows when, the status, _Test mode_, _Waits for confirmation_ when an action is held, and the version; opening it shows the trigger, the event id, the error, _Open the message_, _Show on the flow_ (draws that run's path on the flow tab while the editor holds that run's version unchanged; any edit, a run of another version or unsaved changes hide it, with a line saying whose path it was) and the plan with each action's result (`readResults`: done, skipped, failed, waits, left as a draft, test mode, confirmed, being confirmed, dismissed) and detail. A held action has _Confirm_ (`confirmFlowAction`, carried out as the person confirming) and _Dismiss_ (`dismissFlowAction`). For a flow whose saved trigger is `manual`, _Run by hand_ (`src/rules/manual-run.tsx`) above the log runs the saved version (disabled while there are unsaved changes) on a search, the newest 100 messages it finds, or on one picked message (`runFlow`); the new runs appear in the log.
- **Versions** (`src/rules/versions-panel.tsx`): `GET /api/flows/{id}/versions` (`flowVersionsQuery`), newest first with the current one marked; the chosen version shows its diff from the version before (`diffLines` over `diffText`: keys sorted, positions left out, so a move on the canvas reads "Only the layout changed"; unchanged lines beyond three from a change are folded), and _Open in the editor_ puts it in the editor unsaved; saving makes it the newest version.
- **Import and export** (`src/rules/json-panel.tsx`, `src/lib/rules-json.ts`): the editor's flow (unsaved changes included) as the `holtmail-rules` JSON (`exportText`, the same text `holtmail rules export` prints) with _Download_ (`<name>.json`, `exportFileName`) and _Copy_; _Choose a file_ or a pasted text with _Put in the editor_ replaces the editor's flow (`importText`: not JSON, or JSON without a trigger, is refused with the reason), not saved until _Save_, which validates it.

## Edits

Contacts and events are edited only where a save can succeed: every action below shows only while `CollectionDto.editable` is true for the collection (an account's collection, not `read_only`, not removed, and every lock for `pim.edit` open for the user: the `[write] enabled` switch, the account's _Edit contacts and calendars_ capability, an editor grant and the `write:pim` scope). Nothing is written by the dialog itself: each save is a held change ([API](../../../crates/api/docs/README.md#contacts-and-calendars-edits)) that the server sends only for collections in `write_through`. The dialog says which: "Edits stay in Holtmail until sending to <account> is turned on in Settings → Contacts and calendars", or "Saved edits are sent to <account>".

- **Where.** _New event_ in the calendar header (on the shown day), _New contact_ (a plus) in the people list header, _Edit card_ on a person (`cardEditable`: their `primary_card`'s address book is editable, or, without one, an address book a new card would go to; saved with `PUT /api/people/{id}/card`), _Add sender to contacts_ (a person-plus) in the reader toolbar when the first shown sender has no contact card yet, including a person known from mail alone (`newSender`, from `AddressPerson.has_card`; sent with `from_message`, the form prefilled by `senderDraft`), and _Edit_ and _Delete_ on the item page. A new item asks for the calendar or address book when there are several (by name, with the account). Delete asks first and says the archive keeps the item and its history.
- **Event form** (`src/items/event-fields.tsx`, logic in `src/lib/edits.ts`): title, _All day_, start and end date and time (moving the start keeps the length, `withStart`; an all-day end is shown inclusive and sent exclusive), the time zone (a field with the browser's zones, the viewer's first; empty means the same clock time everywhere), _Repeats_ (does not repeat, every day, week, month or year, or a custom `RRULE`; a rule the presets cannot say opens as custom), location, description, invitees (address and name; the organizer is shown, answers are kept) and reminders (minutes, hours, days or weeks before the start). A new event starts at the next full hour today, else 09:00, one hour long, in the viewer's zone, with a reminder 15 minutes before (`newEventDraft`). Saving an unchanged form sends the start and end exactly as served (`eventRequest`), so the server classifies it as no change; Holtmail does not send invitations yet, and the form says so.
- **Contact form** (`src/items/contact-fields.tsx`): first and last name (middle name, prefix and suffix behind _More name parts_), the shown name (it follows the parts while it was made from them, `withNamePart`), organization, job title, emails and phones with a label (home, work, mobile; other `TYPE` values are kept as they were), postal addresses and notes. Empty rows are dropped; a contact needs a name, an organization or an address (`contactRequest`). Photos, birthdays and other fields stay as they are (the API has no photo field); the form says to edit them as text.
- **Raw editing.** The dialog's _iCalendar_ or _vCard_ tab edits the whole item as text (what is served, or a minimal template with a fresh UID for a new item, `rawTemplate`); the server validates it. An item the form cannot show (`ItemEditDto` without a form) opens as text. The tab that is open when saving is what is sent.
- **Conflicts with another save.** Edits carry `expect` from `GET /api/items/{id}/edit`; a `409` says someone saved meanwhile and to open the item again. Other refusals show the server's words.
- **Local edit mark** (`src/items/local-edit-mark.tsx`): a hairline square badge with the four states of CLIENTS.md (`markText`): "Not sent to <account>" (held), "Sending", "Changed in <account> too" (a conflict, warning color) and "<account> refused" (danger color), with the reason as its title. It shows on the item page and on each open change in settings.
- **Timeline.** The item page's history is `ItemDetail.timeline` newest first: versions as before (a writeback version says "Written to the account by Holtmail") interleaved with changes ("Changed in Holtmail" or "Changed on a device", what it is, its state and reason). Each change opens _Show differences_ (open by default on a conflict): a table of fields with _Before_ (the version the change was made on), _Yours_ and _In the account_ (the latest version), changed values in the strong color and fields both sides changed marked _Both changed_, plus the change's own text under _As text_ (`src/items/change-diff.tsx`).
- After a save, delete or decision the item, the archive's lists, people, events and open changes are fetched again.

The live region announces once and for final states; the ticking number stays out of it. While an edit of the copy has not reached the account the panel says so instead of offering answers (`open_edit`). Answers through the server have no undo. The copy's Local edit mark sits next to the buttons, and when the answer stays in Holtmail for now a notice names the account that gets it later (`isHeld`).

**Organizing:** the event form's invitees say who sends the invitations (`organizingNote`, from `GET /api/collections/{id}/organizing`): "Invitations will be sent by email from ada@example.com" with a _Send invitations_ switch, the account's calendar server (now, or once the change reaches it), nobody for someone else's event, or that the user cannot send as the organizer, in which case the form saves with `invitations: false`. The note shows once an invitee has an address. On the event page of an event the user organizes, the attendees section starts with a count of answers (`tally`); every attendee's answer is in the table below it. The note and switch sit below the form and the raw tab alike and show whenever a save could tell someone: the event has or had invitees, or the raw text names an `ATTENDEE` (`reachesPeople`, `rawHasAttendees`). _Save_ waits for the answer of that request, which says so if it fails. The button shows only to editors and senders; the server refuses everyone else and refuses everyone while writing is off.

## Compose

Shown only in archives where `Archive.rights.compose` is true (the server sends mail, the `[write]` switches allow it, the user has a `sender` grant and may send as an active identity); without it the reader keeps its `mailto:` Reply and there is no compose button, reply action or outbox link. `useComposeHost` in `src/compose/compose-host.tsx` owns the open draft and the toast for the mail layout and hands out `useCompose()`: _New message_ (the button at the top of the sidebar, `n`, the palette) creates a draft; the reader's Reply (`r`), Reply all (`a`), Forward (`f`) and the menu with Reply to list (only when `MessageDetail.list_post` is set), Forward as attachment and Edit as new (a new draft with the message's recipients, subject, text and non-inline attachments by `message` and `ordinal`) ask the server for a template. A failure shows in the toast.

The pane (`compose-pane.tsx`, a lazy chunk with TipTap) slides over the reader from the right (`max-w-3xl`, _Full size_ widens it over the list) and fills the screen on narrow layouts. From the top:

- **From**: the route as one line ("From ada@example.com through Fastmail SMTP"; for a reply through an alias service the path, from `RouteDto.provider`, `contact` and `to`: "To SimpleLogin's reverse address for bob@example.org, from your mailbox ada@example.com through Fastmail SMTP", "To r1@relay.example.net, where Firefox Relay asked replies to go, from your mailbox …", or "From the alias shop@example.org through …" under `direct`) and under it why, one line per reason; a menu picks an identity the user may send as or _Pick automatically_. Without a route the server's `route_error` shows in words and Send is disabled. Texts come from `src/lib/route.ts`.
- **Leaks** (`LeakNotice`, texts in `src/lib/route.ts`): when the draft answers mail that came through an alias and a recipient would see the real mailbox, a notice lists each one with why and its one-click fixes (`leakFixes`): _Send through the alias service_ when the server offers `use_reverse_alias` (`reverseAliasFix`, the server swaps in the reverse alias and saves), _Send as <alias>_ when it offers `use_alias_identity` and the user may send as an active identity whose address is the alias or that is linked to it (`aliasIdentity`; otherwise a line says to set one up in Settings → Sending), and always _Remove_. Sending saves first and checks the leaks of the draft that save returned, so a fix made just before pressing Send counts; while leaks are left, from the button, `⌘/Ctrl+Enter` or _Send anyway…_ in the notice, a confirmation names how many recipients will see which real address, and only _Send and show my address_ there sends with `allow_leaks` (audited on the server). A `409 LeaksDto` on send (the server checks again, asking the alias service, and may find leaks the draft view did not) loads its leaks into the notice and opens the same confirmation (`refusedLeaks`); any other `409` fetches the draft again. The alias for _Send as <alias>_ is `route.alias`, which the server fills with the thread's alias when only an earlier message of the thread came through one. Send stays enabled for `needs_reverse_alias`, which the server resolves when sending. The draft's `context` (with the reverse aliases the server made) is kept from every save, so it is never overwritten by the one the pane opened with.
- **To**, **Cc**, **Bcc** (`recipient-field.tsx`, logic in `src/lib/recipients.ts`): chips; typing turns into chips at a comma, semicolon, Enter, Tab or on leaving the field; pasted lists are split outside quotes and angle brackets; `Name <address>` and quoted names are read; each address once ignoring case; text that is no address stays in the field with a message. From two characters People suggestions (`peopleInfiniteQuery`) by name or address, without chosen addresses, picked with the arrows and Enter or the mouse; `Esc` hides the suggestions only. Backspace in an empty field removes the last chip.
- **Subject**, then **Formatting** or **Plain text**. The rich editor (`rich-editor.tsx`, TipTap `@tiptap/react` and `@tiptap/starter-kit` 3.32.0, MIT) has bold, italic, strikethrough, lists, quotes and links (`http`, `https`, `mailto` only). A reply's or inline forward's quoted original (`<div class="holtmail-quote">` / `holtmail-forward` from the template, split off by `splitQuote`) stays outside the editor, shown read-only in a sandboxed frame whose policy loads no remote content, and is sent unchanged after the edited part. Replies to plain-text mail open in plain text. Switching to plain text keeps the words and drops the formatting; switching back makes paragraphs of the text.
- **Insert signature** (when the identity has one): the HTML signature after a `-- ` line at the end of the editor, or the text signature before the quoted original in plain text.
- **Attachments**: files from disk (the paperclip; uploaded into the draft one after another, each after the latest edits are saved) and from the archive (`archive-picker.tsx`: _Attach from the archive_ searches `has:attachment` plus the typed words, a message shows its attachments, one click adds `{ message, ordinal }`, which the server resolves to the stored bytes), with name, size and remove.
- **Send later** opens a date and time field (the browser's zone, a time in the past is refused); Send becomes _Send at …_.

Every change autosaves 1.2 s after the last one (`saveDraft` with the version; a `409` from another tab takes the server's version and saves again, so this window wins). The header says _Saving…_, _Saved_ or why not. `⌘/Ctrl+Enter` sends, `Esc` closes; the pane is marked `data-compose`, so the list shortcuts (`n`, `r`, `a`, `f`, `j`, `k`) never fire from inside it. Closing saves; a draft this window started (new, reply, forward) that was never touched, and an empty new draft, is deleted instead (`discardsOnClose`). Opening another draft, switching archives or leaving the mail screen saves pending edits first, and the browser asks before leaving the page with unsaved edits. A draft opened from the outbox is fetched fresh, and every save writes the cache. _Delete draft_ asks first. Sending saves, then calls `sendDraft` with an `Idempotency-Key` that stays the same across retries after a network error or a `5xx`, so pressing Send twice queues once, and is renewed after a definite `4xx` (`renewsSendKey`), since the server keeps that answer for the key. Keys come from `crypto.randomUUID`, or `crypto.getRandomValues` on plain HTTP.

After a send the **undo toast** (`undo-toast.tsx`, timing in `src/lib/outbox.ts`) counts down to the message's `send_at` ("Sending in 8 s") with _Undo_, which calls `undoOutbox` and reopens the draft it returns; a message scheduled more than a minute ahead says when it leaves and can be undone until then. When the window is over it reads "Message on its way" and goes away; _Outbox_ opens the outbox.

**Outbox** (`src/mail/outbox-page.tsx`, full width like the calendar): the user's drafts with _Edit_, then the messages grouped as Waiting, Scheduled, Failed, Unclear, Bounced, Sent and Cancelled, newest first. A row has the subject, a state badge, recipients, the `From`, when it was queued, sent or leaves, attempts, the next attempt, each refused recipient with the server's code and words, each bounced recipient with the report's status and words, a note (a delayed delivery), and the last error. Actions follow the server's rules: _Cancel_ (draft, waiting, trying again; confirmed; managers too), _Try again_ (trying again, failed, unclear; unclear asks first, since the recipients may get it twice), _Send again_ to everyone in the original envelope (ended, not unclear; asks first when someone already accepted it) and _Send again to the refused_ (only when some accepted), and _Open the sent message_. Try again and both Send again need the right to compose, so a manager without it sees the outbox with Cancel only. The Unclear group starts with a plain explanation: the connection broke after the message was handed over, Holtmail never sends it again by itself, check for an answer or the Sent folder first.

## Motion

Through `MotionProvider` and the token presets: the reader fades and rises 8px with the expressive curve when the selection changes; thread messages expand and collapse with height and opacity; the selection bar moves with the productive curve; panes and the folder sheet slide on narrow screens. Nothing in the list animates while it scrolls. With reduced motion, movement is dropped and height changes are instant.

Folders are grouped by account. Each shows its unread count emphasised next to the muted total; folders with nothing unread show the total only. Folders with a role come first (inbox, starred, important, drafts, sent, archive, all mail, junk, trash) and are never nested; the others follow alphabetically with natural number order and nest under their nearest existing parent path.

Archives with labels (Gmail) get a Labels section under the folders, with the same counts: Gmail's system labels first (Inbox, Starred, Important, Sent, Drafts, Spam, Trash), then the others by name with natural number order, nested under their nearest existing parent (`Work/Projects` shows as `Projects` under `Work`). The section is absent while the archive has no labels. Labels are refreshed with the folders while a source syncs.

## Theme

Chosen in the user menu or toggled from the command palette. The choice is stored in `localStorage` under `holtmail.theme` as `light` or `dark`; `system` removes the key. `light` and `dark` set `data-theme` on `<html>`; `system` removes it and the tokens follow `prefers-color-scheme`. Every storage access is wrapped in `try`/`catch`.
