# holtmail-integration (tests/integration)

The second test tier: the real `holtmail` binary against real servers in local containers. Unit tests prove each module against in-process fakes; these tests prove the composed binary, its config and its API against IMAP, JMAP, DAV, OAuth, S3 and proxy servers that other people wrote. The plan and its progress are in [TESTPLAN.md](../../../docs/TESTPLAN.md).

This is the only place in the repository allowed to reach the network, and only containers on this machine. Every test starts with `require_it!()` and returns at once unless `HOLTMAIL_IT=1`, so `cargo test --workspace` and `mise run check` stay network-free.

## Running

```bash
mise run it               # start the stack, build holtmail, run every suite
mise run it -- smoke      # one area: tests/smoke.rs
mise run it -- smoke tls  # one area, tests whose names contain "tls"
mise run it -- tls        # not a file name: a filter over every suite
IT_PROFILES=nextcloud mise run it   # also start optional compose profiles (nextcloud only with 20 GiB free)
IT_PROFILES=aliases mise run it -- aliases   # SimpleLogin, Postfix with OpenDKIM and CoreDNS for the alias suite
IT_PROFILES=docker mise run it      # also build holtmail:dev, holtmail:it-insights and holtmail:it-old and run the image tests
IT_THREADS=1 mise run it            # tests in one thread (default 4)
IT_WATCH=1 mise run it              # watch accounts in every suite (off by default; watch.rs and watch_pim.rs turn it on)
IT_RUST_LOG=debug mise run it       # RUST_LOG of the holtmail processes (default info)
mise run it-down          # stop the stack, remove its volumes and .state/
```

`mise run it` runs [`it.sh`](../it.sh): it starts Docker (`orb start` when OrbStack is installed and the daemon is down), brings the stack up with `docker compose up -d --wait`, builds `holtmail` once, and runs `cargo test -p holtmail-integration` with `HOLTMAIL_IT=1` and `HOLTMAIL_BIN` set (the binary in `$CARGO_TARGET_DIR`, or `target/` when it is unset). The stack stays up between runs, so re-runs take seconds; tests isolate themselves instead of resetting the servers.

A failing test prints the logs of the `holtmail` processes it started, with their data directory.

## Helpers

`src/` is a library the suites share:

- `Holtmail` (`holtmail.rs`): `Holtmail::start(Options)` writes a config into a temp dir (`listen` on a free port or `Options::port`, `data_dir`, `tls_ca_file` = the stack's CA unless `trust_stack_ca: false`, `sync_interval_minutes = 0` by default so only requested syncs run, plus `extra_config`), clears inherited `HOLTMAIL_*` variables, starts `serve` and waits until `/api/setup` answers. `logs()` holds stdout and stderr across restarts; `setup_token()`, `kill()` (SIGKILL), `stop()` (SIGTERM), `restart()`, `start_again()` after a kill or stop, `pid()`, `database()`, `age_flag_checks(hours)` (moves every folder's last flag read back in the database, as if that much time had passed), `query(sql, binds)` (rows of the database as text), `open_secret(account)` (the account's sealed password or refresh token, opened with the instance's `secret.key`), `rewrite_collection_tokens(token)` (replaces every collection's stored sync token and forgets its tag), `item_ids(collection)` (every stored item of a collection, of any kind, from the database), `execute(sql, binds)` (a write to the database while it runs), `cli()` (the bare `Command`, for sampling a CLI process), `command(args, stdin)` for other CLI commands on the same config (its log lines and stderr join `logs()`; its printed answer stays in the returned output).
- `Api` (`api.rs`): reqwest with a cookie store and the instance's `Origin` on every request, JSON in and out. `Api::setup_owner` creates `owner@example.com` from the setup link in the logs; `sign_in`, `create_archive`, `add_imap_account`, `accounts`, `sync` (starts a sync and waits for a run that ended after it), `wait_for_run`, `settle` (waits for the run Holtmail starts when an account is added), `add_jmap_account`, `enable_contacts(account, url)`, `calendar(archive, from, to, show_removed)`, `people` (all pages), `bytes(path)`, `import(archive, name, bytes)` (an upload, waiting for its task), `sync_contacts` and `wait_for_contacts` (the contacts and calendars run after a sync), `collections`, `items(archive, "contacts" | "events")`, `task_log(kind, account)`, `add_imap`, `update_account`, `folders`, `message`, `raw`, `tasks`, `sync_log` (the log lines of an account's latest sync task, one per folder: `INBOX: 2 new, 0 known, ...`), `messages` (all pages), `get_bytes(path)` (status and body), `download(path, file)` (streamed to a file), `import_within` (an upload with a longer wait), `delete` (declared JSON, as the web app sends it); `Api::sign_in_url` and `Api::behind_stack_tls` for instances that are not a `Holtmail` of the test (containers, Caddy).
- `data`: `Message::new(to)` with a unique subject, sender and `Message-ID`, builders for subject, date, body, an HTML body (`html`) and headers, `bytes()` with CRLF; `mbox(messages)`; `vcard(...)`; `icalendar_event(...)`. Names and addresses are invented, on `example.com` and `example.org`.
- `imap::Seeder`: `login`, `create`, `append(folder, flags, internal date, bytes)`, `append_many` (pipelined with `LITERAL+`), `status`, `command`, over plain TCP; `imap::utf7` encodes folder names.
- `relay::Relay`: a TCP relay in the test process in front of a server, in `Mode::Pass`, `StallAfter(bytes)` (holds the connection after that many bytes from the server) or `CutAfter(bytes)` (closes it), plus `cut_all()`. TLS passes through, so Holtmail still checks the certificate when it names `localhost`. Preferred over pausing containers: the failure lands at the same byte every run.
- `dav`: `DavServer` descriptors `RADICALE`, `BAIKAL`, `STALWART_DAV`, `NEXTCLOUD` (each with the IMAP server of its users: Dovecot, or Stalwart): `url()`, `user(prefix)` (a fresh user on the DAV server with the mail password), `add_user(user, password)`, `client(user)`, `homes(dav)` (the address book and calendar homes found through the current principal). `Dav` trusts the stack's CA: `propfind`, `create_address_book` (extended `MKCOL`), `create_calendar` (`MKCALENDAR`), `put_card`, `put_event`, `put` (also a whole `.vcf` or `.ics` onto a Radicale collection), `get`, `delete`, `request`. `baikal_php` and `baikal_insert` for Baïkal's database; `hrefs_in` reads hrefs out of a multistatus.
- `proxy::Proxy`: a plain HTTP reverse proxy on `127.0.0.1` in the test process in front of an https server (trusting the stack's CA, following no redirects): `Mode::Pass`, `NoSync` (`sync-collection` reports answered `501`), `Status(code)` (every request), `Rewrite { path, from, to }` (answers to paths containing `path` changed); `seen()` lists each request and whether it was passed on. Holtmail allows plain http to loopback, so it can stand in for a DAV server.
- `pim::PimRun`: one instance with an owner, an archive and a scanner: `add_mail`, `add_dav(server, user, url)` (an IMAP account with contacts and calendars turned on at the server's address or `url`, waiting for the first run without an error), `sync`, `log`, `items`, `collections`, `occurrences(from, to)`, `check_logs`; `pim::line(log, collection)` finds a collection's line in a task log.
- `jmap::Jmap`: a JMAP client with Basic or bearer `Auth` trusting the stack's CA: `session()`, `account(capability)`, `call`, `ok` (one method, failing on refusals), `upload`.
- `stalwart`: ports and passwords, `base_url()`, `session_url()`, `create_user(email)` and `api_key(email)` through the management API, and `Seeder` for mail (`mailboxes`, `role`, `create_mailbox`, `destroy_mailbox`, `import` into several mailboxes with keywords, `update`, `destroy`).

- `oauth`: `OAUTH_PORT`, `issuer()`, `client_id(prefix)` (a fresh client id that is also a fresh Dovecot user), `config(provider, client_id, redirect_url)` (an own client at the provider whose accounts connect to Dovecot's IMAPS port), `wait_ready()`, `authorize(url)` (plays the browser: adds `openid`, submits the provider's sign-in page as the `login_hint` when shown, returns the redirect with `code` and `state`), `callback(redirect)` (opens Holtmail's callback without following its `303`), `query_value`, `revoke(client_id, refresh_token)`, `refresh_accepted` (whether the provider still takes a refresh token; uses it up when it does).
- `images`: the image server and proxy ports and addresses, `Images` (files of one test under `.state/images/<served>/<unique>/`: `put`, `path`, `by_name`, `by_address`, `wait_served`), `Served` (`Plain`, `Slow`, `Paced`, `Wrong`), `requests(path)` and `wait_requests` (client addresses from nginx's access log), `png`, `jpeg`, `noise_png`, `oversized`, `seed`, `html(urls)`.
- `s3`: MinIO's endpoint, bucket and keys, `config(prefix)` (a `[blobs]` table), `env()` (the keys as Holtmail's environment), `key(prefix, blob)`, `objects(prefix)`, `delete(prefix, blob)`.
- `docker` (`IT_PROFILES=docker`): `Volume` (a named volume, removed on drop), `Container::start(image, volume, env)` on the stack's network with a published port, `url`, `logs`, `setup_token`, `exec(args, stdin)` (`docker exec -i … holtmail`), `wait_log`, `stop`, `start_again` (the published port can change), `connect(network)`, `copy_out`; `Container::run` takes the command after the image (`--config … serve`); `docker`/`docker_ok` for other commands, `image_present`, `DEV_IMAGE`, `INSIGHTS_IMAGE`, `OLD_IMAGE`, `OLD_COMMIT`, `NETWORK`.
- `dkim`: `Signer` (a PKCS#1 PEM key, a domain and a selector; `sign(headers, body, signed)` puts a `DKIM-Signature` over the named fields on top), `news_key()` for `news.example.com` from the `aliases` seed.
- `submit::send(port, from, to, data)`: one message over plain SMTP, the server's answer to the data.
- `stalwart::Seeder::emails(mailbox)`: the emails of a mailbox with `messageId`, `keywords`, `size`, `subject` and `mailboxIds`.
- `categories`: the data host's names (`DATA_NAME`, `MIRROR_NAME`, `DATA_NETWORK`), `fetches(prefix)` reading nginx's data log into `Fetch` (host, status, method, path, `If-None-Match`, `ETag`), `table(name, version, rows)` (a format 1 file through `holtmail-category-data`), `Release::new(version, files, not_after, key_id, key)` (a manifest from `Manifest::to_json`, signed over its exact bytes) with `publish(dir)` (data files, then signature, then manifest, each through a rename) and `publish_manifest(dir)`, `test_key()` (the fixture seed, id `TEST_KEY_ID` = `test`) and `stranger_key()`.
- `unsubscribe`: the one-click endpoint's names, networks and allowed subnet; `requests(prefix)` and `wait_requests` read nginx's 443 log into `Request` (method, path, content type, cookie, authorization, referer, origin, body).
- `memory`: `rss_kib(pid)` and `Peak::start(pid)`/`stop()` (peak RSS in MiB, sampled every 100 ms).
- `profile(name)`: whether `IT_PROFILES` names an optional compose profile; tests of optional servers return early without it.
- `unique(prefix)` for user names, folders and subjects that no other test or run uses.

## Adding a suite

1. Add the server to `compose.yaml` with a pinned image version that has an arm64 build, ports on `127.0.0.1`, a profile if it is optional or heavy, and seed files under `seed/<service>/`. Add its ports and passwords to `src/services.rs`.
2. Add `tests/<area>.rs`; start every test with `require_it!();`.
3. Isolate: a fresh user from `unique()` on servers that create users on sign-in, else a unique folder or collection name. Never rely on the order of tests.
4. Use only invented data from `data`, and end each test with a `LogScanner` over everything it seeded.
5. Record what the suite proved in [TESTPLAN.md](../../../docs/TESTPLAN.md) and tick the items in [VERIFY.md](../../../docs/VERIFY.md).
