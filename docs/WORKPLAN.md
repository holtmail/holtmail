# Work plan

A working checklist for building the first usable Holtmail: archive mail into a local or S3 blob store, search it, and read it in the web app. It is written so that work can resume from this file alone after a break or a context reset.

## How to resume

1. Read [AGENTS.md](../AGENTS.md), [PLAN.md](PLAN.md) and [design.md](design.md).
2. Find the first unchecked step below and the latest entry in [Log](#log).
3. `git status` shows work in progress; finish and check it before starting the next step.
4. After each step: `mise run check` (or the cargo commands in AGENTS.md), tick the step, add a log line.

Rules: no commits and no pushes without the maintainer's word; each step stays in its own module directories so the work can be committed module by module afterwards. Never start the web app in a browser to check it; check types, lint, tests and builds.

## Decisions

| Topic | Decision | Why |
| --- | --- | --- |
| Ids | UUIDv7 newtypes in `holtmail-core` (`ArchiveId`, `AccountId`, `FolderId`, `MessageId`, `UserId`) | Time-sortable, generated without the database, the same in SQLite and Postgres |
| Time | `Timestamp`: Unix milliseconds UTC as `i64` in `holtmail-core` | Plain, portable, sortable; formatting happens at the edges |
| Dedup | A message is unique per archive by its `BlobId`; the same blob in another archive is a separate message row pointing at the same blob | Access is granted per archive, storage is shared |
| Locations | A message can be in many folders; `(folder, uid)` rows record where it was seen, with `first_seen_at`, `last_seen_at`, `removed_at` | Archive never forgets; Gmail labels and copies across folders cost one blob |
| Attachments | Extracted on ingest into their own blobs and rows; the message blob stays whole | Dedup of forwarded files; fast attachment views |
| Threads | `thread_id` assigned on ingest from `References`/`In-Reply-To` through a per-archive index of `Message-ID`s, falling back to a new thread | Works for imports in any order: a late parent adopts the existing thread |
| Store | One crate `holtmail-store` with traits by area (`ArchiveStore`, `MessageStore`, `SyncStore`, `UserStore`) and a `Store` supertrait; `store-sqlite` on `sqlx` with embedded migrations | Small traits, one composition object |
| Search | `index-tantivy` behind `holtmail-index`; `holtmail-query` parses `from: to: subject: has:attachment before: after: in: is:` and free text | Database stays metadata-only and fast |
| Ingest | `holtmail-ingest`: raw bytes → blob → parse → attachments → store → index, one function used by sync and import | One path, one set of tests |
| HTML | `holtmail-sanitize` (ammonia): no scripts, no forms, remote images replaced by placeholders unless allowed, `cid:` rewritten to API URLs | The reader shows mail in a sandboxed iframe on top of this |
| Secrets | `holtmail-secret` contract, `secret-local`: XChaCha20-Poly1305 with a key file created on first start | Account passwords and OAuth tokens never stored in clear |
| API | `holtmail-api` on axum with OpenAPI from `utoipa`; JSON, cursor pagination, raw and attachment downloads | Typed client for the web is generated from it |
| Server | `apps/server`, binary `holtmail`: `serve`, `import`, `sync`, config in `holtmail.toml` with env overrides | One binary |
| Web tooling | Bun workspaces, Vite, React 19, TypeScript, oxlint, oxfmt; Tailwind v4; shadcn on Radix; Motion; TanStack Router and Query; `openapi-typescript` + `openapi-fetch` | Same tools as Holtkeeper |
| OAuth | `holtmail-oauth` (presets, PKCE, redirect parsing, token answers) with the HTTP call behind its `TokenEndpoint` contract, implemented by `oauth-http`; how an account signs in lives in its settings JSON (`oauth: { provider, needs_sign_in }`) and the refresh token in `sealed_secret`, so no migration; access tokens and waiting sign-ins only in server memory | Same contract/implementation split as fetch; tests need no network; the store stays ignorant of credentials |
| IMAP | `source-imap` on `async-imap` or `imap-next` (pick after a spike), tested against an in-process fake server | Tests never touch the network |
| Labels | Gmail labels are rows per archive (`labels`, `message_labels`), set from `X-GM-LABELS` of `[Gmail]/All Mail`; label folders are skipped while All Mail syncs; system labels read `Inbox`, `Sent`, `Starred`, `Important`, `Drafts`, `Spam`, `Trash` | One download per message instead of one per label; labels are many-to-many and filterable, folders stay what the server has |
| Attachments, derived | `holtmail-extract` contract + `extract-basic` (lopdf, zip + quick-xml, mail-parser's HTML to text); `holtmail-thumbnail` is a plain library (one pure function, nothing to swap); both results are blobs recorded in `DerivedStore` (`derived` table: source blob, kind, blob or "nothing"); text extracted on ingest once per attachment blob, thumbnails on first request | Raw bytes stay the truth; dedup across forwards; reindex and flag changes reuse cached text; failures recorded once |
| Export | `holtmail-export`, a library (formats are writers, not providers) over the store, blob and index contracts; mboxrd or a zip of `.eml` files written as a stream (`zip` stream writer, data descriptors) straight into the HTTP response, no temp files or background task; members export what they can read | Original bytes unchanged, about one message in memory, works on S3; a download needs no job queue or cleanup |
| Backup | `holtmail backup` writes one tar (`manifest.json` first, a `VACUUM INTO` snapshot, blobs the snapshot references through `InventoryStore`, `secret.key` only with `--include-secret-key`); `restore` only into an empty data directory, every blob checked against its hash, then a full reindex | One file that streams to a pipe; consistent while `serve` runs; works for S3 blobs; the key stays out unless asked |
| Task history | `TaskStore` in the store contract (`tasks`, `task_log`, migration 0009); the server's registry serves from memory and writes behind at most once a second (and on shutdown); 200 finished tasks kept; ids are UUIDv7 strings; tasks left `running` become `interrupted` at start | One process writes, no write per progress tick, ids stay unique across restarts, a crash loses at most a second of progress |
| Last runs | `SyncStore::set_last_run`/`last_runs` (`account_runs`), loaded into the runner at start; the schedule counts from the stored run; an interrupted sync is due at once | The sidebar, settings and "next sync" read the same after a restart |
| Minimum age | `min_age_days` in the account's settings JSON, `SyncOptions::min_age` in `holtmail-sync`; a folder stops at its first too-young new message so the UID cursor never passes unarchived mail; received time, else `Date`, else archived | Nothing is skipped for good; no contract change to sources; at most one batch re-fetched per folder and sync |
| JMAP | `source-jmap` on reqwest behind the unchanged-shape source contract: mailboxes are folders with location rows (an email in several mailboxes is one blob in several folders, like an IMAP copy); UID = `receivedAt` seconds << 22 \| 22 bits of FNV-1a of the email id, `UIDVALIDITY` from the mailbox id; new `FolderStatus::uids_ascend` (`false` for JMAP) makes the sync fetch every UID without a live location instead of those above the cursor; no mod-sequences, so flags are re-read daily; `Email/changes` not used; settings `{ url, username, auth: password\|token }`, the token sealed like a password and passed as `Credentials::AccessToken` (bearer), so `Credentials` is unchanged; https only, http just for loopback | Keeps `holtmail-sync`, the store and its cursors as they are (one small contract field instead of a generic cursor); stable UIDs without storing a map; a message moved into a mailbox later is still found; received-time order keeps the minimum-age stop correct |
| Graph | `source-graph` on reqwest, OAuth only (Microsoft, `Access::Graph`: `Mail.Read User.Read offline_access`; the account kind decides the scopes of the sign-in and of every refresh); folders from `mailFolders` with `childFolders` and hidden ones, search folders skipped, roles from the six well-known names; UIDs derived as for JMAP from `receivedDateTime` and the immutable id (`Prefer: IdType="ImmutableId"`), `uids_ascend: false`; each folder listed with a fresh delta query and its delta link kept as the opaque `FolderCursor::state`, which the next sync asks through the new `SourceSession::state`/`unchanged_since` (defaults keep IMAP and JMAP as they were): no changes means the folder is skipped, any change means a full delta listing; the state is stored only after a sync that left nothing deferred and no failure to retry, and dropped before any other sync; bytes from `$value` only; `429`/`503`/`504` waited out with `Retry-After`; created through the Phase 7 routes with `kind: graph` and `holtmail account add-graph` | Applying delta changes themselves would need every archived message's Graph id (retries, deferred messages and `@removed` entries carry or need only the id), which the store does not keep; skipping quiet folders gets most of the saving with no store change, and the `state` column already existed |
| Contacts and calendars model | `holtmail-pim` is a library (one right reading per format, like import): `calcard` 0.3.14 without default features (no JSContact/JSCalendar code, no serde) parses, and its types stay inside; Holtmail's own `Contact`/`CalendarObject`/`Event` with JSContact-like fields are the normalized view, serialized with a `type` tag; a parse failure is `Unreadable`, never an error | Owning the model keeps `calcard` swappable and the API stable; the JMAP feature pulls in `jmap-tools` for conversions nothing uses yet |
| Splitting files | A `.vcf` is cut into cards byte for byte; an `.ics` is cut per (component type, `UID`), each item's raw being the calendar's own lines + the `VTIMEZONE`s it names + its components, copied byte for byte, + `END:VCALENDAR`; the whole file is not stored | Each item's history is its own, as a CalDAV object resource would be; the bytes are the file's bytes, only regrouped, like mbox messages |
| Item identity in files | Collection = one file of the import account, known by its path inside what was imported (the uploaded name for an upload), named `X-WR-CALNAME` or the file name; item = `UID`, else `name:<lowercased FN>` for cards, else `blake3:<hash>`; repeats get `#2`; a re-import marks items missing from a non-empty file removed | Idempotent re-imports, versions for changes, and the archive never forgets; a card without `UID` cannot be followed through a rename (recorded in VERIFY) |
| Phones and emails | Emails lowercased as a whole without `mailto:`; phones E.164 only when written with `+`, `00` or `tel:+`, 8–15 digits, extensions cut; no default region, no per-country rules, no `phonenumber` crate | Small and predictable; a guessed country would link the wrong people |
| PIM storage | `PimStore` in the store contract; migration 0010 `collections`, `items` (with `archive_id` for access and listing), `item_versions` (numbered from 1, a row only when the blob differs from the latest), derived `pim_index` (columns plus the normalized JSON); photos split into their own blobs on ingest (`photo_blob_id` per version), the raw unchanged; removing an account keeps its collections (`account_id` NULL), removing an archive removes them and returns orphaned blobs; inventory and backups include version and picture blobs | Same shape as messages: access by archive, raw truth in blobs, derived fields rebuildable (`holtmail reindex` rebuilds `pim_index`) |
| PIM API | `GET /api/archives/{id}/collections`, `/contacts` (by name), `/events` (by start), `/api/items/{id}` (versions with diffs computed from the raw blobs per request), `/api/items/{id}/versions/{n}/raw`; members by archive grant like messages; client schema regenerated without factories until the pages exist | Data reachable now without committing to the UI's needs |
| Events from mail | One "From mail" calendar per archive (`remote_id` `holtmail:from-mail`, no account), not one per account | A message is stored once per archive however many accounts saw it, so per account would have to pick one; the archive is the unit of access and grouping, and Phase 17 groups copies across calendars by `UID` anyway |
| iMIP versions | Every `VEVENT`/`VTODO` with a `UID` in a `text/calendar` or `application/ics` part (inline or attached, of the message itself, not of attached messages) is a version of the item keyed by `UID` (`task:<UID>` for tasks); a part without `METHOD` counts as `PUBLISH`; versions are deduplicated by blob across the whole item (the same bytes in another message only add a link), ordered by `SEQUENCE`, `DTSTAMP`, message `Date`, blob id, and renumbered 1..n on insert; `item_version_messages` links `(item, blob)` to messages | Imports arrive in any order, like threading: the same mail always gives the same numbered history; links keyed by blob survive renumbering |
| Merged event view | The item's `pim_index` (and `ItemDetail.data`) is `holtmail_pim::merge` over all versions: the latest full `PUBLISH`/`REQUEST` as base, later instance updates and `ADD`s applied, `CANCEL` sets `CANCELLED` and keeps the fields, each attendee's last said `PARTSTAT` (from requests and replies, in version order) wins; `COUNTER`/`DECLINECOUNTER`/`REFRESH` change nothing; the history shows replies as `answer`s and cancels as one `status` change | A reply carries only one attendee and a cancel only identifying fields; diffing them against the invitation would read as removals |
| Invitations in the API | `MessageDetail.invitations` from the stored merged view (no blob reads per message), `updates_after` counts later non-answer versions, `my_status` matches attendees against the archive's account addresses; item detail adds `archive_id`, per-version `method`, `sequence`, `messages`; client gets `itemQuery`, `itemVersionRawUrl` and aliases | The reader stays cheap; imports have no address, so "your answer" is honest about not knowing |
| Old mail pass | `serve` reads calendar parts of messages that have a `text/calendar`/`application/ics` attachment row once at start, after the index pass, until the setting `invitations_from_mail` is set; `holtmail reindex` runs it too | Attachment rows already list calendar parts (mail-parser treats them as attachments, inline ones too), so only those blobs are read again |
| Collection contract | `holtmail-collection`: `collections()`, `changes(collection, token?)` (no token = everything plus a first token; `TokenExpired`, `Unsupported` as their own errors), `fetch(collection, ids)`, `list(collection)` (ids and ETags, sorted); ids are strings stable per server; its own `Credentials::{Password { username, password }, Bearer }` instead of `holtmail_source::Credentials`; `testing::FakeCollections` and `conformance(source, remote)` with a `Remote` trait (`put`, `delete`, `expire_tokens`) | Neither contract depends on the other's internals; the suite needs to change the server between calls, which only the implementation's own test can do |
| DAV ids and bytes | Collection and item ids are percent-decoded paths (requests encode them again); a collection id is a path, not a URL, with the URL remembered from the last listing; `address-data`/`calendar-data` text is taken without XML line-end normalization; multiget in batches of 50, falling back to one `GET` per item when refused | Servers encode hrefs differently between answers (`@`/`%40`); iCloud partition hosts may move while paths stay; raw bytes must stay byte for byte (CRLF) |
| DAV credentials | Sent only over https (http to loopback), to the configured origins, to where an **unauthenticated** RFC 6764 well-known lookup of a configured address led (followed through redirects), and to `*.icloud.com` when an iCloud host is configured; anything else (a redirect, home set or href on another host, a sibling under the same parent domain) is refused before anything is sent | No public-suffix list, so "same registrable domain" cannot be told safely; the mail domain naming its own DAV host through well-known is the owner's domain speaking; iCloud's home sets need the family rule |
| DAV recovery | A collection's `getctag` (else `sync-token`) equal to the stored one skips it; otherwise `sync-collection` since the stored token; a refused token (`valid-sync-token`, `400/403/409/412`) reads everything again with an empty token and diffs by ETag; a refusal without a token (`403/405/501`…) or a server without the report is listed with `PROPFIND` depth 1 each time; `507` pages are followed | Cheap when the server helps, bounded when it does not; same recovery shape as mail |
| PIM sync engine | New crate `holtmail-pim-sync` (not inside `holtmail-sync`, which is about folders, UIDs and messages); stores through `Ingest::ingest_item`, one item per DAV resource (calendar objects kept whole, kind from the first component); `items.etag` (migration 0012, the source's current ETag, also updated when bytes are equal) drives what is fetched; `collections.ctag`/`synced_at` recorded only after a collection's changes are applied; a failed item clears token and tag so the next run reads everything; collections the server no longer lists are marked removed with their items | Small modules with one job; the stored version's ETag stays the one it was seen with, so the current one needs its own column |
| When contacts sync | Right after each mail sync of the account (scheduled, Sync now, `holtmail sync`), whatever the mail outcome, as its own task kind `contacts_calendars`; turning it on starts one at once; the account's `status.contacts_calendars` is read from the latest such task (no extra store) | One schedule to explain and configure; a failure on one side does not hide the other; tasks already survive restarts |
| Contacts settings | `settings.dav = { enabled, contacts_url, calendars_url }`, off by default; turning on signs in and lists collections before storing; no address given: presets (Fastmail, iCloud, Yandex) by domain, else `https://<mail domain>` (well-known); one address given serves both; Google OAuth accounts always use Google's endpoints; Microsoft (IMAP OAuth and Graph) refused until Phase 18 (since then Graph accounts read them through Graph, see "Graph contacts and calendars"); import accounts refused | Same "check before saving" rule as connections; Nextcloud-style addresses are entered by hand |
| Google scopes | New `Access::ImapDav`: `mail.google.com` + `auth/carddav` (Google has no read-only CardDAV scope) + `auth/calendar.readonly`, but `auth/calendar` with Thunderbird's client (what Thunderbird itself asks for, so the borrowed client's verification covers it); `settings.oauth.access` records what the last sign-in granted; an account whose grant does not cover `ImapDav` shows `needs_consent` and skips contacts until Sign in again (which asks for `ImapDav` because contacts are on); refresh uses the granted access | Mail keeps syncing with the old grant; Google refreshes need no scope, Microsoft's would; nothing asks for more than the settings need |
| People | New library `holtmail-people` over the store contract (one grouping, nothing to swap): cards join by normalized email or E.164 phone through union-find, transitively, removed cards included, never by name; for every key several cards share, the first card (by item id) links to each other one with that key as the reason; a person's id is a UUIDv8 (`PersonId` in core) from BLAKE3 of the archive id and the group's smallest key (`email:` < `tel:`; `item:<id>` for a card with neither) | Stable across rebuilds and import order without storing anything; a person from mail keeps their id when a card with that address appears; only a merge of two groups changes one id |
| People from mail | An address without a card is a person when the owner wrote to it, or it is in at least 2 messages and its local part does not start with `noreply`, `no-reply`, `no_reply`, `donotreply`, `do-not-reply`, `do_not_reply`, `mailer-daemon`, `postmaster` or `bounce`; the owner's addresses (account addresses plus every `From` of mail in a `sent` folder or with the Gmail `Sent` label) are never people from mail and never count as anyone's correspondence; name from the display name used most | Imports have no account address, so "sent by me" needs the Sent folder; one-off senders and the usual automatic senders stay out without a list of providers |
| People storage | Migration 0013: `message_addresses` (one row per `From`/`To`/`Cc`/`Bcc` address, ASCII-lowercased, written by `insert_message`, filled for older mail by the migration with the same rule) and the derived `people` (the `Person` as JSON, name key, search text, card count, differences), `person_emails`, `person_collections`; `PeopleStore` (`mail_addresses`, `replace_people`, `list_people`, `count_people`, `get_person`, `people_by_email`, `correspondence`, `items_by_email`) with a conformance case | Per-address counts, a person's correspondence and the reader's lookup become indexed SQL instead of scanning address JSON; `Reply-To` is not stored with messages and does not count |
| People rebuilds | Whole archive at a time (a few aggregates and an in-memory union-find), never incremental: the runner rebuilds after an import, a mail sync with new mail and a contacts sync with changes (one per archive at a time, one more if asked meanwhile; splits, joins and undos go through the same queue through `Mailboxes::rebuild_people` and the API answers after a rebuild that started after the change; a panicking rebuild is caught by awaiting it as its own task, logged with the archive id only, and counts as failed), `holtmail import`/`sync` before exiting, `reindex` last, and `serve` once at start until the setting `people` is set | One new card can merge any number of groups, so incremental updates would need the same pass; the cost is milliseconds on test archives (VERIFY has the large-archive check) |
| Differences | A field differs when two current cards that fill it give different value sets (emails by normalized form, phones by E.164 else digits, other text by case and spaces); empty fields and removed cards never disagree; nicknames and notes never count; values of removed cards are still shown, marked removed | "Sources disagree" should point at real conflicts, not at an address book that stores less or a card deleted long ago |
| People API and web | `GET /api/archives/{id}/people?q&source&has_differences&cursor&limit` (`source` = `contacts`, `mail` or an address book id; `total` on every page), `GET /api/people/{id}` (merged fields with per-value sources and `seen_at`, cards, link reasons, correspondence over the addresses without the owner's: counts, years, 20 threads, 12 files without calendar parts, 50 meetings by organizer/attendee email), `MessageDetail.people` for reader links; members by archive grant; web Contacts at `/a/$archiveId/people?p=` inside the mail layout (same panes, `j`/`k`/`Enter`/`Esc`/`/`, `g c`) | One layout and keyboard model for mail and people; links from the reader are one indexed lookup per message |
| Recurrence | New library `holtmail-recur` with its own `RRULE` engine on wall-clock times (period by period, `BY*` as filters with ordinals per month or year, `BYSETPOS` per period, `DTSTART` always first and counted, `EXDATE`s counted in `COUNT`), zones from the object's `VTIMEZONE` (its IANA name, else its own `STANDARD`/`DAYLIGHT` rules), IANA and Windows names through `calcard`'s table and `chrono-tz` 0.10; skipped local times read with the offset before the change, repeated ones as the earlier; unknown `TZID`s float like `holtmail-pim`'s `utc` | `calcard::expand_dates` matches overrides by `SEQUENCE` too (Google and Outlook raise it on single instances), has no window and a private iterator; the `rrule` crate is the code `calcard` already vendors; RFC 5545 is small enough to own and test |
| Recurrence fields | `holtmail_pim::Event` gains `rrule` (as `calcard` writes it back), `rdates`, `exdates`, `this_and_future`, `last_modified`; `CalendarObject::zones` lists `VTIMEZONE`s (`iana`, or `observances` when no IANA zone is known); all skipped in JSON when empty; `diff` shows `rule`, `rdate`, `exdate` | The derived calendar works from the stored normalized view (`pim_index.data`) without reading blobs; old rows still deserialize |
| Calendar storage | `CalendarStore` in the contract, migration 0014: `event_series` (group, `SEQUENCE`, stamp = later of `DTSTAMP`/`LAST-MODIFIED`, span, window) and `occurrences`; an event that does not repeat or ends within 1 000 instances is stored whole, a longer or endless one for two years each way from its last rebuild; spans outside a stored window are expanded on the fly per request (`uncovered_series`) and never stored; rebuilt per item by `Ingest::derive_item` on every new version and by `reindex`; the migration sets `index_rebuild` | Cheap month and week reads from an index; no background job to "grow" windows and no stale extension rows; out-of-window answers are always complete |
| Event groups | New library `holtmail-calendar` (one calendar, like people): copies are event items with the same `UID` in an archive, group id `EventGroupId` = UUIDv8 of BLAKE3(archive, `uid:<UID>`, else `item:<id>`); leading copy by `SEQUENCE`, then stamp, then live before removed, then item id; instances fold by `(group, recurrence_id)` and show the leading copy; differences are `holtmail_pim::fields` compared as sets per copy (attendees without answers, answers listed per copy, `UID` and kind ignored) | An item already holds a series and its changed instances, so `UID` alone groups items and `RECURRENCE-ID` folds instances; ids need no table and survive rebuilds |
| Contacts and events in search | The same Tantivy index with a stored `doc_type` (`mail`, `event`, `contact`) and `item_id`; the contract adds `ItemDocument`, `put_items`, `remove_items`, `search_items`, `Clause::Kind` and `Clause::With` (sender or recipients of mail, organizer or attendees of events, a contact's own names and addresses); `search` stays mail-only; the schema change empties old indexes (Phase 8 path); `GET /api/archives/{id}/search/items` folds copies per page; `with:` matches words, not a person's other addresses | One index, one rebuild path and one query language; the mail API and its results stay as they were; resolving a person to all their addresses would need the people store inside the index contract |
| Calendar API and web | `GET /api/archives/{id}/calendar?from&to&collections&show_removed` (≤ 400 days, ≤ 5 000 folded instances), `GET /api/events/{group}?tz`, `group_id` on invitations and meetings; web `/a/$id/calendar?view&d&off&removed` inside the mail layout at full width (hidden calendars in `off`, so new ones show), agenda by default, week and month; the event page is its own route `/events/$groupId`; `j`/`k`/`o` through the layout's list controller, `t`, `a`/`w`/`m`, `←`/`→`, `g e` | Agenda is what an archive is read with; the URL holds the whole view; the grid views need the reader pane's width |
| Flag changes | `CONDSTORE`: `CHANGEDSINCE` the cursor's `highest_modseq` on every sync; without it, every archived UID's flags once a day in batches of 1000 UIDs (`flags_checked_at` in the cursor); changes rewrite the location's flags and labels and rebuild the index document | Cheap when the server helps, bounded when it does not; search stays true to the server |
| Item formats | Each source stores what its server sent: `holtmail-collection` names the media types (`media::{VCARD, ICALENDAR, GRAPH_CONTACT, GRAPH_EVENT, JSCONTACT, JSCALENDAR}`, Graph as `application/vnd.microsoft.graph.contact+json`/`event+json`, JMAP as the registered `application/jscontact+json`/`application/jscalendar+json`); `holtmail_pim::Format` reads each (`read_as`, `Format::stored(content_type, kind)` falls back to vCard/iCalendar for older rows); `IncomingItem.format`, the version's `content_type` and every re-read (`rebuild_item`, the item history) go by it; the raw download is `.json` for JSON | Raw stays the truth and the normalized view is derived from it whatever the protocol; no conversion at the edge that could lose fields |
| Conformance for JSON servers | `Remote::stored(collection, name, raw)` (default: `raw`) says what bytes a fetch returns for an item put as a vCard or iCalendar object, and the suite compares with it; media types are checked to fit the collection's kind and to be one per collection | A JMAP item is a JSON object inside a JSON answer and cannot carry a vCard as it is; Graph and DAV keep the default |

## Lessons from Mail-Archiver

What its code and issues teach, and what Holtmail does instead. Apply these when building each module.

| Mail-Archiver | Holtmail |
| --- | --- |
| Original bytes optional and off by default; bodies cut at 500 KB / 1 MB for `tsvector`; export and restore rebuild messages from database fields | The original bytes are always the blob; export and restore stream them unchanged; the index is separate and never truncates what is stored |
| Attachments and raw messages as `bytea` in Postgres: OOM kills, slow storage stats, dedup crashing at 341k mails | Bytes in `BlobStore` only; storage stats are kept as counters, not computed by reading bodies |
| One row per `Message-ID` with a single folder column: Gmail labels and copies lose their folders | Message unique by content hash; a location row per folder and UID |
| Messages without `Message-ID` and subject silently skipped | Every message is archived; identity is the content hash |
| No index on `Message-ID` | `(archive_id, rfc_message_id)` indexed for threading and lookups |
| Date-window sync re-downloading 12 hours each run, one message per round trip | UID watermark with `UIDVALIDITY`, `CONDSTORE` when present, batched `UID FETCH` of size and headers first, then bodies only for unknown messages |
| One broken message stops the checkpoint forever | Failures are recorded per UID with a reason and retried later with backoff; the cursor moves on |
| Sent dates stored in the display time zone | UTC milliseconds everywhere, formatted only in the browser |
| `simple` full-text search, `OFFSET` paging and exact `COUNT(*)`, unindexed `from:` | Tantivy with per-field indexing, keyset pagination, approximate counts |
| Delete-from-server trusts a `Message-ID` match | Only after the stored blob's hash matches the bytes fetched from that UID, and never when the server's date answer looks wrong |
| Graph: date filters, JSON-built messages, attached emails dropped | Graph delta queries and the MIME `$value` of every message |
| Legacy unsalted password hashes; a user-to-account table as the whole access model | Argon2id or passkeys; roles and per-archive grants as in PLAN.md |

Requests its users keep making, worth planning for: attachment content search, folder allow-lists, archiving only mail older than N days, SMTP or journal ingestion, webhooks, tamper-evident archiving, bulk delete with review, PDF export.

### Phase 7: Gmail and Microsoft sign-in (OAuth)

Microsoft turned off password sign-in for IMAP, and Gmail only accepts app passwords. Gmail, Google Workspace, Outlook.com, Hotmail and Microsoft 365 accounts sign in with OAuth and IMAP `AUTHENTICATE XOAUTH2`.

The default client is the public OAuth client Thunderbird ships for its desktop and mobile apps. Its client ids, and the Google client secret, are public in `mailnews/base/src/OAuth2Providers.sys.mjs` in comm-central. An installed-app client cannot redirect to a self-hosted address, so the flow is:

1. Holtmail opens the provider's sign-in page with PKCE and `state`. The redirect goes to the loopback address the client is registered for:
   - Google: `http://localhost` or `http://127.0.0.1`, on any port.
   - Microsoft: `http://localhost` or `https://localhost`. Check this against the live registration; Thunderbird bug 2036505 shows Microsoft switching between the two. Current comm-central sets no `redirectionEndpoint` for either provider, so both use the default `http://127.0.0.1` (plus a port); Holtmail uses `http://127.0.0.1`, overridable with `redirect_url`.
2. When Holtmail itself runs on that loopback address, its callback route catches the code directly.
3. Otherwise the browser lands on a page that does not load. The user pastes that page's address into Holtmail, which reads `code` and `state` from it.

The owner can set their own client per provider in `[oauth.google]` or `[oauth.microsoft]`, with `client_id`, `client_secret` and a `redirect_url` that points at Holtmail's callback. With their own client there is no paste step.

Risks to state in the docs and the UI:

- The consent screen names Thunderbird.
- The provider can block or rate-limit a borrowed client at any time.
- Whether this fits the provider's terms is the user's call.

Use device code flow for Microsoft if Thunderbird's registration allows it (to check). Not done: checking it needs a live request to Microsoft; the paste flow covers Microsoft for now.

### Message insights (planned 2026-11-06)

The design is in [INSIGHTS.md](INSIGHTS.md).
