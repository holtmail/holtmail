# holtmail-api

The HTTP API the web app and scripts use. Built on `axum`; the OpenAPI description is generated with `utoipa` from the handlers and served at `/api/openapi.json` (`holtmail openapi` prints it). Response types are the API's own, separate from the store's, so the store can change without changing the API.

## Usage

```rust
let app = holtmail_api::router(ApiState { blobs, store, index, auth, mailboxes, operations, aliases, fetcher, secure_cookies, insights, write, sending, devices, serve, rule_hooks });
axum::serve(listener, app.into_make_service_with_connect_info::<SocketAddr>()).await?;
```

`ConnectInfo<SocketAddr>` gives the login rate limit the client address; without it every client counts as `0.0.0.0`.

## Mailboxes

Talking to mail servers, sealing passwords and reading mailbox files need implementation crates, which this crate may not depend on. The server hands them in as `mailboxes: Arc<dyn Mailboxes>`:

| Method | Guarantees |
| --- | --- |
| `add_imap(archive, NewImapAccount)` | Signs in and lists folders first; nothing is stored when that fails (`MailboxError::Invalid` with a message safe to show). Then stores the account with its password sealed and starts its first sync in the background |
| `configure(account, AccountChange)` | Changes the connection (`connection` for IMAP, `jmap` for JMAP), password or token and sync interval; a new connection or password is checked by signing in first and nothing changes when that fails |
| `sync(account)` | Starts a sync in the background; does nothing when one of this account is running |
| `import(account, file)` | Imports the uploaded file into the import account in the background and removes the file afterwards |
| `upload_dir()` | Where uploads are written before `import` |
| `status(account)` | `AccountStatus { running, new_messages, finished_at, error, next_sync_at, contacts_calendars, watch, contacts_watch }` of the running or last run; `contacts_calendars` is the latest contacts and calendars sync (`ContactsCalendarsRun { running, finished_at, summary, error }`); `watch` and `contacts_watch` are `WatchState::{Off, Starting, Live, Polling, Reconnecting(reason)}` for its mail and for its contacts and calendars |
| `add_jmap(archive, NewJmapAccount)` | Signs in to the JMAP server and lists its mailboxes, stores the account with its password or token sealed and starts its first sync; nothing is stored when signing in fails |
| `details(account)` | `AccountDetails { connection, jmap, sync_interval_minutes, min_age_days, oauth_provider, needs_sign_in, sign_in_reason, contacts_calendars, watch }` as stored; `contacts_calendars` is `ContactsCalendars { enabled, contacts_url, calendars_url, needs_consent, protocol, calendars_protocol, interval_minutes, has_dav_password, caldav_offer }` (`ContactsProtocol::{Dav, Graph, Jmap}`), `None` for accounts that cannot have them (import, Microsoft over IMAP); `watch` is `WatchSettings { mode: WatchMode::{Off, Inbox, Folders}, folders }`, `None` for import accounts |
| `insights_changed(archive)` | Derived categories of `archive` may be stale (an override or a trust list changed): wakes the stage-B pass and returns at once; calls may be coalesced. The default does nothing. Called after every override `PUT` or `DELETE` and every trust-list change |
| `receive_push(id, body)` | `true` when `id` is a push address the server registered and `body` decrypts with its keys (the account's contacts and calendars then sync soon); `false` (the default) otherwise |
| `start_oauth(OAuthStart)` | A Gmail or Microsoft sign-in for `OAuthTarget::NewAccount { archive, name }` or `OAuthTarget::Account(id)`, for a new account of `kind` `Imap` or `Graph` (Microsoft only); signing in again keeps the account's own kind. Returns the provider's page, a `state` valid for a few minutes and once, whether the answer must be pasted (`needs_paste`) and whether Thunderbird's client is used. `Invalid` for an unknown provider, archive or account, Graph with Google, or an account that is neither IMAP nor Graph |
| `finish_oauth(answer)` | From the pasted address or the callback's query: exchanges the code, checks that the mail server (IMAP, or Graph by listing the folders) accepts the token, stores the refresh token sealed, then starts a sync. Creates the account, or replaces an existing account's sign-in (moving a password account to OAuth). Nothing is stored when a step fails; `Invalid` with a reason safe to show |
| `oauth_return_to(answer)` | The page a waiting sign-in returns to, without using it up |
| `apply_itip(archive, message)` | "Apply anyway": the message's incoming iTIP parts decided again with the authentication check overridden, an attendee's `REPLY` merged into the user's organizer copies where it applies; returns the parts' `InboxNote`s as they are now. Never sends anything. The default changes nothing and returns none |

Failures are `MailboxError`: `Invalid` (`400`, a message safe to show), `Conflict` (`409`: the request is valid but cannot run until the server catches up, such as a deletion review using insight operators while messages are still being read) and `Backend` (`500`).

## Sign-in

| Method and path | Body | Answers |
| --- | --- | --- |
| `GET /api/setup` | | `200 { "needed": bool }`: `true` while there are no users |
| `POST /api/setup` | `{ "token", "email", "name", "password" }` | `200 { "user" }` and the session cookie; `400` for bad input (password under 10 characters, malformed email, empty name); `403` for a wrong or used token or when users exist |
| `POST /api/login` | `{ "email", "password" }` | `200 { "user" }` and the session cookie; `401` for a wrong email or password (the same message for both); `429` with `Retry-After` seconds after 10 failures from one address for one email within 15 minutes |
| `POST /api/logout` | none or `{}` | `204` and a cookie that expires the session; idempotent |
| `GET /api/session` | | `200 { "user" }` or `401` |

`user` is `{ "id", "email", "name", "role" }` with `role` one of `owner`, `admin`, `member`. Sign-in answers carry `Cache-Control: no-store`.

The setup token comes from the setup link the server prints at start while there are no users (`/setup?token=...`); see [holtmail-auth](../../auth/docs/README.md).

### Session cookie

`holtmail_session=<token>; HttpOnly; SameSite=Lax; Path=/; Max-Age=2592000`, plus `Secure` when `secure_cookies` is set (the server sets it for an `https` `public_url`) or the request has `X-Forwarded-Proto: https`. The token is 43 base64url characters; only its hash is stored. Sessions last 30 days from sign-in.

### Access and CSRF

- Every route except the five above, `/api/oauth/callback` and `/api/openapi.json` answers `401 { "error": "sign in required" }` without a live session. Unknown paths under `/api/` answer `401` too, and `404` once signed in.
- Owners and admins manage the instance: users, archives, accounts, transports and identities. Writing to a mail server and sending need more (see [The one check](#writing) and [Who may do what](#sending)): only the instance owner writes by role; admins and members need an `editor` or `sender` grant, only the owner gives those, and `/api/audit` is the owner's alone. Members may read the archives granted to them (`GET` on `/api/archives…`, `/api/messages…`, `/api/threads…`, `/api/items…`, `/api/events…`, `/api/people…`, including the exports, the people overrides, the categories and the category overrides; splitting, joining and undoing, and `PUT` or `DELETE` of a category override, are writes and answer `403`) and change their own profile (`/api/me…`) and their own devices (`/api/devices…`); archives, messages, threads, contact or calendar items, events and people they may not read answer `404` as if missing, and every other write, `/api/users…`, `/api/accounts…`, `/api/audit` and `/api/oauth…` answer `403`. The sending routes (drafts, `messages/{id}/reply` and `forward`, the outbox, transports, identities and the default identity) pass `access::check` for members too and are checked in their handlers by `may_send` and the grant role. `GET /api/archives` lists only readable archives.
- `POST` requests must have `Content-Type: application/json` or, for uploads, `application/octet-stream` (else `415`); neither can be sent cross-site without a CORS preflight, which the server never grants. `PUT`, `PATCH` and `DELETE` need no content type, since browsers never send them cross-site without a preflight either. Every request other than `GET`, `HEAD` and `OPTIONS` is refused with `403` when they carry an `Origin` whose host differs from `Host`, or `Sec-Fetch-Site: cross-site`. Together with `SameSite=Lax` this keeps other sites from acting with a visitor's session.
- The OpenAPI description declares the cookie as the `session` security scheme; the sign-in routes are marked as needing none.

## Endpoints

| Method and path | Returns |
| --- | --- |
| `GET /api/archives` | Archives with totals and `rights`: the current user's `ArchiveRightsDto { role, manage, compose }`. `role` is the grant (`reader`, `editor`, `sender`; the owner is `sender`, admins without a grant `reader`); `manage` is true for owners and admins; `compose` is true only when the server sends mail, the `[write]` switches allow sending, the grant is `sender`, the credentials carry `send:mail` and the user may send as an active identity of the archive. The web shows compose, reply actions and the outbox only with `compose`; every send is still checked as below |
| `GET /api/archives/{id}` | One archive, with `rights` as above |
| `GET /api/archives/{id}/accounts` | Its accounts with `status` (including `next_sync_at`), `connection` (host, port, security, user name and excluded folders of IMAP accounts; `null` for members and other kinds; never the password), `jmap` (`url`, `username`, `auth` and `exclude` of JMAP accounts; `null` for members and other kinds; never the password or token), their own `sync_interval_minutes`, `min_age_days` (only mail at least that many days old is archived; `null` for all mail), `oauth_provider` (`google`, `microsoft` or `null` for a password) and `needs_sign_in` (the provider no longer accepts the sign-in, so it does not sync until someone signs in again; or a capability needs consent the sign-in lacks, see `sign_in_reason`), `sign_in_reason` (why signing in again is needed while the sign-in still works and syncs go on, such as Microsoft's consent to send; `null` otherwise), and `contacts_calendars` (`enabled`, `contacts_url` and `calendars_url` (`null` for members), `needs_consent` (a Google or Microsoft Graph account that must sign in again to grant access), `protocol` (`dav`, `graph` or `jmap`); `null` for import accounts and Microsoft accounts over IMAP). `status.contacts_calendars` is the latest contacts and calendars sync (`running`, `finished_at`, `summary`, `error`), `null` when there was none. `contacts_calendars` also has `calendars_protocol`, `interval_minutes` (`null` follows the mail interval), `has_dav_password` and `caldav_offer` (a CalDAV address that answered for a JMAP account without calendars; `null` for members). `watch` is `{ mode, folders }` (`null` for import accounts and members); `status.watch` and `status.contacts_watch` are `{ state, reason }` with `state` `off`, `starting`, `live`, `polling` or `reconnecting`. `trusted_authserv_ids` and `suggested_authserv_id`: see [Trust lists](#trust-lists) (`null` for members and import accounts). `writable` lists the mailbox capabilities (`mail.flags`, `mail.move`, `mail.delete`, `mail.expunge`, `mail.append`) the current user may use on the account now, every lock of `may_write` open; empty for import accounts and in every other answer that carries an `AccountDto`. The web offers mailbox actions from it; each change is checked again |
| `GET /api/archives/{id}/folders` | Its folders with message and `unread` counts (`unread`: not removed, without `\Seen`) |
| `GET /api/archives/{id}/labels` | `LabelDto[]`: every label carried by at least one message (Gmail), by name, with `messages` and `unread` (not read in any folder the message is in); empty for archives without labels |
| `GET /api/archives/{id}/messages?folder&label&category&after&limit` | A page of message summaries, newest first; `next` continues. `label` keeps messages carrying that exact label, alone or with `folder`. `category` keeps messages with that effective kind (`personal`, `list`, `bulk`, `notification`) or topic (`purchases`, `travel`, `finance`, `health`, `social`, `jobs`, `events`, `government`); `health` is allowed when asked for by name and lists nothing when the server turns it off; any other value is `400`. Each summary has `flags` (in `folder` when given, else the union over the folders it is in), `thread_count`, `folder_ids`, `labels` (sorted) `insight_kinds`, `kind` and `topic` (see [Insights](#insights)) |
| `GET /api/archives/{id}/search?q&sort&offset&limit` | Search with the [query language](../../query/docs/README.md); `400` with the parser's message for a bad query. Each summary has `attachment_match`: `true` when the words were found only in text inside its attachments (from the index's `attachment_hits`; always `false` in plain lists) |
| `GET /api/archives/{id}/export?format=mbox\|zip\|pdf&folder&label&q` | Downloads the messages with [`holtmail-export`](../../export/docs/README.md): the whole archive, or one folder (id), label or search, as one mbox file (`application/mbox`), a zip of `.eml` files in folder directories (`application/zip`), or a zip of PDFs laid out the same way (`pdf`, `application/zip`). `Content-Disposition: attachment` with a name like `Personal - INBOX.mbox`, `Cache-Control: no-store`, `nosniff`. The body is streamed while it is written (chunked, about one message in memory); an export that fails part way ends the response without its final chunk, so clients see a broken download rather than a short file that looks complete. `400` for another format, more than one of `folder`, `label` and `q`, or a query that does not parse; `404` for an unknown archive or a folder of another archive. A `GET`, so members can export the archives granted to them and anything in them, like they can read it; the session cookie goes along with a plain link (`SameSite=Lax`). Messages whose bytes are missing are left out; the log line at the end carries the counts |
| `GET /api/messages/{id}/pdf` | The message as a PDF (`application/pdf`, `Content-Disposition: attachment`, named after the subject) made by `holtmail_export::message_pdf`, with the original message attached inside it; the same access check as the message; `404` for an unknown message |
| `GET /api/archives/{id}/contacts/export?format=vcf\|zip&collection&person&removed` | Downloads contacts with [`holtmail-export`](../../export/docs/README.md), streamed like the mail export: `vcf` is the latest version of each contact in one `text/vcard` file (vCard bytes unchanged, Graph and JSContact cards written as vCard), `zip` every version as stored with `manifest.json`. `collection` narrows to an address book, `person` to a person's cards (not both: `400`); `removed=true` puts contacts removed from their source into a `vcf` too (a zip has them always). `404` for an unknown archive, address book or person of another archive. Members export what they can read |
| `GET /api/archives/{id}/calendar/export?format=ics\|zip&collection&from&to&removed` | The same for calendar items: `ics` (`text/calendar`, iCalendar bytes unchanged, Graph and JSCalendar events written as iCalendar) or `zip`; `collection` narrows to a calendar; `from` and `to` (Unix milliseconds, both or neither) keep events with an instance in that span, leaving tasks out. `400` for another format, one end of the span alone, or a span that ends before it starts |
| `GET /api/messages/{id}` | The reader's view: headers, `list_post` (the `List-Post` address without `mailto:`, `null` when the message names no list; the web offers Reply to list only when it is set), `preview`, `in_reply_to`, `references`, plain text, attachments (each with `url` and, for PNG, JPEG, GIF and WebP up to 25 MiB, `thumbnail_url`), folders, `labels`, and `invitations`: for each event or task its calendar parts are a version of, `InvitationDto { item_id, group_id, uid, version, method, summary, start, end, all_day, recurring, location, organizer, status, cancelled, my_status, version_count, updates_after }`. `group_id` opens the event with its copies at `/api/events/{group_id}`. The fields describe the event as the archive knows it now (the merged view); `version` and `method` are this message's; `updates_after` counts later versions that changed the event (not replies, counters or refreshes); `my_status` is the answer of the attendee whose address is one of the archive's own addresses (accounts, identities and own aliases), absent when none matches. Times are `EventTimeDto { value, time_zone, utc }`. `people`: `AddressPersonDto { email, person_id, has_card }` (`has_card`: the person has a contact card that is not removed, rather than being known from mail alone) for each `From`, `To`, `Cc`, `Bcc` and `Reply-To` address (and the sender an alias service hid) that belongs to a person, each address once (one indexed lookup per message). `alias`: `MessageAliasDto { provider, alias, sender, reverse_alias, signed, known, note }` when an alias detector recognised the message or one of its recipients is a known alias, else `null` (see [Aliases](#aliases)). `insights`: codes, action links, parcels, reservations, orders, invoices, passes and unsubscribe links (see [Insights](#insights)) |
| `GET /api/messages/{id}/body?remote=block\|proxy\|direct` | The sanitized HTML body as a full document (`text/html`); a plain text body is escaped into `<pre>`. See [Remote images](#remote-images) |
| `GET /api/messages/{id}/remote/{key}` | One remote image of the message: the archive's saved copy, or fetched now by the server. `404` when the message links no such image or the server will not fetch it, `502` when the remote server fails |
| `GET /api/messages/{id}/raw` | The original bytes as `message/rfc822`, named after the subject |
| `GET /api/messages/{id}/attachments/{ordinal}` | Attachment bytes |
| `GET /api/messages/{id}/attachments/{ordinal}/thumbnail` | A preview at most 320 px on its longest side, JPEG or PNG (with transparency), made by [`holtmail-thumbnail`](../../thumbnail/docs/README.md) on first request and kept as a derived blob (`DerivedKind::Thumbnail`), so later requests read it back. `404` for other types and for images that do not decode; that answer is recorded and the image is not decoded again. At most two thumbnails are made at a time |
| `GET /api/threads/{id}` | Every message of the conversation, oldest first |
| `GET /api/archives/{id}/insights/status` | `{ pending, reindex, categorize, running }`: messages whose insights are missing or from older extractors, messages whose search entry is behind their categories or insights (the store's reindex queue; overrides queue the messages they change), messages whose categories were derived under another stage-B fingerprint than the current one (`count_needing_derive`, 0 without `InsightsConfig.deriver`), and whether the server is computing them now. The web shows "Some messages are still being read (N left)" with N = `pending + categorize + reindex`; `404` without an insights runner. Members may read it |
| `GET /api/insights/data` | `InsightsDataDto { holtmail_version, files, updates }` for Settings → About: the server's version; `files` as `DataFileDto { name, file, version, rows, license, origin, attribution }` sorted by name (`name` `wikidata` or `ut1`, `license` an SPDX id, `origin` `bundled` or `downloaded`, `attribution` "Contains data from UT1 (Université Toulouse Capitole), CC BY-SA 4.0" for `ut1`, else `null`); `updates` as `DataUpdatesDto { enabled, data_sources, last_checked_at, last_outcome }` (`last_checked_at` in Unix ms, `last_outcome` `updated`, `not_modified`, `refused` or `failed`, both `null` before the first check). Without an insights runner it answers `200` with no files and updates disabled, so the page still shows the version. Every signed-in user may read it, members included (explicit in `access.rs`) |
| `GET /api/archives/{id}/categories?include=health` | `CategoriesDto { kinds: [{ id, count }], topics: [{ id, count }] }` in taxonomy order with zeros, from `category_counts` (exact as soon as a write or override returns). `health` is in `topics` only with `include=health` and when the server has it on; another `include` is `400`. `404` without an insights runner. Members may read it |
| `GET /api/archives/{id}/category-overrides` | `CategoryOverrideDto[]`, address overrides first, then by key (see [Categories](#categories)). `404` without an insights runner. Members may read it |
| `PUT /api/archives/{id}/category-overrides` | Owners and admins (`403`). See [Categories](#categories) |
| `POST /api/messages/{id}/unsubscribe` | Owners and admins (`403`). `{ "confirm": true }`; see [One-click unsubscribe](#one-click-unsubscribe) |
| `DELETE /api/archives/{id}/category-overrides/{override}` | Owners and admins (`403`). `204`; the messages it matched get their derived values back at once. `404` for an unknown id or one of another archive |
| `GET /api/archives/{id}/collections` | `CollectionDto[]`: address books (`kind: "contacts"`) and calendars (`calendar`) of the archive, removed ones too (`removed_at`), by kind and name, with `items` (live) and `removed_items`, `account_id` (absent once the account was removed) and `account_name`, `synced_at` (the last sync from its server; absent for imported files and the "From mail" calendar), `name`, `color` |
| `GET /api/archives/{id}/contacts?collection&removed&after&limit` | `ItemPage` of contacts by name without regard to letter case, unnamed last; each `ItemSummaryDto` has `title`, `readable`, `versions`, `first_seen_at`, `removed_at`, `uid`, `emails` (lowercased) and `phones` (E.164). `removed`: `hide` (default), `include` or `only`; `400` for another value or a foreign cursor |
| `GET /api/archives/{id}/events?collection&removed&after&limit` | `ItemPage` of events by start (UTC), a recurring event once by its first start, events without a start last; summaries add `starts_at`, `ends_at`, `all_day`, `time_zone` (as written), `recurring` and `organizer`. Tasks are archived but not listed here yet |
| `GET /api/items/{id}` | `ItemDetail`: the summary (with `archive_id`), `data` (the normalized view of the latest version from [`holtmail-pim`](../../pim/docs/README.md): `{"type": "contact", ...}`, `{"type": "calendar", "components": [...]}` or `{"type": "unreadable"}`; for an event found in mail, every version merged by `holtmail_pim::merge`) and `versions`, oldest first, each with `number`, `seen_at`, `etag`, `content_type`, `readable`, `raw_url`, `changes` against the version before (`{ field, before?, after? }`, see `diff` in holtmail-pim; empty for the first; for versions from mail, `timeline` in holtmail-pim: replies list `answer`s, a cancellation one `status` change, updates diff against the previous update), and for versions from mail `method` (lowercase), `sequence` and `messages` (`SourceMessageDto { id, subject, from, date }`, oldest first). Diffs are computed from the raw blobs on each request |
| `GET /api/archives/{id}/people?q&source&has_differences&cursor&limit` | `PersonPage { items, next, total }` of the people derived by [`holtmail-people`](../../people/docs/README.md), by name without regard to case, nameless last; `total` counts every match on every page. `q` matches a name, address or phone substring; `source` is `contacts` (with a card), `mail` (from mail alone) or an address book id; `has_differences=true` keeps people whose current cards disagree. Each `PersonSummaryDto` has `name`, `email`, `phone`, `emails`, `phones`, `cards`, `removed_cards`, `collection_ids`, `messages` and `from_me` (summed per address), `first_message_at`, `last_message_at`, `differences`, `removed`. Pages of 100 by default, at most 500. `400` for another `source` or a foreign cursor |
| `GET /api/people/{id}` | `PersonDetailDto`: the summary; `fields` merged from the cards (`PersonFieldDto { name, values, differs }`, each value with its `sources`: `ValueSourceDto { item_id, collection_id, collection_name, account_name, removed, seen_at }`, where `seen_at` is when the card was removed, else the later of its address book's last sync and its latest version, else when its latest version was seen); `cards` (`PersonCardDto { item_id, collection_id, collection_name, account_name, title, readable, versions, first_seen_at, removed_at, seen_at }`, current ones first, most recently seen first; their history is `/api/items/{item_id}`); `links` (`PersonLinkDto { from_item_id, to_item_id, kind: email\|phone\|hand, value }`, why the cards are one person; `hand` is a join made by hand, its `value` the join's id); `correspondence` over their addresses without the owner's (`messages`, `from_them`, `to_them`, `first_at`, `last_at`, `years`, up to 20 `threads` with the latest message's id and subject, up to 12 `attachments` without calendar parts, each as an `AttachmentDto`); `meetings`: up to 50 events whose organizer or attendees include them, latest start first, copies of one event once, with `group_id`, `role` (`organizer`, `attendee`), their `status` (lowercase `PARTSTAT`), `cancelled` and `removed_at`; `overrides`: the splits and joins made by hand that touch one of their cards or addresses. `404` for an unknown or malformed id |
| `POST /api/people/{id}/split` | `SplitRequest { cards }`: item ids of some of the person's cards. Stores a split ([`holtmail-people`](../../people/docs/README.md) says how it holds), waits for `Mailboxes::rebuild_people` and answers `201` with the `PersonOverrideDto`; its `people` are the person left with the other cards (it keeps its id) and then the person of the moved cards. `400` for no cards, every card, or a card that is not theirs; owners and admins only (`403`) |
| `POST /api/people/join` | `JoinRequest { people }`: two or more person ids of one archive. Stores a join naming each person by its first card (`item:<id>`) or, for a person from mail, its address (`email:<address>`), waits for the rebuild and answers `201` with `people` = the one person they are now. `409` when a split made by hand keeps them apart (nothing is stored), `400` for fewer than two different people or people of different archives, `404` for an unknown person; owners and admins only |
| `GET /api/archives/{id}/people/overrides` | Every split and join of the archive, oldest first: `PersonOverrideDto { id, kind: join\|split, keys, from, created_at, created_by, people }`, `people` being who holds its keys now (for a split, the side of `from` first). Members read it for granted archives |
| `DELETE /api/people/overrides/{id}` | Undoes a split or join: removes it, waits for the rebuild and answers the removed `PersonOverrideDto` with `people` holding its keys afterwards. `404` for an unknown id; owners and admins only |
| `GET /api/archives/{id}/calendar?from&to&collections&show_removed` | `CalendarRangeDto { occurrences, calendars, truncated }`: every instance of the archive's events overlapping `from..to` (Unix ms, at most 400 days, else `400`), from [`holtmail-calendar`](../../calendar/docs/README.md): stored instances, and instances worked out on the fly for repeating events whose stored window does not cover the span. ### Insights

See [INSIGHTS.md](../../../docs/INSIGHTS.md). `ApiState.insights` is `Option<InsightsConfig>`, `None` when the server runs no insights runner; messages then carry `insights: null`.

```rust
pub struct InsightsConfig {
    pub fingerprint: String,                 // the runner's current extract_fp
    pub show_possible: HashMap<KindTag, u16>, // lowest score of a shown Possible item, per kind
    pub progress: Arc<InsightProgress>,
    pub health: bool,                        // [insights.categories] health
    pub deriver: Option<Arc<Deriver>>,       // stage B, for the status counts
    pub one_click: Option<Arc<dyn OneClick>>, // None: [insights] one_click = false
    pub data: Arc<DataStatus>,               // loaded category data, set by the server
}
InsightsConfig::new(fingerprint)             // no Possible items, health on, fresh progress, empty data status, one-click off
InsightProgress::{start, advance(n), finish, running, done}   // atomics, shared with the walk
DataStatus::{set(DataSnapshot), get() -> DataSnapshot}        // whole values only; empty until the first set
pub struct DataSnapshot { pub files: Vec<LoadedDataFile>, pub updates: DataUpdates }

pub enum DataOutcome { Updated, NotModified, Refused, Failed }
```

The API never loads or downloads category data: the server sets `DataStatus` after start-up and after every check, and `GET /api/insights/data` serves the latest value.

`MessageDetail.insights` is `MessageInsightsDto { status, trust, own, kind, topics, items, unsubscribe }`, read from the stored row without reading the message bytes (`insight_view`; a thread reads `insight_views_among` once):

- `status`: `pending` without a row; `outdated` when the row's fingerprint is not the current one or its items were written in another shape or hold a kind this build cannot read (the readable items are still served); otherwise `ready`, `partial`, `unparsable` or `unreadable` from the row's outcome.
- `trust`: `TrustDto { state, domain, provider }` from the stored stage-B row: `aligned` with `domain`, `relayed` with the alias service as `provider`, `unverified`, or `unknown` (also before stage B, with no row).
- `own`: from the stage-B row; before it, a `From` address is one of the archive's own addresses (an account's `address` or an alias address the store knows, `own_alias_addresses`), compared lowercase when the request is served.
- `kind`: `CategoryKindDto { id, source, overridden }` with the effective kind; `source` is `override`, `content`, `domain` or `headers`; `null` before stage B.
- `topics`: `CategoryTopicDto { id, source, overridden, held_back? }[]` in taxonomy order: the effective topics, and the topics of the applying override that the trust gate kept off this message, marked `held_back: "not_verified"` (a sensitive topic on a sender that is not aligned). With `health` off, `health` never appears.
- `items`: `InsightDto`, tagged by `type`:
  - `code { value, origin_bound, confidence, score, forwarded }`
  - `unsubscribe { https, mailto, http, one_click, list_id, confidence, score, forwarded }`
  - `action { action, url, destination, display_host, via, tracked, text_domain_mismatch, destination_differs_from_sender, confusable, label, confidence, score, forwarded }`; `action` is a `LinkActionDto` (`verify`, `confirm`, `activate`, `reset_password`, `sign_in`, `magic_link`, `view_order`, `track`, `check_in`, `wallet_save`, `view`)
  - `parcel { carrier, number, check_digit, track_url, track_host, confidence, score, forwarded }`; `track_host` is the display host of `track_url`

  - `reservation { reservation, confidence, score, forwarded }`; `reservation` is a `ReservationDto` tagged by `kind`:
    - `flight { reservation_number, carrier, flight_number, departure_airport, arrival_airport, departure, arrival, passengers, seats, url, url_host }`
    - `lodging { reservation_number, name, address, checkin, checkout, guests, url, url_host }`
    - `train` and `bus { reservation_number, number, departure_station, arrival_station, departure, arrival, passengers, seats, url, url_host }`
    - `event { reservation_number, name, start, end, venue, tickets, url, url_host }`
    - `food { reservation_number, name, start, party_size, url, url_host }`
    - `rental_car { reservation_number, company, pickup, pickup_location, dropoff, dropoff_location, url, url_host }`
  - `order { number, merchant, total, status, url, url_host, confidence, score, forwarded }`
  - `invoice { number, payee, total, due, url, url_host, confidence, score, forwarded }`; `due` is `YYYY-MM-DD`
  - `pass { style, organization, description, relevant, boarding, attachment, signature_checked, confidence, score, forwarded }`; `style` is `boarding_pass`, `event_ticket`, `coupon`, `store_card` or `generic`; `boarding` is `{ pnr, passenger, legs: [{ from, to, carrier, flight, date, seat }] }` where `date` is a `YYYY-MM-DD` string or `{ month, day }` when no year is known

  Times are `TimeDto { local, offset, zone }`: `local` is the wall time as written (`YYYY-MM-DDTHH:MM:SS`, seconds kept, fractions dropped), `offset` the offset written with it (`+01:00`), `null` for a time written without one, and `zone` the IANA name when the message gave one. They are never converted to UTC or to the server's zone. Money is `MoneyDto { amount, currency, exponent }`: `amount` is the stored minor units as an exact decimal string with exactly `exponent` fraction digits (`1200` JPY, `1234.50` USD, `-3.000` KWD), formatted with integer arithmetic over the whole `i64` range, never through a float or a JSON number. Every `url` comes with `url_host`, `display_host` of its host (the A-label form when confusable); a URL without a host (`mailto:`) is `null` with its `url_host`. Items below `likely` are shown only when `show_possible` names their kind (`link` for actions) with a score they reach.
- Action flags are computed when the response is built from the stored hosts with [`holtmail-links`](../../links/docs/README.md), never stored, so a Public Suffix List update changes them without recomputing insights:
  - `display_host`: `display_host(destination host)`: the Unicode form, or the A-label form when `confusable` (a mixed-script or confusable label, UTS 39).
  - `text_domain_mismatch`: the anchor text reads as a host (`text_host`) whose registrable domain is not the destination's; when either side has no registrable domain, only an exact host difference (case and a trailing dot aside) counts.
  - `destination_differs_from_sender`: the destination's registrable domain is not the sender's: the stage-B row's `sender_domain` (the alias's claimed real sender for alias mail), or before stage B the first `From` address's domain; `false` without either. When either side has no registrable domain (an IP literal, a single-label host, a bare public suffix), any host difference (case and a trailing dot aside) counts, so a link to `http://192.0.2.1/` is flagged.
  - An action whose destination has no host (never written by the extractors) is left out.
- `unsubscribe`: `{ https, mailto, http, one_click: { available, reason }, last_request? }` from the first shown unsubscribe item, else `null`. `available` is `true` exactly when `reason` is `null`. `reason` is the first that applies: `members`; `no_post_header` (no `List-Unsubscribe-Post` signal); `not_https` (no https link on port 443, explicit or default, without user name or password); `multiple_fields` (the auth facts count more than one `List-Unsubscribe` or `List-Unsubscribe-Post` field); `no_post_header` (the item is not one-click, so the field's value is not exactly `List-Unsubscribe=One-Click`); `no_trusted_authserv` (trust `unknown`, or no stage-B row); `not_aligned` (`relayed` or `unverified`); `not_covered` (`one_click_ok` is false); `disabled` (`InsightsConfig.one_click` is `None`); `recently_requested` (the last request for the list was `accepted` or `redirected` less than 24 hours ago). A failed request does not change the reason; the route answers `429` for a minute instead.
- `last_request`: `UnsubscribeRequestDto { outcome, status, requested_at }` of the latest one-click request for the item's list in this archive, from any message, left out when there is none and always for members. `outcome` is `accepted | redirected | refused | http_error | network`, `status` the HTTP status when the list answered, `requested_at` Unix milliseconds. The list key is the item's `list_id` (the `List-Id` identifier, lowercased), else the stage-B row's registrable `sender_domain`; with neither there is no last request. A message reads it with one `last_unsubscribe`, a thread with one `last_unsubscribes` for all its keys.
- Code and action items are left out on own mail; reservations, orders, invoices, parcels and passes stay, for members too.
- For members: code and unsubscribe items are left out, and so are action items whose `action` is `sign_in`, `magic_link`, `reset_password`, `verify`, `confirm` or `activate` (`view_order`, `track`, `check_in`, `wallet_save`, `view` and parcels stay), and `unsubscribe` keeps only `{ one_click: { available: false, reason: "members" } }` with every link `null`.

`MessageSummary.kind` is the effective kind and `MessageSummary.topic` the stored `list_topic` (the first effective topic in taxonomy order), never `health`; both `null` before stage B. Members see both.

`MessageSummary.insight_kinds` lists the kind names of the stored row's bits (`code`, `link`, `unsubscribe`, `reservation`, `order`, `invoice`, `parcel`, `pass`, in that order), never values; `code` is left out for members and on own mail, and `link` on own mail. Members keep `link`: the stored bits do not say which actions a message has, and a message may hold actions members see (`view_order`, `track`), so the glyph can stand for actions their card does not show.

### One-click unsubscribe

`POST /api/messages/{id}/unsubscribe` with `UnsubscribeConfirmRequest { "confirm": true }` sends the RFC 8058 request for the message's list. Owners and admins only (members `403` in `access.rs`); `404` for an unknown message or without an insights runner. Any other body is `400` with `reason: null`; a URL in the body is ignored, only the link stored with the message is used.

1. `Operations::fresh_insights(id)`: the server recomputes the insights row when its fingerprint is not the current `extract_fp` (one blob read) and the stage-B row when it is missing or its `derive_fp` is not the current one, then wakes the walk if anything was queued for reindexing.
2. Under one process-wide lock, so two clicks never send twice, the view is read again and the reason function above runs on it without the last request. Any reason is `400` with `UnsubscribeRefusalDto { error, reason }`; `disabled` when `InsightsConfig.one_click` is `None`.
3. The list key's last request (`last_unsubscribe`): `accepted` or `redirected` less than 24 hours ago answers `200` with that stored request and `repeated: true`, sending nothing; `refused`, `http_error` or `network` less than a minute ago answers `429` with `Retry-After` in seconds.
4. `OneClick::post(url)` once: `Ok` gives `accepted` (2xx), `redirected` (3xx, not followed) or `http_error` with the status; `Err(Refused)` gives `refused` and `Err(Unavailable)` `network`, both without a status. The request is stored with `record_unsubscribe` (a new UUIDv7 id, `requested_by` the user) and answered `200` with `UnsubscribeResultDto { request: UnsubscribeRequestDto, repeated: false }`.

The log line carries the archive, message and user ids, the outcome and the HTTP status, never the URL, host, list id or addresses. OpenAPI lists `200`, `400`, `401`, `403`, `404`, `429` and `500`.

### Categories

Effective kinds and topics come from the stage-B rows the server derives ([`holtmail-insights`](../../insights/docs/README.md)); the API reads them and edits overrides. Every route here answers `404` without an insights runner.

`CategoryOverrideDto { id, scope, key, kind, topics, created_at, created_by }`: `scope` is `address` or `domain`, `kind` a kind name or `null` (keeps the derived kind), `topics` topic names or `null` (keeps the derived topics); `created_at` (Unix milliseconds) and `created_by` (a user id) are those of the first `PUT` for the scope and key. Unknown topic bits from a newer build are not listed; `health` is not listed while the server has it off.

`PUT /api/archives/{id}/category-overrides` takes `CategoryOverrideRequest { scope, key, kind?, topics? }`:

- `key` is normalised with `holtmail_insights::override_key`: trimmed, lowercase, IDNA A-label, no trailing dot; a `domain` key becomes its registrable domain (an address is accepted there and its domain taken), an `address` key keeps its `+tag`. A key it refuses is `400`.
- At least one of `kind` and `topics` (`null` counts as missing), else `400` "nothing to change". An unknown scope, kind or topic is `400`; `topics: []` sets an empty set. `health` is `400` while the server has it off, and an existing override's stored `health` is kept when it is replaced then.
- Idempotent on `(scope, key)`: it replaces the override with the same scope and key and keeps its id. Edits run one at a time (a module mutex), the store recomputes the matching rows in the same transaction, so counts and `?category=` lists follow at once, and `Mailboxes::insights_changed` is called. Answers `200` with the stored override.
- Per axis, an address override wins over a domain override, which wins over the derived value. Sensitive topics of an override apply only to `aligned` messages (the message's `topics` lists them `held_back`), and `health` follows the server's flag.

#### Trust lists

`AccountDto.trusted_authserv_ids` is the account's list of trusted authserv-ids and `suggested_authserv_id` the suggestion of [INSIGHTS §4.3](../../../docs/INSIGHTS.md): with an empty list, `holtmail_insights::suggest_authserv` over `recent_auth_facts(account, 1000)`; never used for trust. Both are `null` for members and for import accounts (the SMTP account included), whose trust comes from `[insights] import_authserv_ids` and `[smtp] trusted_authserv_ids`.

`PATCH /api/accounts/{id}` with `trusted_authserv_ids` replaces the list (owners and admins): at most 16 ids, each trimmed and 1 to 255 bytes of printable ASCII without spaces, duplicates dropped ignoring case, order kept; `400` otherwise and for import accounts. When the list changed it is stored with `set_trusted_authserv_ids` and `Mailboxes::insights_changed` is called; the new list reaches `derive_fp`, so stage B recomputes the archive.

`holtmail_api::trusted_authserv_preset(provider)` is the list a new account of `gmail`, `fastmail`, `outlook`, `icloud` or `yandex` starts with. The provider is read from the account's IMAP host, JMAP address or OAuth provider when an account is added or signed in with OAuth, and the preset is stored only while the list is empty. Every preset is empty until a VERIFY entry confirms that the provider stamps its id and strips forged fields carrying it, so new accounts start with no trusted server today.

## Devices

Device credentials ([SERVE.md, Devices and sign-in](../../../docs/SERVE.md#devices-and-sign-in)). Every route acts on the signed-in user's own devices only; another user's device answers `404`. `ApiState.devices` is the `DeviceAuth`; `ApiState.serve` is `ServeOptions { members, trusted_proxies, recent_sign_in, servers, local_flags, client, profile_links }`; `client` is a `ClientSetup { server, instance, mail_domains }` (the [`holtmail-client-setup`](../../client-setup/docs/README.md) `Server`, the instance id that fixes profile identifiers, and the operator's own mail domains), `None` without a `public_url`; `profile_links` holds the open one-time links.

- **Recent sign-in.** Making a device, and any raise of its rights (a new scope or protocol, a wider archive list, another mail archive), need a session that started within `recent_sign_in` (5 minutes). It takes the socket's address, unless that is in `trusted_proxies`; then it takes the rightmost `X-Forwarded-For` hop that is not itself a trusted proxy (the leftmost when all are), and hops left of a malformed one are not believed.

## Writing

The foundation for every endpoint that writes to a mail, contacts or calendars server or sends mail ([WRITE.md](../../../docs/WRITE.md)). Sending (below) is the first user of these pieces.

**Instance switches.** `ApiState.write` is `WriteSwitches { enabled, send, rules }` from the server's `[write]` config, all `true` by default. A switch that is off closes its capabilities for every account, whatever the account allows: `enabled` closes everything, `send` closes `mail.send`, `rules` closes rule flows.

**Scopes.** `Scope` is `read`, `write:mail`, `send:mail`, `write:pim` or `rules`; `require_session` puts `Scopes` next to `CurrentUser` in the request's extensions. A cookie session carries every scope. Devices are managed through `/api/devices` and carry their scopes on the protocol front ends (`holtmail_access::Scopes::of_device`), not through `require_session`. API tokens do not exist yet; when they come, they will carry the subset they were issued with.

**The one check.** `may_write(state, user, scopes, account, capability)`, a thin wrapper over [`holtmail_access::Access`](../../access/docs/README.md), is what every write endpoint calls before it changes anything. Every lock must be open:

| Lock | Open when |
| --- | --- |
| Instance switch | `enabled`, and `send` for `mail.send` |
| Account capability | The capability is on for the account; `mail.expunge` also needs `mail.delete` |
| Archive role | The instance owner has every right. Everyone else needs a grant on the account's archive: `editor` for `mail.flags`, `mail.move`, `mail.delete`, `mail.expunge`, `mail.append`, `pim.edit` and `pim.respond`, `sender` for `mail.send`. Admins read every archive but write only with a grant; they get no `sender` by role |
| Scope | `write:mail` for the `mail.*` capabilities except `mail.send`, which needs `send:mail`; `write:pim` for `pim.*` |

It fails closed: an unknown account, an archive the user may not read (`404`), a closed lock (`403`) or a store failure (`500`) refuses. `Access::may_use_rules(user, scopes, archive)` is the same for rule endpoints (`rules` switch, `editor`, `rules` scope). Write endpoints for members must also be let through `access::check`, which refuses every other member write; the sending routes are let through and check the grant themselves. `audit(state, user, kind, archive, account, targets)` records the write before it happens, and a write whose entry cannot be stored fails.

**Account capabilities.** `GET /api/accounts/{id}/capabilities` answers `{ account, capabilities, active, switches }`: the capabilities turned on (`mail.flags`, `mail.move`, `mail.delete`, `mail.expunge`, `mail.append`, `mail.send`, `pim.edit`, `pim.respond`; all off for a new account), the ones in effect under the switches, and the switches. `PUT` with `{ "capabilities": [...] }` replaces them; an unknown name or `mail.expunge` without `mail.delete` answers `400`. Only owners and admins (the archive's managers) read or change them; a change is audited as `capabilities_changed` with the new names as targets.

**Grant roles.** `PUT /api/users/{id}/grants/{archive}` with `{ "role": "reader" | "editor" | "sender" }` grants or changes the role; `DELETE` takes the grant away (idempotent). Each role includes the ones before it. Only the owner gives or takes away `editor` and `sender`, also by setting such a grant back to `reader` or by leaving the archive out of `archives` in `POST`/`PATCH /api/users…`; admins manage `reader` grants of non-owners. Each change is audited as `grant_changed`, also through `archives`. People in `GET /api/users` carry `grants: [{ archive, role }]` next to `archives`; `archives` in `PATCH /api/users/{id}` keeps the roles of archives that stay and grants new ones as `reader`. An admin may not change the email or password of someone with an `editor` or `sender` grant (`403`), so an admin cannot sign in as a sender.

**Audit log.** `GET /api/audit?archive=&before=&limit=` lists entries newest first (`limit` 100 by default, 500 at most; `before` is the last `seq` of the previous page): `{ seq, at, user, kind, archive, account, targets, count }`, ids and counts only. Only the instance owner reads it.

**Idempotency-Key.** Every mutating request may carry `Idempotency-Key` (1 to 255 visible ASCII characters, else `400`). The same key from the same user on the same method and path within 24 hours (`IDEMPOTENCY_WINDOW`) gets the first response again, byte for byte with its status and content type and `Idempotent-Replayed: true`, and the handler does not run again; the same key with another body answers `422`, and while the first request runs `409`. A request that never finishes (the client went away, the handler panicked) releases its key; after a crash an unfinished claim is taken over once 10 minutes (`IDEMPOTENCY_LEASE`) have passed. A `4xx` answer is kept like any other, so a client that changes its request after one uses a new key (the web app does). Server errors, responses with `Set-Cookie` and responses marked `Cache-Control: no-store` (such as a new webhook secret) are not kept, so their request may run again. The middleware runs after the session and access checks, so refused requests are not kept. The server prunes expired keys hourly.

## Mailbox changes

Flags, labels, moves, deletes and restores on the servers mail was synced from ([WRITE.md, Mailbox changes](../../../docs/WRITE.md#mailbox-changes)). Nothing is written by the request itself: each change becomes a held row in `mail_changes`, which `mail-writeback` in the server sends; flags changes are confirmed by the next sync and the server wins.

| Route | Body | Answer |
| --- | --- | --- |
| `POST /api/messages/{id}/changes` | `MessageChangeRequest { op, account? }` | `MailChangesDto { changes, skipped }` |
| `POST /api/mail/changes` | `BulkChangeRequest { messages (1 to 500), op, account? }` | The same for many messages |
| `POST /api/messages/{id}/restore` | `{ folder }` | `MailChangeDto`: an append of the archived bytes with `\Seen` and the message's received time to that folder of an account in the message's archive (`mail.append`) |
| `POST /api/mail-changes/{id}/retry` | | `MailChangeDto`: the failed change is dismissed and recorded again as a new held change with the same operation and origin, by the current user; it needs `may_write` for its capability now and is audited like a new change. `409` when it is not failed or was dismissed |
| `POST /api/mail-changes/{id}/dismiss` | | The dismissed `MailChangeDto`, hidden from `MessageDetail.failed` (its row and state stay); editors of the archive, owners and admins. `409` when it is not failed or was dismissed |
| `GET /api/accounts/{id}/mail-changes?state=held,sending&limit=` | | The account's changes, newest first (100 by default, 500 at most); anyone who may read the archive |
| `GET /api/accounts/{id}/retention?days=` | | `RetentionDto { account, days, checked_days, due, more, expunge, active }`: the stored period and how many messages the job would delete now (at most 10 000 counted), or with `days` a dry run for another period that saves nothing |
| `PUT /api/accounts/{id}/retention` | `{ days: 1..36500 \| null }` | The same after storing it in the account's settings as `delete_after_days`; owners and admins, and setting a period also needs `may_write(mail.delete)` (so an admin needs an editor grant). Audited as `capabilities_changed` with the target `delete_after_days:<days\|off>` |

`op` is `{ kind: "flags", add, remove }` (IMAP spellings; `\Deleted`, `\Recent`, empty names and names with spaces answer `400`), `{ kind: "labels", add, remove }` (Gmail; only places in an all-mail folder; `Inbox`, `Sent`, `Drafts`, `Trash`, `Spam` in any case and names starting with `\` answer `400`, because changing them moves or trashes the message, which needs `mail.move` or `mail.delete`), `{ kind: "move", folder }` (a folder id; places in other accounts are skipped) or `{ kind: "delete", expunge? }`. A change applies to every live place of the message with a UID (or only those in `account`): one held change per place. A delete moves to the account's trash folder (a place already there is skipped), marks deleted when the account has no trash, and with `expunge` removes for good. Places that need nothing are listed in `skipped` with a reason: `not_on_server`, `no_server` (an import account), `already` (the stored flags, with the place's open flags changes applied, already show it, so undoing a held change is recorded), `in_target`, `in_trash`, `no_labels` or `other_account`.

Every account a request touches must pass `may_write` before anything is recorded: `mail.flags` for flags and labels, `mail.move` for a move (or `mail.delete` for a move to the trash without `mail.move`), `mail.delete` for a delete, `mail.expunge` for an expunge, `mail.append` for a restore; an editor grant and `write:mail`. A message in an archive the user may not read answers `404`. Each request writes one audit entry per account and kind (`mail_flags`, `mail_move`, `mail_delete`, `mail_append`) with the message ids, before the rows. The capability mapping is `holtmail_mail_writeback::capability_for`, the same the server's writers use.

`MailChangeDto { id, account_id, folder_id, message_id, uid, kind, add, remove, target_folder_id, expunge, origin, device_id, state, attempts, last_error, outbox_id, sent_at, result_uid, created_at, updated_at }`. **The held mark:** `MessageDetail.pending` lists the message's `held` and `sending` changes, oldest first; its locations still show what the server last showed. `MessageDetail.failed` lists its failed changes nobody dismissed, oldest first, for Retry and Dismiss. `OutboxDto.sent_copy` is the append of a sent copy for an identity with `append:<folder>`.

## Contacts and calendars edits

Creating, changing and deleting contacts and events ([WRITE.md, Contacts and calendars](../../../docs/WRITE.md#contacts-and-calendars), [CLIENTS.md, Edits from native apps](../../../docs/CLIENTS.md#edits-from-native-apps)). Nothing is written by the request itself: each edit becomes a held row in `item_changes` with origin `api` (`ItemChangeStore::record_change`), served at once on top of the latest upstream version; `pim-writeback` in the server sends it when the collection is `write_through`. Bytes are validated, classified and turned into a patch by `holtmail-pim-edit`; what is served comes from `holtmail_pim_sync::Edits`.

| Route | Body | Answer |
| --- | --- | --- |

**Locks.** Every edit, resolution and person card edit needs the collection to be editable (it belongs to a server account and is not `read_only`, else `403`) and `may_write(pim.edit)`: the `[write] enabled` switch, the account's `pim.edit`, an editor grant and the `write:pim` scope, also in `held` mode. A collection, item or person in an archive the user may not read answers `404`. Every recorded change and resolution writes one `pim_edit` audit entry (archive, account, the change id; Keep mine on an item gone upstream names the discarded change and its new create), before success is reported; then the item's derived data follows what is served (`Edits::derive`) and the server's `Mailboxes::pim_changed` wakes the writer and refreshes people.

**Collections.** `CollectionDto.write_mode` is the collection's mode, and `CollectionDto.editable` says whether the current user may create, change and delete its items now (an account's collection, not `read_only`, not removed, every lock for `pim.edit` open), so the web app shows edit actions only where a save can succeed.

**Marks.** `ItemSummaryDto.local_edit` (lists and details) and `ItemEditDto.local_edit` are `LocalEditDto { change_id, state, op, class, reason, account_id, account_name, write_mode, created_at }` while an open change is served: `held` reads "not sent to <account>", `sending`, `conflict` "changed in <account> too" (`reason`: `overlap`, `reply_obsolete`, `upstream_deleted`, `upstream_changed`, `upstream_unreadable`), `rejected` "<account> refused". `ItemDetail.data` is the served version's normalized view while a change is open. `ItemDetail.timeline` interleaves versions (`origin` `upstream` or `writeback`, with the change a writeback version came from) and changes, oldest first.

**Creates.** A create whose `UID` a live item of the collection already has answers `422` (`no-uid-conflict`); held creates that have not reached the account yet are not compared.

**Replies.** A change that only changes the user's own answer is recorded as class `reply` with `pim.edit` like any edit; it goes upstream only while the account also has `pim.respond` (the writer holds it with `respond_off` until then), because an auto-scheduling server tells the organizer.

**Invitations an organizer sends.** A create, edit or delete of an event whose `ORGANIZER` is one of the archive's own addresses also schedules ([WRITE.md, Contacts and calendars](../../../docs/WRITE.md#contacts-and-calendars)): `holtmail_pim_edit::organize` turns the change into the copy to record (`SEQUENCE` raised, answers reset when the time moves) and the `REQUEST` and `CANCEL` messages, and `organizer_route` picks who sends them from `Mailboxes::scheduling` (the collection's host and writer; `SchedulingProbe::NoServer` counts as `Host::Mail`) and the write mode: where the server does not schedule they go through the outbox from the user's identity whose address is the organizer (new invitees and kept ones a `REQUEST`, removed ones a `CANCEL`, a delete a series `CANCEL`, one mail per message to its attendees, each held until the change is recorded and released into the undo window with an `outbox_changed` audit entry); where it schedules and the change can be written now, only attendees with `SCHEDULE-AGENT=CLIENT` are mailed; where it schedules but the change waits (`held`, writes off), the same attendees are mailed at once and the server tells the rest once the change reaches it (`Deferred`). When the server cannot be asked (`SchedulingProbe::Unknown`) and anyone would be mailed, the edit is refused with `503`, because mailing could double what that server sends later; `invitations: false` records it without mail. Sending checks the `send:mail` locks and the transport before anything is queued; without an identity for the organizer, or without a sender grant, the edit is refused (`403`) unless it says `invitations: false` (`ItemContentRequest.invitations`, `DELETE /api/items/{id}?invitations=false`), which records the change and mails nobody. An event form with invitees and no organizer gets one: the user's default identity in the archive, else their first active identity of the account, else the account's address. A recorded change whose messages could not be queued is not recorded; messages whose change failed are cancelled. The held messages are linked to the change in the transaction that records it (`NewItemChange.messages`), the request runs on its own task so a client going away cannot stop it halfway, and a failed audit entry or release after the change exists is logged rather than undoing it; `Outbox::recover_held` releases at the next start whatever a stop left held.

**Limits.** A held create has no item until it reaches the account, so in `held` mode it shows only in `/api/pim/changes`, not in lists, the calendar or search (a decision recorded in [WRITE.md](../../../docs/WRITE.md); the web dialog says where it waits).

## Answering invitations

`POST /api/items/{id}/rsvp` (an event item: an account's copy or the event from mail) and `POST /api/messages/{id}/rsvp` (a message carrying an invitation) take `RsvpRequest { answer, comment?, recurrence_id? }` (`accepted`, `tentative` or `declined`; one occurrence by its `RECURRENCE-ID` as iCalendar writes it) and answer `RsvpDto { route, copy, change, outbox }` ([WRITE.md, Contacts and calendars](../../../docs/WRITE.md#contacts-and-calendars), [CLIENTS.md, Invitations and RSVP](../../../docs/CLIENTS.md#invitations-and-rsvp)).

- **What is answered.** The event's copies are found by `UID` (its calendar group): the copy in an account's calendar that is not `read_only` when there is one (the starting item first), and the "From mail" event otherwise. The invitation's bytes are the copy as served, or the newest `REQUEST` or `PUBLISH` of the event from mail; the mail it came in (for threading and routing) is the message asked about, else the one that brought that version.
- **Locks.** `may_write(pim.respond)` on the copy's account, or on the account the invitation mail was synced from when only "From mail" holds it (`403` without one). An iMIP reply also needs the sending locks (`send:mail`, a sender grant, the `send` switch) before anything can reach an alias service, then `may_send` on the routed transport. The user's own event (organizer among the archive's own addresses) and an invitation listing none of them answer `422`, as do an unknown occurrence and a "From mail" invitation whose organizer asked for no answers (`SCHEDULE-AGENT=NONE`).
- **The route** is `holtmail_pim_edit::reply_route` over `Mailboxes::scheduling` (the host and writer of the copy's collection; for "From mail" `Host::Mail`, and when the server cannot be asked an iMIP reply with a held copy that never asks the server to tell the organizer), the writer's capabilities only while the collection is `write_through`, `[write] enabled` is on and the account has `pim.respond`, and the invitation's `SCHEDULE-AGENT`. `server`: the change is recorded with `Respond { notify: true }` and `pim-writeback` calls `CollectionWriter::respond`, so the server tells the organizer (Graph `accept`/`decline` with `sendResponse`, JMAP `participationStatus` with `sendSchedulingMessages`, CalDAV RFC 6638 attendee-copy `PUT`); Holtmail mails nothing. `imip`: an iMIP `REPLY` (`holtmail_pim_edit::reply`, `holtmail_compose::imip`, `In-Reply-To` and `References` to the invitation mail) goes through the outbox with the identity `holtmail-route` picks for a reply to the invitation mail (the address it was sent to, the alias strategy for mail that came through an alias, the account it came from), or, without one, for a reply as if the event's attendees had been the mail's recipients. The attendee is `holtmail_route::attendee_address`: the alias for an invitation received through one. When that address is not on the invitation, the answer goes as the first invited address the user has an identity for, from that identity; an alias linked to an identity whose address differs is refused (`409`), so an alias `ATTENDEE` never leaves with the real mailbox in `From`, and an address only someone else answers for is `422`. The reply waits for the undo window (cancelling the outbox message takes the answer back before it leaves), and its `reply` change does not go upstream until five seconds after that window (`next_attempt_at`), so _Undo_ can still discard it. `quiet`: only the copy follows.
- **The copy.** On an account's copy the answer is a held `reply` change (`holtmail_pim_edit::answered`, audited as `pim_respond`) served at once, on the line of the account's own address when it is invited, else of the user's first invited address; while an edit of the copy has not reached the account the answer is refused (`409`, preview reason `open_edit`), because answering upstream would drop that edit; `copy` says how it follows: `respond` (through `respond`, without telling the organizer again after an iMIP reply), `put` (a CalDAV server that does not schedule), or `held` (it waits until the collection writes through, then goes with `notify: false`, so a scheduling server never answers twice). With only "From mail" nothing is recorded (`copy: none`, one `pim_respond` audit entry): the archived iMIP reply is a version of the event from mail once it leaves, and `InvitationDto.my_status` (matched against the archive's own addresses: accounts, identities and own aliases) shows it.
- **One scheduler.** The iMIP reply and the organizer's `REQUEST` and `CANCEL` messages go through `Sending.scheduler` (`holtmail_schedule::Scheduler::deliver` with `Origin::Web`, the routed identity as `ReplyAs` for an answer, with relay routing's reverse alias or `Reply-To` as `ReplyAs::to`, so an answer to an invitation that came through an alias service goes back through the service; `References` from `compose::answer_references`, at most 20 usable ids), the same scheduler CalDAV devices and SMTP submission use, so a message delivered within the last 10 minutes is not queued again and a client's own copy of it is dropped by submission. Messages are held in the outbox until the change is recorded: they are linked to it in the transaction that records it, then `Scheduler::confirm` lets them into the undo window and they are audited (`outbox_changed`, `queued`); when recording fails `withdraw` takes them back. So neither the message nor the change happens without the other, also with `[write] undo_seconds = 0`, and `Outbox::recover_held` releases at the next start the messages of a change recorded just before a stop. An answer that does not change the user's `PARTSTAT` sends nothing. A recipient the scheduler could not queue for (`3.7`: no identity may send it, `403`; `5.1`: the outbox refused it, `429`) takes back what was queued and refuses the request; an outbox that cannot be reached is `503`. The organizer's copy is recorded as the scheduler returns it, with `SEQUENCE` raised and `SCHEDULE-STATUS` written.
- **Members** reach both routes (the access check lets them through to the handler), which answer `404` for an archive they may not read.

**Answers that failed the sender check.** `InvitationDto.schedule_note` is what scheduling made of the message's iTIP part for the event (`ScheduleStore::inbox_entries_of`): `applied`, `unauthenticated` (an attendee's `REPLY` without DKIM or DMARC pass for its sender), `not_from_attendee`, `no_copy`, `unchanged`, `update`, `upstream_holds` or `own_organizer`. `POST /api/messages/{id}/itip/apply` ("Apply anyway") is `403` while `[write] enabled` is off (the hook refuses too, so nothing is recorded with writing closed), needs an editor grant (or owner and admin), `422` unless the message has an `unauthenticated` part, then calls `Mailboxes::apply_itip`, audits `pim_respond` with `apply_anyway` and answers `ItipApplyDto { notes }`.

**Before answering.** `GET /api/items/{id}/rsvp` and `GET /api/messages/{id}/rsvp` answer `RsvpOptionsDto { allowed, reason, route, copy, item_id, collection_name, account_name, from, attendee, provider, my_status, recurring, occurrences, local_edit }`: what the `POST` would do now, read with the same choosers and locks. They record nothing, send nothing and ask no alias service (`from` is absent when a reverse alias would have to be made first). `reason` is `organizer`, `not_invited`, `locked`, `no_answers` or `cannot_send`. `occurrences` are a repeating event's instances from a month ago to a year ahead (at most 60, no cancelled ones), each with the `recurrence_id` to send back written the way the series writes it, and the `key` the calendar names it by (`CalendarOccurrence.recurrence_id`).

**Who sends invitations.** `GET /api/collections/{id}/organizing?item=` answers `OrganizingDto { route, from, account_name, allowed }`: `server`, `deferred`, `imip`, `unknown` (the server cannot be asked; `allowed` is false and saving with invitations is `503`) or `none` (someone else's event). For `imip`, `from` is the event's organizer (a new event's: the identity it would be organized as), and `allowed` is false when no identity of the user sends as it or the user may not send mail. Records and sends nothing.

**Taking an answer back.** `POST /api/pim/changes/{id}/resolve` with `discard` on a `reply` change needs `pim.respond` rather than `pim.edit`, so whoever may answer may take the answer back; every other resolution keeps the `pim.edit` locks.

## Sending

Drafts, identities, transports and the outbox ([WRITE.md, Sending](../../../docs/WRITE.md#sending)). `ApiState.sending` is `Option<Sending { outbox, transports, secrets, submission }>`: the `holtmail-outbox` queue, the `Submission` that `POST /api/drafts/{id}/send` hands its composed message to with the route it chose (every lock is checked there again, and the row is held until its audit entry is stored), the server's `Transports` (which builds a transport's submitter and refuses what the instance or the account does not allow) and the `SecretBox` that seals transport passwords with context `transport:<id>`. With `None` every route that needs it answers `503`.

**Who may do what.** Transports, identities, who may send as an identity, and identity suggestions are managed by owners and admins (`403` for members). Anyone who may read the archive lists its transports (never a password, only `has_password`) and the identities they may send as (managers see all). Drafts, replies, forwards, uploads and the default identity need a `sender` grant and the `send:mail` scope (`403`). Sending, retrying and resending also need what `may_send(state, user, scopes, archive, transport)` checks: the `enabled` and `send` switches, `mail.send` on the transport's account for an `account` transport (an `smtp` transport needs no account capability), the `sender` grant and the scope; it fails closed like `may_write`. A user sees and changes only their own drafts (`404` for others') and their own outbox messages (the list is narrowed in the store, before its limit); managers see every outbox message of the archive and may cancel them, but only the sender undoes, and retrying or resending as an identity needs the right to send as it.

The route explanation is the router's own: `route { identity, from, name, transport, strategy, reasons: [{ code, address, alias, account }], to?, alias?, strategy_source?, provider?, contact? }` (`provider` is the alias service's id when the original came through an alias; `contact` is the real sender, lowercase, whom `to` reaches when a reply replaces the sender) or `route_error { code, id?, transport?, address?, alias?, contact? }`, recomputed whenever a draft is shown.

Drafts never leave Holtmail and are not audited; every change to a transport (`transport_changed`), an identity or its users (`identity_changed`) and every queue, undo, cancel, retry and resend (`outbox_changed`) is, with ids only, recorded before the change: `send` queues the message held, records it, and only then releases it, and cancels it again if the entry cannot be stored. The outbox adds `mail_send` before every attempt hands a message to a transport. An `Idempotency-Key` on `send` is also handed to the outbox, so a retried send never queues twice.

**Replies through alias services.** For a reply or forward of a message with an alias hit, the route is `holtmail_route::route_relay` with a `Relay` built from the hit (`signed` from the provider's DKIM check), the effective strategy (`holtmail_aliases::effective_strategy` over the archive's overrides and `Aliases::default_strategy`; `strategy_source` names where it came from), the alias's forwarding mailboxes from the alias store and the original's first `Reply-To`. Showing a draft never asks an alias service: a route that needs a reverse alias uses the one made when the draft was started (`payload.context.reverse_alias`), else answers `route_error.code = needs_reverse_alias`, which sending resolves. Starting a reply makes the reverse alias when needed (a refusal leaves the draft with that route error) and puts it in place of the sender in `To` (an empty `To` gets it). The sender is the original's `From`, the hit's sender and reverse alias, and its `Reply-To` only when the service signed the mail or it is the hit's reverse alias; any other `Reply-To` (a list, a third party) stays a recipient of its own and the leak guard checks it. Every reverse alias made through `Aliases::reverse_alias` is recorded in the alias store as the pair of contact and address. Sending ignores the stored `reverse_alias` and asks again, and counts a `reverse_contacts` pair as a reverse alias only when the pair's address is still a recipient and the service gives the same address again. The draft view trusts the stored pairs (only the reverse-alias fix sets them) and runs the same `To` rewrite as sending, but it never asks a service, so the leaks of a send's `409` are the authoritative ones: clients show those. The leak guard (`holtmail_route::leaks`) runs with the thread's aliases (the original's own alias hit always, plus every message of the thread with an alias hit among the newest 200), its signed reverse aliases, a signed original's `Reply-To` and the confirmed pairs; `leaks: [{ recipient, field, reason, fix }]` is on every draft and in the `409`. `route.alias` is the original's alias, else the first alias of its thread, so a client can offer `use_alias_identity` with the identity that sends as it; `use_reverse_alias` is offered when a reverse alias can be made for that alias (also when only the thread came through it).

## Rules

Flows, their runs and the executor ([WRITE.md, Rules](../../../docs/WRITE.md#rules)). Every rule route needs what `Access::may_use_rules` checks: the `enabled` and `rules` switches, an `editor` grant on the archive and the `rules` scope (`403`; `404` for an archive the user may not read). A flow that sends (any action with `mail.send`) also needs a `sender` grant to be saved (`403`), and someone other than its saver needs one to turn it on or run it by hand, since it then sends as the saver (`403`). Saving validates with `holtmail_rules::validate`, parses every `query` node with the search parser and asks `RuleHooks::webhook_allowed` about every `webhook` node (only a webhook subscribed to `flow.run` may be named); problems answer `422 FlowIssuesDto { error, issues: [{ node, code, detail }] }`. Every create, save, change, delete, manual run, confirmation and dismissal is a `rule_changed` audit entry with ids only.

**The executor** (`Rules`, `rules_run.rs`) is built by the server over the same `ApiState`. `Rules::observe(archive, message, parsed, live)` keeps an event (`RuleStore::put_rule_event`) for live mail only, and only in an archive with a flow of that trigger: `message.archived:<message>` and, for mail with an iTIP `REQUEST`, `invitation.received:<message>`. `Rules::tick(from, to)` keeps `schedule:<flow>:<minute>` for every cron minute of `(from, to]` and `upcoming:<flow>:<group>:<start>` for every instance starting `minutes_before` later (copies of one event counted once). `Rules::run` interrupts runs left `running`, then loops: tick (resuming from the setting `rules.ticked_through`, at most an hour back), handle waiting events oldest first, prune runs older than 30 days and actions older than 400 days once a day, and wait 30 seconds or for `observe`. An event stays when the store fails before every flow had its run, and runs already claimed are not repeated: delivery is at most once per flow and event, and a run cut short by a stop shows as `interrupted` with the actions it did not reach left undone.

For each event, flows of the archive run in order, skipping `off` and paused ones and those of another trigger (`schedule`, `event.upcoming` and `manual` events name their flow). A run is claimed by flow version and event id before anything happens, and a flow that had a run for the event under any version gets none again, so a retried event or a save in between repeats nothing. When a retried event meets a flow's earlier run, that run's `stop` still ends the chain, and so does a live run that never recorded its plan (it may have stopped). A test run never ends the chain. Facts are loaded from the store and the raw bytes: the search `Matcher`'s `MessageFacts` (body, the attachment text ingest extracted, empty without attachments, insights and categories; a fact not derived yet makes a query `Unknown`, taken as no match and logged with the message id; ingest tells the executor about a message only after its categories and index document, so live mail has them), sender, subject, headers, alias hit, trust, insight kinds, whether the sender is a person, the invitation, the upcoming event, the counters the flow reads (`sender`: archived messages from that address; `flow`: runs of the flow that carried out an action) and the flow's last reply to the sender. Templates see the insight values of the first shown order, invoice, parcel, reservation and pass as `insights.<kind>_<field>` (never codes or links), and an upcoming event's summary, start, location and organizer. A flow in test mode, or a dry run, stops after `evaluate`: every action is logged as `test`, nothing counts as acted and its `stop` does not end the chain.

Otherwise the run acts as the user who saved the current version, while they still pass `may_use_rules` and, for a flow that sends, hold a `sender` grant (`failed` with the reason otherwise), with the full web scopes; every action goes through the path a person uses, so every lock is checked again: `label` sets a local label, `set_flags`, `move` (a folder of an account holding the message, by path, then path ignoring case, then role) and `delete` record mail changes, `reply`, `forward` and `send` write a draft (`template_draft`, the identity `auto` letting the route pick, so mail through an alias is answered through it; a reply goes to the one sender the RFC 3834 checks ran on, never `Reply-To`) and send it through `send_stored_draft` and the `Submission` with `Auto-Submitted` and the idempotency key `rule:<flow>:<run>:<node>`, `rsvp` answers through the RSVP path, `create_event` and `create_contact` record a create in the given or first editable collection (events without invitations), `notify` and `webhook` go to `RuleHooks` (`call` refuses a webhook not subscribed to `flow.run`). A send whose recipients would see the real mailbox behind an alias is not sent: its draft waits. An action with `confirm` is held: a sending action leaves its draft in the outbox (`draft`), any other is `pending` in the run until someone confirms or dismisses it. Each result is `{ node, type, result, detail?, outbox?, draft? }`; details never hold message content.

**Limits** (`RuleLimits`, defaults): a flow carries out at most 60 actions an hour and flows send at most 30 messages an hour as one identity, counted for the identity the route picked, so `auto` counts too (`skipped` with `rate_limited`); only actions carried out (`done`, a queued message) count, not skipped ones or drafts the leak guard kept; a flow with more than 100 runs that carried out an action in an hour is paused by the circuit breaker (`paused: circuit_breaker`), which tells `RuleHooks::flow_paused` once (the server's `flow.paused` webhook) and writes a `rule_changed` audit entry; a person turns it on again. RFC 3834 (`Auto-Submitted`, lists, bulk, null return path, no-reply senders, own addresses, once per sender per `days`) is planned by `holtmail-rules` from these facts and `FlowAction` records.

**`message.sending`** runs inside `POST /api/drafts/{id}/send` (not for SMTP submission or JMAP clients), with only the sending user's own flows, and only while that user passes `may_use_rules` and, for flows that change the route, holds a `sender` grant: the draft's identity, recipients, subject and text are the facts; runs are logged per draft version, and a flow in test mode changes nothing and never ends the chain. A rule that adds a blind copy or sets the identity or transport writes a `mail_send` audit entry (`<draft>`, `rule`, `<flow>:<action>`). `set_transport` takes another identity of the same address that uses the transport (`400` when there is none). A broken flow is logged as failed and left out.

## Safety

- `/body` runs [`holtmail-sanitize`](../../sanitize/docs/README.md). Inline `cid:` images point at absolute attachment URLs built from the request's `Host` and `X-Forwarded-Proto`.
- The web app shows `/body` in an iframe with `sandbox="allow-same-origin allow-popups allow-popups-to-escape-sandbox"` and no `allow-scripts`; the document's own CSP forbids scripts as well.
- Attachments are served inline only for images and PDF; everything else, including HTML and SVG, is `application/octet-stream` with `Content-Disposition: attachment`. Every download, thumbnails included, has `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`, and goes through the same access check as its message. Thumbnails are re-encoded by the server, never the sender's bytes.
- File names in `Content-Disposition` are cleaned and sent both as ASCII and as RFC 5987 UTF-8.

## Remote images

`?remote=` on `/body` decides what happens to images and backgrounds hosted elsewhere:

- `block` (default): left out; `x-holtmail-remote-blocked: 1` tells the reader to offer them.
- `proxy`: pointed at `/api/messages/{id}/remote/{key}`, so the server fetches them and the reader's address stays private. Remote styles and fonts are still left out.
- `direct`: original addresses kept and allowed by the document's CSP; the reader's browser contacts the sender's servers.

Images the archive saved (see `save_remote_images`) are pointed at `/remote/{key}` whatever the mode, because showing them reaches no one, and `x-holtmail-remote-saved: 1` says so. `?saved=false` ignores saved copies and shows the originals as `remote` says, through `/api/messages/{id}/live/{key}` for `proxy`, which always fetches now. The stored message is never changed: copies live beside it.

`/remote/{key}` serves only URLs that the message itself links, so it is not an open proxy. It answers with the saved copy when there is one (cached for a year) and otherwise fetches through the [`Fetcher`](../../fetch/docs/README.md), which never contacts private or local addresses (cached for a day). Responses carry `nosniff` and `Content-Security-Policy: default-src 'none'; sandbox`; types other than common raster images are sent as `application/octet-stream`.

`ApiState.fetcher` is the `Fetcher`.

### Saving and tasks

`ArchiveDto.remote_images` has `since` (when saving was turned on), `images`, `bytes`, `failed` and `older_pending`: messages archived before `since` and not looked at. Turning saving on starts nothing: new mail is handled after each sync or import, older mail only through `POST /api/archives/{id}/remote-images` with `{ "job": "older" }`, and `{ "job": "failed" }` fetches failed images again. Both answer `202` with the task, or the archive's running remote image task when there is one.

`GET /api/tasks` lists running tasks and recent finished ones (`kind` `sync`, `import`, `remote_images`, `contacts_calendars`, `ledger_verify`, `delete_messages` or `analyse`) with `done`, `total` (`null` when unknown), a `summary` and a `log` of `{ at, level, text }` lines that carry counts, folder names and reasons, never message content. `POST /api/tasks/{id}/cancel` stops a cancellable task after its current step (`409` otherwise). Finished tasks stay listed after a restart (the server keeps the last 200); a task's `state` is `running`, `done`, `failed`, `cancelled`, or `interrupted` when the server stopped while it ran. Task ids are unique across restarts. `TaskKind`, `TaskState`, `TaskLevel` and `TaskLine` are the store's types, re-exported.

`GET` / `PUT /api/image-proxy` read and set the outbound proxy for remote images: `{ "proxy": "socks5h://127.0.0.1:9050" }` or `null`. The answer shows `address` without credentials and `from_config` when the server's config sets it (then `PUT` answers `400`). Setting checks that the proxy accepts connections.

`POST /api/archives/{id}/deletions` with `{ "query": "..." }` or `{ "message_ids": [...] }` (exactly one) freezes the list of messages a deletion would remove and answers `200 { id, archive_id, query, count, bytes, oldest, newest, sample, expires_at }` without deleting anything; `sample` holds up to 20 `{ id, subject, from, date, size }`, newest first. `400` for neither or both, a bad id, an empty or unreadable query, nothing found, or more than 100 000 messages. `409` with `{ "error": "Some messages are still being read. Try again when search has caught up." }` when the query uses insight operators (`category:`, `has:code` and the other insight kinds, `is:newsletter|notification|personal|list`) while the archive has pending insights or reindex entries (`MailboxError::Conflict`). `POST /api/deletions/{id}/confirm` with `{ "count": <the review's count> }` starts a `delete_messages` task (`202`); the review is used up, valid for 30 minutes and only for the user who asked for it, and another count is `400`. Members get `403` on both. The server provides them through `Operations::{review_deletion, confirm_deletion}`.

`GET /api/smtp` (owners and admins) answers `{ enabled, listen, hostname, allow, starttls, require_tls, auth, max_size_mb, routes: [{ recipient, archive_id, folder, journal }], received, deleted, refused_recipients, failed, last_received_at }` from `Operations::smtp`; `enabled: false` with empty fields when the config has no `[smtp]`.

Webhooks (owners and admins; members `403`): `GET /api/webhooks` answers `{ events, webhooks }` with every subscribable event name and each webhook `{ id, url, events, enabled, created_at, last_delivery }`; `POST /api/webhooks` with `{ url, events }` answers `201 { webhook, secret }`, the only time the signing secret is shown; `PATCH /api/webhooks/{id}` changes `url`, `events` and `enabled`; `DELETE` removes it with its deliveries (`204`); `POST /api/webhooks/{id}/secret` answers a new `{ secret }`; `POST /api/webhooks/{id}/test` queues a `webhook.test` delivery (`202`); `GET /api/webhooks/{id}/deliveries` lists the newest 50 `{ id, event, event_id, created_at, attempts, next_at, last_status, last_error, delivered_at }`. A bad address or unknown event is `400`, an unknown webhook `404`. Secrets come from `Operations::{create_webhook, rotate_webhook_secret}` and test deliveries from `Operations::test_webhook`; the rest reads and writes the store.

`GET /api/ledger` answers `{ head, last_verification }`: the newest ledger entry `{ seq, event, at, archive_id, message_id, blob_id, hash }` (or `null`) and the last finished verification `{ started_at, finished_at, ok, entries, head_seq, head_hash, anchor_seq, blobs_checked, problems, problem_count }` (or `null`). `POST /api/ledger/verify` with `{ "blobs"?: bool, "anchor"?: "<seq>:<hash>" }` starts a `ledger_verify` task (`202` with the task; the running one when there is one) and `400` for a malformed anchor. The server provides both through `Operations::{ledger, verify_ledger}`.

Members get `403` on `/api/tasks`, `/api/image-proxy`, `/api/sync-schedule` and `/api/ledger`. The server provides all of this through `Mailboxes`: `tasks`, `cancel_task`, `start_remote_images`, `image_proxy`, `set_image_proxy`, `rebuild_people` (returns once a rebuild of the archive's people that started after the call has finished; rebuilds of one archive never overlap, so a split, join or undo is never lost to a background rebuild running at the same time), and for accounts `configure` (connection, password, interval, minimum age; a password for an OAuth account is `400`, a new connection of one is checked with a fresh access token), `details`, `sync_schedule` and `set_sync_schedule`.
