# holtmail (apps/server)

The `holtmail` binary and the only place that chooses implementations: it reads the config, opens the blob store, the metadata store and the search index, and hands them to the API and the commands as contracts.

## Commands

```bash
holtmail serve                                   # API and web app
holtmail import --archive Personal ~/mail.mbox   # mbox, Maildir, .eml, .vcf, .ics, zip (Google Takeout too) or a directory of them
holtmail archives                                # archives with totals
holtmail account add-imap --archive Personal --host imap.example.com --username ada@example.com
holtmail account add-oauth --archive Personal --email ada@gmail.com [--provider google|microsoft]
holtmail account add-graph --archive Work --email ada@contoso.example.com
holtmail account add-jmap --archive Personal --url https://api.fastmail.com/jmap/session --token-stdin
holtmail account add-jmap --archive Personal --url jmap.example.com --username ada@example.com
holtmail account list                            # accounts of every archive
holtmail account edit <id> [--name --host --port --security --username --url --auth --exclude ... | --clear-exclude] \
  [--interval <minutes>|0|default] [--min-age-days <days>|0] [--pause | --resume] [--password-stdin] \
  [--contacts-calendars on|off [--dav-url <url> | --carddav-url <url> --caldav-url <url>] [--dav-password-stdin]] \
  [--pim-interval <minutes>|0|default] [--watch off|inbox|<folder>,<folder>...]
holtmail sync [--account <id>]                   # archive new mail now, then contacts and calendars where on
holtmail user add --email ada@example.com --name "Ada Lovelace" [--role owner|admin|member]
holtmail user password --email ada@example.com   # set a password, end the user's sessions
holtmail user list                               # users with their roles
holtmail reindex [--refresh-attachments]         # rebuild the search index, missing or outdated message insights, the listed fields, calendar instances and search documents of contacts and events, events from invitations in mail, and people
holtmail export --archive Personal [--folder INBOX | --label Travel | --query "from:ada"] \
  [--format mbox|zip|pdf] --output personal.mbox # write messages as mbox, a zip of .eml files or a zip of PDFs
holtmail export --archive Personal --contacts [--collection Work | --person <id>] \
  [--include-removed] [--format vcf|zip] --output contacts.vcf   # contacts: latest versions, or every version
holtmail export --archive Personal --calendar [--collection Team] [--from 2025-03-01 --to 2025-04-01] \
  [--include-removed] [--format ics|zip] --output team.ics       # calendar items the same way
holtmail backup --output holtmail.tar [--skip-blobs] [--include-secret-key]
holtmail restore --input holtmail.tar --data-dir /srv/holtmail-new [--skip-reindex]
holtmail delete --archive Personal --query "from:news@example.com before:2020-01-01" [--yes]   # delete for good after a review
holtmail ledger head                             # the ledger's newest position and hash, to write down elsewhere
holtmail ledger verify [--blobs] [--anchor <seq>:<hash>]   # check the ledger; exit code 1 when anything is wrong
holtmail insights explain <message-id>          # which insight rules matched in a message: names, positions, scores, value shapes; never values
holtmail send --archive Personal --from ada@example.com --to bob@example.org [--cc ... --bcc ...] \
  --subject "Plans" --body "Noon?" | --body - | --eml message.eml [--at 2026-11-08T09:00:00Z] [--wait]   # queue a message as an identity
holtmail outbox list [--archive Personal] [--state queued,failed]   # outgoing messages with each recipient's result
holtmail outbox retry <id> | holtmail outbox cancel <id>
holtmail openapi                                 # the API description as JSON
```

While `serve` runs, `user`, `account list`, `account edit`, `export` (except `--query`), `ledger`, `send`, `outbox`, `backup` and `restore` (into another directory) work next to it, also through `docker exec`. `archives`, `import`, `sync`, `reindex` and the `account add-*` commands open the search index, which `serve` holds; they stop with "the search index is in use by another process" then. Use the web app for those, or stop `serve` first.

`import` reads mail and, from the same path, address books and calendars: a `.vcf` or `.ics` file, every `.vcf` and `.ics` in a directory, or those inside a zip, such as Google Takeout's `Takeout/Contacts/<group>/<group>.vcf` and `Takeout/Calendar/<calendar>.ics`. Each file becomes a collection of the import account (named after the path, as for mail; `--account` overrides), known by the file's path in what was imported (for an upload, the uploaded name) and named after the calendar's `X-WR-CALNAME`, else the file name. Each contact, event or task becomes an item known by its `UID` (a card without one by its lowercased name, anything else by the hash of its bytes; a repeated id gets `#2`, `#3`, …), split and read by [`holtmail-pim`](../../../crates/pim/docs/README.md) and stored by [`holtmail-ingest`](../../../crates/ingest/docs/README.md): bytes unchanged, a new version only when they differ, pictures of contacts as blobs of their own. Importing the same file again adds nothing; a changed file adds versions for the items that changed, and items of the collection that the file no longer holds are marked removed (never deleted) unless the file holds no items at all. The summary line counts new, changed, unchanged, gone and unreadable contacts and events next to the messages. Files are read whole, at most 256 MiB each.

`export` writes the original bytes of the messages of an archive (by name or id), one folder (by path, `account name/path` when several accounts have it, or id), one label, or a search, newest first, with [`holtmail-export`](../../../crates/export/docs/README.md). `--format` defaults to `zip` for an output ending in `.zip` and `mbox` otherwise; `--output -` writes to standard output. It writes `<output>.part` and renames it when done, and never overwrites a file. It needs only the database and the blobs, so it works while `serve` runs, except `--query`, which needs the search index that `serve` holds: export searches from the web app then. Messages whose bytes are missing or damaged are left out and counted. The web app and `GET /api/archives/{id}/export` stream the same files.

`export --contacts` and `export --calendar` write an archive's contacts or calendar items instead (see [Contacts and calendars](../../../crates/export/docs/README.md#contacts-and-calendars)): the latest version of each as one `.vcf` or `.ics`, or every version as stored in a zip with `manifest.json`. `--format` defaults to `zip` for an output ending in `.zip`, else `vcf` or `ics`. `--collection` takes an address book's or calendar's name or id; `--person` a person's id (contacts only); `--from` and `--to` days in UTC, both or neither (calendars only), keep events with an instance in that span; `--include-removed` puts items removed from their source into the `.vcf` or `.ics` too. Graph and JMAP items are written as vCard or iCalendar text in the `.vcf` and `.ics`, and as their stored JSON in the zip. Works while `serve` runs; the API streams the same files.

`delete` removes the messages a search finds from one archive for good, after printing how many, their size, their date range and ten of them, and asking to type that number (`--yes` skips the question). It does what the web app's deletion does: the messages, their attachments, saved remote images and calendar versions read only from them go, blobs nothing else uses are deleted, the index entries are removed, each message is entered in the ledger as `deleted`, and the people are rebuilt. Tombstones of the bytes and of the folders and UIDs they had keep syncs and imports from archiving them again; syncs and imports count them as "deleted earlier left out". It needs the search index, so stop `serve` first or use the web app. An empty search is refused; to drop a whole archive, remove the archive. At most 100 000 messages at once.

`ledger` looks at the archive ledger ([`holtmail-ledger`](../../../crates/ledger/docs/README.md)): every message archived, every message deleted and every archive deleted is an entry sealed with BLAKE3 over its fields and the entry before. `serve` enters messages archived before the ledger existed at every start (oldest first; the log says how many). `ledger head` prints `<seq>:<hash>`; kept somewhere the instance cannot change (a printout, another machine, a webhook receiver), it proves later that nothing up to it was changed. `ledger verify` enters missing messages first, then checks every link and hash in the chain, compares the entries with the live messages (missing entries, messages pointing at other bytes, messages gone without a deletion entry) and with `--anchor` that the entry at that position still has that hash; `--blobs` also reads every message's bytes and compares their BLAKE3 hash with their id. It prints each problem (ids and positions only), the head, and exits 1 when anything is wrong; the result is kept and shown in the web app. Admins start the same check from the web app or `POST /api/ledger/verify`, which runs it as a `ledger_verify` task.

`account add-imap` reads the password from `HOLTMAIL_IMAP_PASSWORD` or the first line of stdin, seals it with the instance key (`<data_dir>/secret.key`, bound to the new account's id) and stores only the sealed bytes. `--security tls|starttls|plain`, `--port`, `--name` and repeated `--exclude <folder path>` are optional. `sync` prints one line per folder: new, known, removed, failed and any error.

`account edit` changes one account (its id from `account list`) through the same path as the web app: a new server, port, security, user name, excluded folders (`--exclude` replaces the list, `--clear-exclude` empties it) or password (`--password-stdin`, the first line of standard input) is checked by signing in to the mail server first, and nothing is stored when that fails; an OAuth account gets a fresh access token for the check. A new `--security` without `--port` uses that security's default port. A stored password or token is never sent to another server: another host or port (by the effective port, so a new security that changes the default port counts), a move from TLS or STARTTLS to `plain`, or a JMAP `--url` on another origin (scheme, host or port) needs the secret again through `--password-stdin`, and is refused with "changing the server needs the password or token again" otherwise (the web app and API answer `400` "Enter the password again when changing the server."). A change of security on the same host and port that keeps encryption keeps the stored password, as does a JMAP address on the same origin. An OAuth (Gmail or Microsoft) IMAP account keeps the server, port and security its provider set; any change to them is refused, since the account's access token would go to that server. `--interval` sets the account's own minutes between syncs, `0` only on request, `default` follows the server's; `--min-age-days` archives only mail at least that many days old (at most 3650; `0` archives all mail); `--pause` and `--resume` stop and restart syncing. It opens only the database (and `secret.key` and the OAuth clients for a change that signs in), so it works while `serve` runs: `serve` picks the change up at its next 30-second check. A sync running in `serve` at that moment finishes with the settings it started with.

`account add-jmap` adds a JMAP account (Fastmail, Stalwart, Cyrus and others; see [holtmail-source-jmap](../../../crates/source-jmap/docs/README.md)). `--url` is the session address or just the server's address, where `/.well-known/jmap` is asked; https only. With `--token-stdin` it signs in with an API token (bearer) read from the first line of stdin and needs no `--username`; otherwise it signs in with HTTP Basic as `--username` and reads the password from `HOLTMAIL_JMAP_PASSWORD` or stdin. It signs in and lists the mailboxes before storing anything, and seals the password or token like IMAP passwords. Repeated `--exclude <mailbox path>` and `--name` are optional. For a JMAP account `account edit` takes `--url`, `--auth password|token`, `--username` and the excluded mailboxes instead of a host, port and security; changing `--auth` needs the new secret through `--password-stdin`, which also takes a new token for a token account. Accounts are stored with kind `jmap` and settings `{ "url", "username", "auth" }`; the scheduler, Sync now, tasks, minimum age and folder rules work as for IMAP.

`account add-oauth` prints the provider's sign-in page, then reads the address the browser lands on from stdin (see [OAuth](#gmail-and-microsoft-sign-in-oauth)); the provider is guessed from well-known domains unless `--provider` is given. With an own client whose redirect is Holtmail's callback, sign in from the web app instead.

`account add-graph` adds a Microsoft 365, Outlook.com or Hotmail mailbox read through Microsoft Graph ([holtmail-source-graph](../../../crates/source-graph/docs/README.md)) instead of IMAP, for tenants where IMAP is turned off. It runs the same sign-in as `add-oauth` with Microsoft and the Graph scopes, lists the mailbox's folders with the new token and reads the signed-in address from `/me` before storing anything; the account is stored with kind `graph`, the signed-in address and settings `{ "oauth": { "provider": "microsoft" } }`. Signing in again keeps the kind and refuses a different mailbox ("You signed in as …, but this account archives …"). The scheduler, Sync now, tasks, needs-sign-in, minimum age and `folders.exclude` work as for IMAP; `account edit` changes its name, interval, minimum age and pause, and refuses server settings and passwords.

## Sending mail

`serve` runs the outbox ([holtmail-outbox](../../../crates/outbox/docs/README.md)): at start every message left `sending` by a stopped process becomes `uncertain`, then a worker hands due messages to their transports, one in flight per transport. Messages wait `[write] undo_seconds` (10 by default) before they leave. The first attempt archives the exact bytes through ingest; once the transport takes them, the message gets a location in the account's Sent folder with `$HoltmailSent`.

`src/send.rs` builds each transport's submitter with [holtmail-submit-smtp](../../../crates/submit-smtp/docs/README.md), [holtmail-submit-jmap](../../../crates/submit-jmap/docs/README.md) or [holtmail-submit-graph](../../../crates/submit-graph/docs/README.md), trusting `tls_ca_file` too. Whenever `[write] enabled` or `send` is off, or the account's `mail.send` is off, it answers with a retryable error, so queued messages wait (up to the outbox's 24 hours) instead of failing, and a check says why. Before every attempt it also tells the outbox whether the user who queued the message may still send from the archive (the owner always; anyone else with a `sender` grant), and a message whose sender lost that right fails. The account's own password or token is only ever sent to the account's server:

| Transport                               | Server and sign-in                                                                                                                                                                                                                                                      |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `smtp`                                  | The transport's `host`, `port` and `security` (`tls`, `starttls`, `none` only towards localhost), and its user name with the password sealed as `transport:<id>`, or no sign-in                                                                                         |
| `account`, IMAP account with a password | Only with `mail.send` on for the account. The account's IMAP host on 587 with `STARTTLS` (its `port` and `security` may be changed), with the account's user name and password; a transport with its own user name and password may also name its own `host`            |
| `account`, Gmail (OAuth)                | `smtp.gmail.com:465` over TLS, `AUTH XOAUTH2` with the account's access token (Google's mail scope covers SMTP); the transport's `host`, `port` and `security` are ignored. A token that cannot be refreshed retries later unless the sign-in was revoked               |
| `jmap`                                  | JMAP submission to the transport's `url` (a session address, or a server where `/.well-known/jmap` is asked), with its user name and password or a bearer token (`auth` `token`), sealed as `transport:<id>`; the provider keeps the sent copy (`onSuccessUpdateEmail`) |
| `graph`                                 | Microsoft Graph `sendMail` at the transport's `url` (Microsoft's when missing) for `mailbox` (the token's own when missing) with a bearer token sealed as `transport:<id>`, which Holtmail does not refresh; Graph keeps the sent copy                                  |
| `account`, Microsoft over IMAP (OAuth)  | `smtp.office365.com:587` with `STARTTLS` and `AUTH XOAUTH2`, once the sign-in includes `SMTP.Send`                                                                                                                                                                      |
| `account`, JMAP account                 | JMAP submission at the account's session address with its own password or token; the transport's server settings are ignored                                                                                                                                            |
| `account`, Microsoft Graph account      | Graph `sendMail` for the signed-in mailbox with the account's access token, refreshed as for syncs, once the sign-in includes `Mail.Send`. Graph is the only way out for these accounts, and the default for Microsoft (many tenants turn SMTP AUTH off)                |
| `account`, import account               | Refused: it has no server                                                                                                                                                                                                                                               |

**Consent to send (Microsoft).** A Microsoft sign-in covers sending only with `SMTP.Send` (IMAP) or `Mail.Send` (Graph). When an account transport of a Microsoft account is used while `settings.oauth.send` is not set, the server records `settings.oauth.missing_consent = "mail.send"`, sends the `account.needs_sign_in` webhook once and answers with a retryable error, so the message waits in the outbox (up to its 24 hours) instead of failing. Syncs go on. The account then shows `needs_sign_in` with a `sign_in_reason`, and **Sign in again** asks for the send scope whenever `mail.send` is on for the account; the new sign-in records `send` and clears the mark, and its refresh token is refreshed with the same scopes. Google's mail scope already covers SMTP.

**What sync learns after sending.** Every ingest the server builds carries an observer (`SentMail`) that hands each message added to an archive to `Outbox::observe` once the outbox runs: the provider's own Sent copy with other bytes is linked to its outbox row (`synced_copy`) and a rewritten `From` flags the identity; a delivery status notification arriving live (a watch, a poll of a folder synced before, an SMTP delivery) marks the row `bounced` per recipient. The command line has no outbox, so imports there match nothing.

**Sent copies upstream.** Identities keep `sent_copy`: `provider` (the default for `account`, `jmap` and `graph` transports) needs nothing, `none` keeps only the archive's copy, and `append:<folder>` makes the outbox record an append of the sent bytes with `\Seen` for the identity's account right after the send, which the mailbox writeback below saves (only with `mail.append`; otherwise the outbox message gets a note).

`holtmail send` queues a message as an identity of the archive (`--from` takes its address or id): built from `--to`, `--cc`, `--bcc`, `--subject` and `--body` (`-` reads standard input) with [holtmail-compose](../../../crates/compose/docs/README.md), or read from `--eml`, whose bare LF line ends become CRLF and whose `From` must be the identity; `--to`, `--cc` and `--bcc` then make the envelope, else its `To` and `Cc`. A message with a `Bcc` header or without a `Message-ID` is refused. The command only queues, into the database `serve` shares, and audits it with no user; the running server sends it. `--wait` waits until it was sent or given up, prints each recipient's result and exits 1 unless it was sent. `holtmail outbox list` prints messages with their recipients; `retry` and `cancel` do what the web app's buttons do. These commands act as the operator: they check the `[write]` switches, and the account's `mail.send` is checked when the server builds the transport, but no grant.

## Changing mailboxes

`serve` runs [holtmail-mail-writeback](../../../crates/mail-writeback/docs/README.md) next to sync (`src/writeback.rs`): at start every change left mid-send by a stopped process goes back to held, then a worker sends held changes (flags, labels, moves, deletes, appends) first in first out per account, and settles flags changes no sync confirmed within 15 minutes. Sync confirms flags changes itself after each folder's flag read; the server wins when it shows something else.

`ServerWriters` hands a writer to the worker only while `[write] enabled` is on and the account's capability for that kind of change is on (`holtmail_mail_writeback::allows`: `mail.flags`, `mail.move`, `mail.delete` for a move to the trash or a delete that only marks, `mail.expunge` with `mail.delete` for removing for good, `mail.append`); otherwise the change fails as `not_allowed` without reaching the server. Writers are `ImapSource::writer`, `JmapSource::writer` and `GraphSource::writer` with the account's sign-in as for syncs (a fresh OAuth token), kept for five minutes per account and only while the account's settings and stored sign-in stay the same (a new host, user, password or sign-in builds a new writer at the next change); import accounts have none. A rejected sign-in or connection failure pauses the account's changes in the worker (one attempt per backoff step, never one sign-in per held change).

**Consent to change mail (Microsoft Graph).** Graph writes need `Mail.ReadWrite` (`Provider::write_scope`). **Sign in again** asks for it whenever any of `mail.flags`, `mail.move`, `mail.delete`, `mail.expunge` or `mail.append` is on, and the sign-in records `settings.oauth.write`. Until then (`holtmail_mail_writeback::write_consent_missing`) the API offers no mailbox changes on the account (`writable` is empty, `may_write` refuses with `403`), the account list shows `needs_sign_in` with a `sign_in_reason` while such a capability is on, and a change already held (a retention delete, say) gets no writer: the server records `missing_consent = "mail.write"` (the webhook fires once; an earlier missing consent is kept, and one sign-in asks for every scope a capability needs) and answers `auth`, so the change waits instead of failing at once. Microsoft's IMAP scope and Google's mail scope already write.

**Retention.** An account's `delete_after_days` setting (set through `PUT /api/accounts/{id}/retention`) makes an hourly job record deletes for its live messages received (or dated) longer ago, at most 1 000 per account per pass, origin `retention`, one `mail_delete` audit entry per account and pass without a user: with `mail.expunge` they remove for good (the trash included), otherwise they move to the account's trash folder and leave what is already there. Nothing happens without `mail.delete`, with `[write] enabled` off, or without a trash folder and `mail.expunge`. Locations with an open change, or with any earlier retention change, are skipped, so a pass never records a second delete for the same place and a refused or failed delete is not recorded again every hour (it waits in the reader for _Try again_). The archive keeps every message.

## Writing contacts and calendars

`serve` runs [holtmail-pim-writeback](../../../crates/pim-writeback/docs/README.md) (`src/pim_writeback.rs`): at start every edit left mid-send goes back to held, then a worker sends held edits of `write_through` collections first in first out per collection; `Mailboxes::pim_changed` (called by the API after every edit) wakes it. `PimWriters` hands out an upstream only while `[write] enabled` is on, the collection is `write_through`, it belongs to a server account (not an import account) and that account has `pim.edit` or `pim.respond`; otherwise the edit waits as `not_allowed`. Edits other than replies also need `pim.edit` (`Writers::may_edit`, else they wait with `edit_off`), replies `pim.respond`. The upstream is the account's collections source for the collection's kind, built and signed in as for syncs (`dav::upstream_for`: CardDAV/CalDAV, Graph or JMAP, so a JMAP account with CalDAV calendars writes calendars over CalDAV), which is also the writer; a CalDAV writer lists its collections first and matches attendees against the account's address and its identities' addresses. Upstreams are kept five minutes per account and kind, and only while the account's settings and stored sign-in stay the same. `EditRebaser` implements the `Rebaser` with `holtmail-pim-edit`: the fields a change touched come from its stored patch, a change the post-batch step rebased sends its rebase on that version, and a reply is rebased once after a failed precondition, matching the user's attendee entry by the entries the patch itself touches.

**Consent (Microsoft Graph and Google).** Changing contacts and calendars through Graph needs `Contacts.ReadWrite` and `Calendars.ReadWrite`, and through Google's CalDAV `auth/calendar` instead of `auth/calendar.readonly` (`Provider::pim_write_scope`). **Sign in again** asks for them while `pim.edit` is on, and the sign-in records `settings.oauth.pim_write`. Until then (`holtmail_pim_writeback::pim_write_consent_missing`) the writer records `missing_consent = "pim.edit"` (the account shows `needs_sign_in` with a reason) and answers `auth`, so edits wait. Google's CardDAV scope already writes. With your own client, add the delegated permissions `Contacts.ReadWrite` and `Calendars.ReadWrite` (Microsoft) or the `auth/calendar` scope (Google). Answering invitations upstream (a `reply` change) also needs the account's `pim.respond` (`Writers::may_reply`); until then such changes wait with `respond_off`. The writer of a CardDAV, CalDAV or Graph account lists its collections when it is built, and a cached writer that does not know a collection (one created since) is built again, so its changes are not rejected as `unsupported`.

**Invitations.** `PimWriters::scheduling(collection)` answers the API's `Mailboxes::scheduling`: the collection's host (`Graph` always schedules; a CalDAV calendar does when its writer offers `respond`, which it does only where the server advertises `calendar-auto-schedule`; a JMAP calendar counts as not scheduling, because writes never pass `sendSchedulingMessages` and JMAP has no way to learn whether a server would honour it, so Holtmail mails attendees itself) and its writer's capabilities, whatever the write mode or capabilities say. It builds (or reuses) the account's writer, so it reaches only the account's own server. `SchedulingProbe::NoServer` means nothing will ever schedule (no account, an import account); `Unknown` means a server exists but cannot be asked now (unreachable, a failed sign-in, contacts and calendars off), and the API refuses to mail then rather than risk attendees hearing twice. A Graph account without the write consent counts as `Graph` with no capabilities. `EditRebaser::respond` reads a reply change's `Respond` from its patch, so `pim-writeback` answers through `CollectionWriter::respond`. `src/replies.rs` is an ingest observer: for mail that arrives live (never a backfill or an import) carrying an iMIP `REPLY`, every copy of that `UID` in a `write_through` calendar of an account with `pim.edit`, organized by one of the archive's own addresses and held by a server that does not schedule, gets a held change with the attendee's answer (`holtmail_pim_edit::apply_reply`, origin `api` without a user, recorded against what was served and checked with `validate`, one `pim_edit` audit entry per change), and the writer is woken. **Trust:** a reply is applied only when it names exactly one attendee and that attendee is the mail's `From`, or the real sender of mail through an alias service whose signature passed; anything else stays derived data. `From` can itself be forged, so this stops one attendee answering for another and casual forgery, not a sender who spoofs that attendee's address; such a mail can only change that one attendee's answer. **When it cannot be applied now** (the server cannot be asked, what is served keeps changing after three tries, a store error, or more than 300 automatic changes in the archive this hour) the reply is kept in `deferred_replies` and tried again with growing waits, from one minute up to six hours, for seven days; applying twice changes nothing. Elsewhere the reply only shows as derived data (a version of the event from mail and its answers in the calendar). Logs carry message and item ids and counts only.

## Contacts and calendars

An IMAP, JMAP or Microsoft Graph account can also archive its address books and calendars, synced by [holtmail-pim-sync](../../../crates/pim-sync/docs/README.md): over CardDAV and CalDAV ([holtmail-collection-dav](../../../crates/collection-dav/docs/README.md)), through Microsoft Graph for Graph accounts ([holtmail-collection-graph](../../../crates/collection-graph/docs/README.md)), or through the account's own JMAP session for JMAP accounts whose server offers contacts ([holtmail-collection-jmap](../../../crates/collection-jmap/docs/README.md)). It is off by default; turn it on in the web app (the account's menu → Archive contacts and calendars) or with `account edit <id> --contacts-calendars on`. The account's settings then hold `dav: { enabled, protocol, contacts_url, calendars_url, calendars_protocol, interval_minutes, dav_secret }`, where `protocol` is `dav` (left out), `graph` or `jmap` for address books, `calendars_protocol` (left out when the same) is how calendars are read, `interval_minutes` their own interval and `dav_secret` a sealed CardDAV and CalDAV password of their own.

- **Addresses.** `--dav-url` sets one address for both (Nextcloud: `https://host/remote.php/dav`; Radicale and Baïkal: the server), `--carddav-url` and `--caldav-url` set them apart. Without any, they are detected from the account's address: Fastmail (`https://carddav.fastmail.com`, `https://caldav.fastmail.com`), iCloud (`https://contacts.icloud.com`, `https://caldav.icloud.com`) and Yandex (`https://carddav.yandex.ru`, `https://caldav.yandex.ru`) by domain, else the mail domain's well-known addresses (`https://<domain>/.well-known/carddav` and `caldav`). Turning it on signs in and lists the collections first; nothing is stored when that fails, and a failed detection asks for the address.
- **Sign-in.** Password accounts use the mail user name and the stored password (an app password where the provider needs one); a JMAP account with a token sends it as a bearer token. Google accounts that sign in with OAuth use Google's addresses (`https://www.googleapis.com/.well-known/carddav`, `https://apidata.googleusercontent.com/caldav/v2/`) with a bearer token; turning it on asks for the extra CardDAV and CalDAV scopes, so the account has to **Sign in again** once (the web app opens it right away). Until then mail keeps syncing and the account shows "sign in again to allow access"; `settings.oauth.access` records what the last sign-in granted (`imap` or `imap_dav`). **Microsoft Graph accounts** read `/me/contacts`, the contact folders and `/me/calendars` with the account's Microsoft sign-in; turning it on asks for `Contacts.Read` and `Calendars.Read` on top of the mail scopes (`Access::GraphPim`, recorded as `graph_pim`), so the account signs in again once, as for Google, and mail keeps syncing meanwhile. With your own client, add the delegated Graph permissions `Contacts.Read` and `Calendars.Read`. **Microsoft accounts over IMAP** (OAuth) are refused with a note to add the mailbox as a Microsoft Graph account: their sign-in is for Outlook's IMAP resource, and reading Graph would need a second Microsoft sign-in with its own refresh token for the same account.
- **JMAP accounts** without a contacts address given ask the account's JMAP session first: when it offers `urn:ietf:params:jmap:contacts`, contacts are read through JMAP with the account's own password or token, and `protocol` is `jmap`; otherwise the CardDAV and CalDAV addresses are detected as above. Calendars come from JMAP too when the session offers `urn:ietf:params:jmap:calendars`. When it does not, or when only a calendars address is given (`--caldav-url`), calendars are read over CalDAV (`calendars_protocol: dav`) while contacts stay on JMAP, through [holtmail-collection-merge](../../../crates/collection-merge/docs/README.md): the given address, or the first of the provider's preset, the JMAP host's `/.well-known/caldav` and the mail domain's that lists a calendar with the account's sign-in (none found leaves the account with contacts only). Giving a contacts address always uses CardDAV and CalDAV for both. Moving an account from one protocol to the other marks the old collections removed and archives the new ones (their ids differ); nothing is lost. At start, `serve` looks once for CalDAV calendars of every JMAP account that reads contacts through JMAP and has none, and the API offers what it finds (`contacts_calendars.caldav_offer`); nothing changes until someone turns it on.
- **A password of their own.** `dav_password` in the API (`--dav-password-stdin`) stores a CardDAV and CalDAV password sealed apart from the account's (context `<account id>:dav`), for servers that want an app password; the user name stays the account's. An empty one removes it.
- **When.** On their own schedule: every `interval_minutes` (`--pim-interval`, the account's menu → Check contacts and calendars), else the account's mail interval, else the server's; `0` only on request. Sync now, turning them on, a change reported by the server's push (below) and `holtmail sync` start one too. Each run is a task of its own ("Contacts and calendars", kind `contacts_calendars`) with one log line per address book or calendar: new, changed, unchanged, removed and failed items and how changes were read. An unchanged CardDAV or CalDAV account costs one `PROPFIND` per home set, since collections whose tag did not move are not read. The account's status carries the latest such task (`status.contacts_calendars`); the schedule counts from the last run kept in the task list. Turning it off keeps everything archived; the collections stay browsable.

## Watching for changes

`serve` keeps watched accounts connected, so changes on the server start a sync within seconds instead of waiting for the interval, which still runs as a safety net. A watch only queues syncs: it never archives anything itself.

- **Mail.** IMAP accounts idle (`IDLE`, or `NOTIFY` for several folders where the server offers it; see [holtmail-source-imap](../../../crates/source-imap/docs/README.md#watching)) on the inbox, or on the all-mail folder for Gmail (by OAuth provider or an `imap.gmail.com` host), as archived so far, `INBOX` before the first sync; JMAP accounts listen to their event source. A change queues a sync of just the folders the server named (`SyncOptions::only`), or of the whole account for JMAP, after a two-second pause that gathers further changes (ten seconds at most). The account's setting `watch: { mode, folders }` (the account's menu → Watch for changes, `--watch`, `PATCH` `watch`) is `inbox` by default, `folders` with chosen paths (three at most without `NOTIFY`), or `off`. Microsoft Graph accounts are not watched (Graph's change notifications are not used); they keep their delta links and interval.
- **Contacts and calendars.** A JMAP event source with the contact and calendar types queues a contacts and calendars sync. CardDAV and CalDAV collections that offer WebDAV-Push get a registration (below). Both follow the account's `watch` mode: `off` turns them off too.
- **Connections.** One task per watched account opens its watches with fresh credentials and keeps them open: after a broken or refused connection it waits 5 seconds, doubling up to 5 minutes (5 minutes at once after a refused sign-in), and queues a catch-up sync once it is back. OAuth accounts reopen their watch every 45 minutes, before the access token expires, and others once a day. Access token refreshes of one account run one at a time and read the stored refresh token afresh, so a watch and a sync never spend the same rotated refresh token twice. A change to an account's settings, sign-in or pause restarts or stops its watch at once (API) or within 30 seconds (CLI). Accounts that need to sign in again are not watched.
- **State.** `status.watch` and `status.contacts_watch` say `live`, `starting`, `reconnecting` (with the reason), `polling` (the server cannot push) or `off`; the web app shows Live next to the account.
- **Queue.** Scheduled runs, watch runs and Sync now share one queue: at most `[watch] parallel_syncs` (4) accounts sync at a time, mail and contacts runs alike, and an account has one mail run and one contacts run at most. A request while a run is queued or going makes one more run follow it, covering every folder asked for meanwhile, so no change is lost.
- **WebDAV-Push.** With an https `public_url`, every CardDAV or CalDAV collection that lists the `web-push` transport gets a subscription for `<public_url>/api/push/dav/<id>` (a random 128-bit id, fresh P-256 keys and auth secret per collection), asked to last three days and renewed when less than a day is left; collections are listed again every six hours, or 30 minutes after a failure, and registrations of collections that are gone, accounts turned off and accounts removed are ended. `POST /api/push/dav/{id}` takes the server's message without a session, decrypts it with that subscription's keys ([holtmail-webpush](../../../crates/webpush/docs/README.md)) and queues the account's contacts sync; any other body or id answers `410`, which tells the server to forget the address. The keys live only in memory: after a restart new registrations are made, and the old addresses answer `410`. The server must be able to reach `public_url`. Without an https `public_url`, CardDAV and CalDAV run on their interval.

Logs carry account ids, counts and states, never folder names, collection addresses, subjects or secrets.

Everything the commands do can also be done in the web app by the owner or an admin: archives, IMAP accounts, uploads of mailbox files, syncing now, people and their access. The CLI stays for scripts and headless installs.

`serve` checks every 30 seconds which enabled accounts are due and queues their syncs (see "Watching for changes" for the queue), and removes expired sessions every hour. An account is due every `sync_interval_minutes` after its last run ended, at once when it never ran or a restart interrupted its sync (also an account that syncs only on request: the interrupted sync runs once at start, then it waits for requests again); each account can have its own interval (`sync_interval_minutes` in its settings, set from the web app), `0` meaning only on request. The server-wide interval comes from the config when set there, else from the web app (stored in the settings), else 15 minutes. Changing an account's server, user name or excluded folders from the web app signs in with the new settings first; the account keeps its archive, and messages it already has are recognized by their bytes, so nothing is stored twice. A change to another server (host, port, or a drop to plain text) or another user name forgets the UIDs and cursors of the account's folders, so the next sync looks at every message of the new mailbox: its `UIDVALIDITY` and UIDs can equal the old ones by chance (Dovecot and GreenMail both derive `UIDVALIDITY` from the clock) and would otherwise hide its mail. Syncs and imports started from the web, the schedule and watches share one runner that keeps at most one run per account. How the last run of each account ended (when, new messages, the error) is stored, so the web app shows it after a restart and the schedule counts from it. Uploaded files wait in `<data_dir>/uploads` and are removed once imported; files of an import a restart interrupted are removed at start.

An account can archive only mail older than a number of days (`min_age_days` in its settings, set from the web app or `account edit --min-age-days`): a folder's sync stops at its first message that is younger, by the server's received time or else its `Date` header, and that message and the later ones are archived by a sync once they are old enough. See [holtmail-sync](../../../crates/sync/docs/README.md).

Attachment text is read by [`holtmail-extract-basic`](../../../crates/extract-basic/docs/README.md) (plain text, CSV, HTML, PDF, DOCX, XLSX, PPTX, ODT, ODS, ODP) while mail is archived, once per file, and kept as a derived blob so reindexing and flag changes reuse it. `reindex` also rebuilds the listed fields of every contact and event from its latest raw version, and with them what is derived from those fields: each event's group of copies and stored instances (see [holtmail-calendar](../../../crates/calendar/docs/README.md)) and the search documents of contacts and events. `reindex` reuses those texts; `--refresh-attachments` drops them (and their blobs) and reads every attachment again, e.g. after an upgrade that reads more types. At start, `serve` indexes the attachment text of mail archived before this existed: in the background, only messages with attachments, once (the setting `attachment_text` records it is done); search finds the text as it goes. Image thumbnails for the reader are made on first view and kept as derived blobs too.

Invitations, updates, replies and cancellations in mail (`text/calendar` and `application/ics` parts) become events in each archive's "From mail" calendar as mail is archived (see [holtmail-ingest](../../../crates/ingest/docs/README.md#invitations-in-mail)). At start, `serve` reads them from mail archived before this existed: in the background, after the index pass, only messages with a calendar part among their attachment rows, once (the setting `invitations_from_mail` records it is done). `reindex` reads them again too and prints how many messages had calendar parts and how many versions were new. The log carries counts and message ids only.

People (contact cards grouped by a shared email or phone, plus frequent correspondents from mail; see [holtmail-people](../../../crates/people/docs/README.md)) are derived per archive and rebuilt whole. The runner rebuilds an archive's people in the background after an import, after a mail sync that archived new messages and after a contacts and calendars sync that added, changed or removed something; one rebuild per archive runs at a time, and requests while it runs make it run once more at the end. Splits, joins and undos made in the web app go through the same queue and the API answers once a rebuild that started after the change has finished. A rebuild that panics is logged (archive id only) and counts as failed; later requests still run, and a contacts sync that panics still frees its account for the next one. `holtmail import` and `holtmail sync` rebuild the archives they touched before they exit and print the counts. At start, `serve` builds the people of every archive once, after the index and invitation passes, until the setting `people` is set. `reindex` rebuilds every archive's people last and prints how many have cards and how many come from mail alone. Ids stay the same across rebuilds. The log carries archive ids, counts and milliseconds only.

Remote images go through [`holtmail-fetch-http`](../../../crates/fetch-http/docs/README.md), which only contacts public addresses, optionally through an outbound proxy (`image_proxy` in the config, or set by an owner or admin in the web app, stored sealed with `secret.key`; the config wins). The proxy can change while the server runs. For archives with "Save remote images" on, [`holtmail-remote`](../../../crates/remote/docs/README.md) saves the images of new messages after every sync or import that brought any and once at start; mail archived before saving was turned on, and failed images, only when asked from the web app. One remote image task per archive at a time. The web reader's image proxy uses the same fetcher.

Syncs, imports, contacts and calendars syncs and remote image work run as tasks with progress and a log (counts, folder names and reasons, never message content), listed in the web app under Settings → Tasks. Remote image tasks can be stopped between messages. Tasks are stored in the database (written behind the work at most once a second, and at shutdown on `SIGINT` or `SIGTERM`), so the list looks the same after a restart; the last 200 finished tasks are kept, and logs keep their first 50 and last 450 lines. Tasks a previous process left running are marked _interrupted_ at start: an interrupted sync is due again at once (also for an account that syncs only on request), and interrupted remote image work (older mail, or failed images) starts again and skips the messages it already looked at; images of new mail are picked up at start anyway.

## Receiving mail over SMTP

`[smtp]` turns on an SMTP listener ([holtmail-smtp](../../../crates/smtp/docs/README.md)) for mail servers that forward, BCC or journal into the archive, such as Postfix `always_bcc`, an Exchange or Microsoft 365 journal rule, or a Google Workspace routing rule:

```toml
[smtp]
listen = "0.0.0.0:2525"
hostname = "archive.example.com"
allow = ["10.0.0.0/8", "127.0.0.0/8"] # client networks; loopback only by default
max_size_mb = 50
tls_cert = "/etc/holtmail/smtp.pem" # turns STARTTLS on; with tls_key
tls_key = "/etc/holtmail/smtp.key"
require_tls = false
username = "journal" # with HOLTMAIL_SMTP_PASSWORD: clients must sign in
# trusted_authserv_ids = ["mx.example.org"] # see "Message insights"; none by default
[[smtp.route]]
recipient = "journal@archive.example.com"
archive = "Contoso"
journal = "exchange" # store the original message of a journal report
[[smtp.route]]
recipient = "*@bcc.archive.example.com"
archive = "Contoso"
folder = "BCC"
```

Each route takes one address or every address of a domain (`*@domain`, case-insensitive); other recipients are refused with `550`, so it never relays. Mail goes into the route's archive (a name that does not exist is created), in the "Received by SMTP" account of that archive (an import account, made at the first start), in the route's folder (the recipient by default). A message for several routes is stored once per archive and folder. The bytes are stored as received; `journal = "exchange"` stores the original message attached to an Exchange journal report instead, byte for byte, and keeps the report when the mail is not one (the report's envelope part, with Bcc recipients, is not kept). The answer `250` comes after the bytes and their metadata are stored; the search index is committed every two seconds. Messages deleted from the archive earlier are accepted and left out. `serve` checks the config at start and refuses to start on a bad one; `GET /api/smtp` and Settings → SMTP show the listener and its counters since the start. Remote images of such mail are saved by "Save images of older mail", not at once.

## Webhooks

Owners and admins add webhooks in Settings → Webhooks (or `POST /api/webhooks`): an address and the events it wants, `task.finished`, `account.needs_sign_in`, `messages.deleted` and `ledger.verified` (see [holtmail-hooks](../../../crates/hooks/docs/README.md) for the payloads). Each delivery is a `POST` of `{ "id", "event", "at", "data" }` with `Holtmail-Event`, `Holtmail-Delivery` (the same on every attempt) and `Holtmail-Signature: t=<seconds>,v1=<HMAC-SHA256>` keyed with the webhook's secret, which is shown once when the webhook is added or its secret is renewed and stored sealed with `secret.key`. Payloads carry ids, counts, states and ledger hashes, never mail content or addresses.

Events are written to the database when they happen, also from the command line (`holtmail delete`, `holtmail ledger verify`), and `serve` delivers them: at once, then 30 seconds, 2 minutes, 10 minutes, 1 hour and 6 hours after failures (any answer other than `2xx`, no connection, or no answer within 10 seconds), and gives up after six attempts. Deliveries survive restarts; the newest 200 finished ones per webhook are kept. A turned-off webhook gets no new events; waiting deliveries still go. Redirects are not followed. The log carries webhook ids, delivery ids, statuses and attempt counts only. `messages.deleted` and `ledger.verified` carry the ledger's head, so a receiver that keeps them holds the anchors `holtmail ledger verify --anchor` checks.

## Email aliases

See [ALIASES.md](../../../docs/ALIASES.md). `src/aliases.rs` is the only place that names the alias implementations: `detectors(&config.aliases)` (SimpleLogin, addy.io, Firefox Relay, DuckDuckGo, Apple, then each `[[aliases.rules]]` in order; the first that recognises a message wins), `providers()` (with their capabilities and where the owner finds a key) and `connect(roots)` (SimpleLogin, addy.io, Relay and Fastmail directories, trusting `tls_ca_file`). The ingest pipeline gets the detectors; `holtmail_aliases::AliasManager` gets the providers, `connect` and the same detectors (for encoded reverse aliases and default reply strategies), and `Runner` implements the API's `Aliases` with it.

- At start, after the other passes, every message is detected again when the detectors' fingerprint (their versions, so trusted domains and rules too) differs from the setting `alias_detectors`; the archives that changed get their people rebuilt. Changing a rule therefore takes effect for old mail on the next start.
- Every `sync_interval_minutes` (from a minute after start) every service's aliases are listed; a failure is kept on the service and logged with the count only.
- Keys are sealed with the instance's secret box for `alias-service:<id>` and never logged; logs carry service ids and providers.

A rule with a bad provider id stops the server at start with the rule named.

## Message insights

See [INSIGHTS.md](../../../docs/INSIGHTS.md). `src/insights.rs` is the only place that names the extractors: `[insights] extractors` picks among `unsubscribe` ([holtmail-insight-unsubscribe](../../../crates/insight-unsubscribe/docs/README.md)), `schemaorg` ([holtmail-insight-schemaorg](../../../crates/insight-schemaorg/docs/README.md)), `pass` ([holtmail-insight-pass](../../../crates/insight-pass/docs/README.md)), `parcel` ([holtmail-insight-parcel](../../../crates/insight-parcel/docs/README.md)), `links` ([holtmail-insight-links](../../../crates/insight-links/docs/README.md)) and `code` ([holtmail-insight-code](../../../crates/insight-code/docs/README.md)), all on by default, and they always run in that order, whatever the order in the file, because the order is part of the fingerprint. It builds one [`holtmail_insights::Runner`](../../../crates/insights/docs/README.md), installs its panic hook (panic reports name the extractor and message id, never the panic's text), gives the runner to every ingest pipeline (`Services::ingest`), and gives the API its fingerprint, `show_possible` and the walk's progress (`holtmail_api::InsightsConfig`). With `enabled = false` (or `HOLTMAIL_INSIGHTS=false`) nothing is computed, stored or served: messages carry `insights: null` and `/api/archives/{id}/insights/status` is `404`. An unknown extractor or kind name stops every command at start.

New mail gets its insights as it is archived. Older mail, and every message after an upgrade changes the fingerprint, gets them from **the walk** (`src/walk.rs`):

- It runs once in the start-up chain, after people are built, then whenever `WalkWake` is signalled and at least hourly, so rows a crash lost while the server runs are caught too. Signals while it runs coalesce into one more run.
- Each step (a server-private `#[async_trait] Step`: `name`, `pending`, `apply`, `unusable`, and `committed`, called after the index commit of each page, a no-op by default) lists what it still has to do as an anti-join or a durable queue, so the walk keeps no cursor: a walk stopped at any point, even by SIGKILL, picks up where the rows end. The steps, in this order:
  - `insights`: messages without a row under the current fingerprint. A message whose row it writes gets its stage-B row and its search document rebuilt at once.
  - `index`: messages in the store's reindex queue (`insight_reindex`), whose search document is behind their categories or insights. It rebuilds the document from the bytes the walk already parsed (`Ingest::reindex_parsed`, no second blob read) and, in `committed`, dequeues each message under the sequence it listed it with. A message re-queued in between keeps its higher sequence and stays queued; a run that stops before the commit leaves everything queued. A message whose bytes cannot be read or parsed is dequeued too, since nothing can be indexed from them. `category:` search therefore catches up as the queue drains (INSIGHTS.md §13: about 4,000 messages a minute on SSD), while lists and counts, which come from the database, are exact at once.
  - Chats' `chat-facts` follows.
- Per archive it takes the union of the steps' pending ids in pages of 200, ordered by id, reads each blob once and parses it once, two messages at a time, and runs every step that listed the message. It commits the search index after each page and pauses 50 ms between pages.
- A message deleted meanwhile is skipped. A blob that cannot be read is recorded as `unreadable`, bytes that do not parse as `unparsable`; neither is listed again until the fingerprint changes.
- A run with work shows as one task of kind `analyse` ("Reading archived mail again", counts only, cancellable; the next wake carries on), and its `task.finished` webhook carries ids and counts only. The same counts feed `GET /api/archives/{id}/insights/status`. Logs carry message ids, counts and timings, never content.

`holtmail reindex` also fills missing and outdated insights rows, since it reads and parses every message anyway. The index fields `insights` and `categories` came in one schema change, so the first start after that upgrade finds an emptied index, records `index_rebuild` and rebuilds every document, filling any missing insights and stage-B rows on the way; the walk then finds nothing to do.

**Deletion reviews and insight searches** (INSIGHTS.md §9). A deletion review (web app, API or `holtmail delete`) whose search uses an operator that reads insights or categories (`category:`, `has:code` and the other kinds, `is:newsletter`, `is:notification`, `is:personal`, `is:list`, negated or not) is refused with `409` and "Some messages are still being read. Try again when search has caught up." while the archive has messages without insights under the current fingerprint, categories rows derived under another stage-B fingerprint than the archive's current one (a changed trust list, own-address set, category data or `health` flag), messages in the reindex queue, or `index_rebuild` is set. A refusal also wakes the walk. Other searches are never refused for it. With insights off such a review is refused with `400`, since rows left from when insights were on are no longer kept up to date. The walk's insights step queues a message for reindexing before it writes its insights row and dequeues it only after the page's index commit, so a crash mid-page leaves the message for the index step.

**Trust and categories** (stage B, INSIGHTS.md §4.2, §4.3, §6.5). `src/insights.rs` also names the categorizers: `[insights.categories] sources` picks among `signals` ([holtmail-category-signals](../../../crates/category-signals/docs/README.md)), always on whether listed or not, and `domains` ([holtmail-category-domains](../../../crates/category-domains/docs/README.md)). They vote in that fixed order, and the order of the names in the config never changes `derive_fp`. It builds one [`holtmail_insights::Deriver`](../../../crates/insights/docs/README.md) with `health`, `sources`, `[insights] import_authserv_ids` for import accounts, `[smtp] trusted_authserv_ids` for the "Received by SMTP" account (empty without `[smtp]`), and every other account's list as stored. Ingest (`Services::ingest`) derives one message after each insights write; the API gets `health`.

`domains` looks the sender up in the CC0 Wikidata table compiled into the binary (`wikidata`, offline, no download): first the sender's host, then its registrable domain, giving topics and never a kind. A sensitive topic from the table (such as `finance`) counts only when the message's trust is `aligned`; the others apply at every trust level. `Insights::open` loads the table once, when `domains` is listed, and keeps it as `Insights::domains`, the one `Arc<DomainsCategorizer>` the deriver votes with; `src/category_data.rs` calls `reload` on it (see **Category data files** below). At start it logs `domain table loaded` at info with the table name, version, row count and load time in `millis` (about 8 ms for some 28,000 rows in a release build, 70 ms in a debug one). A table that does not load stops every command at start with an error naming the table and the broken rule, never a row. The default list includes `domains`, so an archive derived before it runs one stage-B pass, with no blob read, on the first start; drop `domains` from `sources` to turn it off.

| Key                                  | Default                  | What                                                                                                                                                                    |
| ------------------------------------ | ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `[insights] import_authserv_ids`     | `[]`                     | authserv-ids whose `Authentication-Results` are trusted for mail of import accounts other than the SMTP one                                                             |
| `[insights] one_click`               | `true`                   | `false` sends no one-click unsubscribe requests (the kill switch); the reader then says `disabled`                                                                      |
| `[insights] one_click_test_networks` | `[]`                     | only with the `insights-test-data` feature: CIDR networks one-click may reach although they are not public; an unknown key in every other build                         |
| `[insights.categories] health`       | `true`                   | `false` derives, applies and serves no `health` topic; stored override bits are kept                                                                                    |
| `[insights.categories] sources`      | `["signals", "domains"]` | the categorizers that vote, among `signals` and `domains`; an unknown or repeated name stops every command at start                                                     |
| `[insights.categories] update`       | `false`                  | `true` checks for signed category data releases every 168 h and loads newer ones; needs `domains` in `sources` and at least one data source                             |
| `[insights.categories] data_sources` | `["wikidata"]`           | the downloaded tables to use, among `wikidata` (CC0) and `ut1` (CC BY-SA 4.0, a separate opt-in); an unknown or repeated name stops every command at start              |
| `[smtp] trusted_authserv_ids`        | `[]`                     | set it only to the authserv-id of the MTA in front of Holtmail, and only when that MTA removes forged `Authentication-Results` fields carrying its own id (RFC 8601 §5) |

An authserv-id is 1 to 255 printable ASCII characters without spaces; a list holds at most 16, none repeated ignoring case. A bad one stops every command at start, naming the setting.

**The stage-B pass** (`src/derive.rs`, `derive_if_needed`) runs after every walk run, so once in the start-up chain and then on every `WalkWake`. Per archive it takes one `DeriveContext` (categorizer snapshots, trust lists, own addresses and their `derive_fp`), pages `derive_inputs` 1,000 at a time, derives each row from stored columns only, never a blob, and writes with `set_message_categories_queued` in batches of 500: the messages whose effective kind or topics changed are put in the reindex queue in the same transaction as their rows. When it queued any, the walk runs again at once, without waiting for a wake, so its `index` step brings search up to date. When a categorizer's snapshot changes, the archive starts again after the batch in flight with a fresh context; rows already written carry the old fingerprint and are listed again, and archives finished under the old snapshots are done again before the pass ends. An archive that keeps changing is left for the next wake after 8 restarts. Nothing in the server writes overrides: the API does, under its own `CHANGES` mutex. What wakes the pass:

- `Mailboxes::insights_changed`, which the API calls after an override edit, a changed trust list or a stored preset;
- alias detection at start, when it changed any message (`refresh_alias` removes that message's stage-B row);
- the hourly timer and every other walk wake.

Override edits queue the messages they change in their own transaction (`put_category_override`, `delete_category_override`) and wake the walk through `insights_changed`.

**One-click unsubscribe** (INSIGHTS.md §10). With insights on and `[insights] one_click = true` (the default), `InsightsConfig::one_click` builds one [`HttpOneClick`](../../../crates/fetch-http/docs/README.md) with the built-in roots plus `tls_ca_file`, and `Insights::open` hands it to the API as `Arc<dyn OneClick>`. It always connects directly: `image_proxy` and the proxy environment variables never apply, because a proxy would resolve the list's name itself and the public-address check could not hold. `one_click = false` is the kill switch: the reader says `disabled` and `POST /api/messages/{id}/unsubscribe` answers `400`. `Operations::fresh_insights` (`src/operations.rs`), which the route calls first, runs `Ingest::refresh_insights` when the message's row is missing or not under the current `extract_fp`, then `Ingest::derive_categories` when its stage-B row is missing or not under the current `derive_fp` (a fresh `DeriveContext`), both on the runner's own ingest pipeline, and signals `WalkWake` when either queued the message for reindexing. A failed recompute logs the message id only and answers `500`.

**Category data files** (INSIGHTS.md §8, `src/category_data.rs`). Whenever insights are on and `domains` is among the `sources`, update on or off, `Updater::open` reads `{data_dir}/categories/manifest.json` and `manifest.json.sig` if they exist, checks them with `verify_stored` (signature and compiled-in key; not the expiry or the version, so stored files keep loading after `not_after` while updates are off or the server is offline), then loads each file of `data_sources` the manifest lists with `check_file` (size first, then SHA-256, header and row count). The bundled `wikidata` table is always loaded and is replaced by a downloaded `wikidata` only when that one's version is newer ([`is_newer`](../../../crates/category-data/docs/README.md)); `ut1` is added only when listed. Anything that fails is ignored with a warning naming the file and the reason, and the bundled table stays. The categorizer is reloaded with that set before anything derives.

With `update = true` the server runs one loop (`category_data::run`, spawned beside `aliases::run_schedule`). It waits 5 minutes after start, or longer when the last check recorded in settings was less than one interval ago, then checks every 168 h. A check:

1. Fetches `manifest.json` from the release address (`https://github.com/holtmail/holtmail/releases/download/categories-latest/`) with the stored `ETag`. A `304` records `not_modified` and changes nothing. No `ETag` is sent while the stored release is not fully loaded, so a damaged or half-written release is fetched again.
2. Fetches `manifest.json.sig` and runs `verify_manifest` (signature, key id, expiry at most 60 days ahead). A version older than the loaded release, or older than the last accepted one (`categories_data_version`) when the stored files do not load, is refused (`not_newer`); the same version as the loaded release counts as `not_modified` and stores the new `ETag`.
3. Fetches each file of `data_sources` the manifest lists, by its fixed name (never a name read from the manifest) and capped at the listed size, and checks it with `check_file`.
4. Writes the files, then the manifest, then the signature into `{data_dir}/categories/`, each through a temporary file in the same folder, `fsync`, rename and an `fsync` of the folder. A crash between two writes leaves a manifest whose files do not match; start-up then refuses those files and loads the bundled table, and the next check fetches the release again.
5. Stores `categories_data_version` and `categories_data_etag`, reloads the categorizer and wakes the walk: the new snapshot changes `derive_fp`, and the stage-B pass derives every row again with no blob read.

Every check records `categories_data_checked_at` (Unix ms) and `categories_data_outcome` (`updated`, `not_modified`, `refused` or `failed`) in settings and publishes them, with the loaded files, to `GET /api/insights/data` (`holtmail_api::DataStatus`). A refusal (signature, key, expiry, rollback, hash, size, a file name outside the fixed set, a table that does not load) leaves the files and the loaded tables as they were. Downloads use [`HttpDataDownload`](../../../crates/fetch-http/docs/README.md) with the built-in roots plus `tls_ca_file`, https only, a direct connection whatever `image_proxy` says, redirects only to `github.com`, `objects.githubusercontent.com` and `release-assets.githubusercontent.com` (at most 2), and a 60 s timeout per file.

Logs: `stored category data file loaded` (file, version, rows), `stored category data file ignored` / `stored category data ignored` (file, reason), `category data file verified` (file, version, bytes, rows), `category data updated` (version, files, millis), `category data not modified` (millis), `category data refused` (`reason`: `signature_length`, `no_release_key`, `unknown_key`, `signature`, `manifest`, `expired`, `too_far_ahead`, `not_newer`, `file_name`, `not_listed`, `size`, `sha256`, `data`, `table_name`, `table_version`, `rows` or `download_refused`), `category data check failed` (the fetch or write error). Never the signing key, a URL or file contents.

The release build compiles in no signing key yet: both slots in `holtmail-category-domains` are empty, so with `update = true` every release is refused with `no_release_key` until the maintainer compiles the production keys in (see its README, "Keys and rotation").

**Test networks.** The `insights-test-data` Cargo feature (off by default; it turns on `holtmail-fetch-http/test-networks` and `holtmail-category-domains/test-key`, which compiles in the public test key `test`) adds `[insights] one_click_test_networks = ["CIDR", ...]`: networks one-click may reach although they are not public, for the integration suite's `images` network. Only one-click uses the list, never the image fetcher. A malformed entry stops every command at start. Without the feature the key is an unknown key and stops the server, and the release build and the default Docker image have neither the key nor the code behind it. It also adds four keys to `[insights.categories]` for the data download suite, unknown keys in every other build: `update_base_url` (default the release address above; https, ending in `/`), `update_hosts` (the pinned hosts; default the three GitHub hosts), `update_interval_secs` (default 604800) and `update_delay_secs` (the least wait before the first check; default 300). Build it with `cargo build -p holtmail-server --features insights-test-data`.

The pass logs rows, changed rows, restarts, failed archives, batches, the slowest batch and the elapsed time, never addresses, domains or authserv-ids. With insights off nothing is derived and `insights_changed` does nothing.

`holtmail insights explain <message-id>` prints, for the operator's terminal only, what each extractor saw in one stored message: rule names, positions and scores, each candidate as its shape (digits as `D`, letters as `a`), keywords only when they are in the extractor's own table, and markup tag names. It never prints a value, host, URL or address. It reads only the database and the blobs, so it works while `serve` runs, and it uses the configured extractors even when `enabled = false`.

## Back up and move an instance

An instance is its database, its blobs and `secret.key`; the search index, uploads and thumbnails can be made again.

```bash
holtmail backup --output /backups/holtmail-2026-11-05.tar
holtmail restore --input /backups/holtmail-2026-11-05.tar --data-dir /srv/holtmail
```

`backup` writes one tar file, front to back, so it can go to a pipe (`--output -`) and needs about one message of memory:

| Entry           | What                                                                                                                                                    |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `manifest.json` | First entry: format version, Holtmail version, `created_at`, counts of archives, messages and blobs, whether blobs and the key are in                   |
| `holtmail.db`   | A consistent snapshot of the database (SQLite `VACUUM INTO`), taken while `serve` keeps running; it carries the splits and joins of people made by hand |
| `secret.key`    | Only with `--include-secret-key`                                                                                                                        |
| `blobs/<hash>`  | Every blob the snapshot references (messages, attachments, saved images, derived files), read through the blob store, so S3 blobs are included too      |

It is safe while `serve` runs: mail archived after the snapshot is simply not in the backup. A blob that is missing or damaged in the blob store is left out, named, and makes the command fail after the file is written. It writes `<output>.part` and renames it when done, and never overwrites a file.

**`secret.key`.** Mailbox passwords, OAuth refresh tokens and the image proxy password are sealed with it. Without it a restored instance has all the mail but must sign in to every mailbox again. By default the key is left out and `backup` says so: keep a copy of `<data_dir>/secret.key` somewhere safe, apart from the backups. `--include-secret-key` puts it in, and then the backup file opens those credentials for anyone who has it; store it like the key.

**Blobs on S3.** By default the blobs are copied out of the bucket into the backup like any other. When the bucket has its own backup or versioning, `--skip-blobs` leaves them out and says so; a restore from such a backup checks that the blob store the config names holds every blob the database references and warns about the ones it does not.

`restore` reads a backup into a data directory that does not exist or is empty, and refuses any other. It checks that the first entry is a manifest it understands, writes `holtmail.db` (and `secret.key` when present, mode `0600`), and puts every blob into the blob store the config names (`<data-dir>/blobs` by default, or `fs_at` / S3 from the config) after checking that its bytes hash to its name; one damaged blob stops the restore. It then checks that every blob the database references is in the blob store and rebuilds the search index (`--skip-reindex` leaves that to `serve`, which rebuilds it in the background at start). A restore that stops part way says so; remove the directory before trying again.

To move an instance to another machine: `holtmail backup` on the old one (or stop it and copy the data directory), copy the file and `secret.key`, `holtmail restore` on the new one with its config, copy `secret.key` into the new data directory if it was not in the backup, then start `serve`.

## Signing in

While there are no users, `serve` logs a one-time setup link at start:

```
No users yet. Open http://127.0.0.1:8080/setup?token=... to create the owner; the link works once.
```

Whoever opens it creates the owner account and is signed in. The link stops working once any user exists and a new one is printed on every start until then, so keep the log private. The link uses `public_url` when set, else the listen address (`localhost` for `0.0.0.0`).

On headless installs, `user add` creates users directly; the first user becomes `owner` unless `--role` says otherwise, later ones `member`. `user add` and `user password` read the password from `HOLTMAIL_PASSWORD` or the first line of stdin; passwords need at least 10 characters. Passwords are stored as Argon2id hashes and never logged. The `user` commands open only the metadata store, so they work while `serve` is running; in Docker, run them with `docker exec <container> holtmail user ...`.

`sync` prints per folder how many messages were new, already known, removed from the server, changed (flags or labels changed on the server since archiving) and failed; the Tasks log shows the same. Gmail accounts sync `[Gmail]/All Mail` with labels instead of each label folder, and pick up read, flagged and label changes through `CONDSTORE`; see [holtmail-sync](../../../crates/sync/docs/README.md).

`reindex` rebuilds every message's search document. The server also does it by itself: when the search index on disk was written by an older version with other fields (Tantivy cannot add a field, so the new version starts with an empty index), any command that opens it records the setting `index_rebuild`, and `serve` rebuilds the index in the background at start and clears the setting when done. Until then search finds only mail indexed since; lists, folders and labels come from the database and are complete. An interrupted rebuild runs again at the next start. Migration 0014 (the calendar) sets `index_rebuild` too, because the index schema gained contacts and events and the calendar's derived rows have to be filled for items stored before: the first `serve` after the upgrade rebuilds the index, every item's calendar rows and its search document, and commits after every page of items.

`import` creates the archive and an import account (named after the file, or `--account`) when missing, maps folder names to roles (`Sent`, `Отправленные`, `[Gmail]/All Mail`, ...), commits the index every 500 messages and prints progress. Running it again on the same files adds nothing: messages are recognised by their bytes. Files that are not messages are counted as failed and skipped.

## Gmail and Microsoft sign-in (OAuth)

Microsoft turned off password sign-in for IMAP, and Gmail only takes app passwords, so Gmail, Google Workspace, Outlook.com, Hotmail and Microsoft 365 accounts sign in with OAuth and IMAP `AUTHENTICATE XOAUTH2`.

**The default client is Thunderbird's.** Its client ids, and Google's client secret, are public in `mailnews/base/src/OAuth2Providers.sys.mjs` in comm-central, and Holtmail uses them unless the config names another client. Such an installed-app client can only send the browser back to a loopback address (`http://127.0.0.1`), not to a self-hosted Holtmail, so:

1. The web app (or `account add-oauth`) opens the provider's page in a new tab, with PKCE, a random `state` and the address as `login_hint`.
2. After the person allows access, that tab lands on `http://127.0.0.1/?code=…&state=…`, a page that does not load.
3. They copy that page's address and paste it into Holtmail, which reads `code` and `state`, exchanges the code and signs in to IMAP with the token before storing anything.

Risks of the borrowed client, also shown in the web app:

- The consent screen says Thunderbird, not Holtmail.
- Google or Microsoft can block or rate-limit the borrowed client at any time; sign-in then fails with "the provider refused" until you set your own client.
- Whether using it fits the provider's terms is your call.

**Your own client.** Register an app with the provider and put it in the config. Its redirect is `<public_url>/api/oauth/callback`, so set `public_url` to the address people open. The browser then comes back to Holtmail on its own and there is no paste step.

- Google: in Google Cloud Console create a project, enable the Gmail API, configure the OAuth consent screen (add the scope `https://mail.google.com/`; while the app is in testing, add the people who will sign in as test users, and note that refresh tokens of apps in testing expire after 7 days), then create an OAuth client of type "Web application" with the redirect URI above.
- Microsoft: in Microsoft Entra ID → App registrations register an app for "Accounts in any organizational directory and personal Microsoft accounts", add a Web redirect URI as above, create a client secret, and add the delegated permissions `IMAP.AccessAsUser.All` (Office 365 Exchange Online / `https://outlook.office.com`) and `offline_access`.

```toml
[oauth.google]
client_id = "123-abc.apps.googleusercontent.com" # HOLTMAIL_OAUTH_GOOGLE_CLIENT_ID
client_secret = "..." # HOLTMAIL_OAUTH_GOOGLE_CLIENT_SECRET
# redirect_url = "https://mail.example.com/api/oauth/callback"  # HOLTMAIL_OAUTH_GOOGLE_REDIRECT_URL

[oauth.microsoft]
client_id = "00000000-0000-0000-0000-000000000000" # HOLTMAIL_OAUTH_MICROSOFT_CLIENT_ID
client_secret = "..." # HOLTMAIL_OAUTH_MICROSOFT_CLIENT_SECRET
```

`authorize_url` and `token_url` (`HOLTMAIL_OAUTH_<PROVIDER>_AUTHORIZE_URL`, `_TOKEN_URL`) replace the provider's endpoints, for a single-tenant Microsoft authority (`https://login.microsoftonline.com/<tenant>/oauth2/v2.0/authorize` and `/token`) or a national cloud; `graph_url` (`HOLTMAIL_OAUTH_MICROSOFT_GRAPH_URL`) is the Graph address new Graph accounts are given (stored as their `api_url`), such as `https://graph.microsoft.us/v1.0`. `imap_host` and `imap_port` (`HOLTMAIL_OAUTH_<PROVIDER>_IMAP_HOST`, `_IMAP_PORT`) are the IMAP server new OAuth IMAP accounts of that provider connect to over TLS, instead of `imap.gmail.com` or `outlook.office365.com` on 993, for a national cloud such as `outlook.office365.us`; accounts keep the server they were created with, and their server, port and security cannot be changed. The integration tests point them at Dovecot, which checks the tokens at a mock provider. The three URLs must use https (plain http only to a loopback address, which is how the end-to-end checks point them at a local fake). `redirect_url` defaults to `<public_url>/api/oauth/callback` for an own client and `http://127.0.0.1` for Thunderbird's. Setting it without `client_id` changes only the redirect of Thunderbird's client, e.g. to `http://127.0.0.1:8080/api/oauth/callback` when Holtmail itself runs on that loopback address (untested against the providers). A redirect ending in `/api/oauth/callback` turns the paste step off. `client_secret` without `client_id` is an error. Prefer the environment variables for the secret. `public_client = false` (`HOLTMAIL_OAUTH_<PROVIDER>_PUBLIC_CLIENT=false`) turns Thunderbird's client off for that provider: without its own `client_id` the provider is then not offered at all (`GET /api/oauth/providers` leaves it out, the web app shows no sign-in button for it, and starting a sign-in is `400`); accounts already signed in with it fail at their next token refresh and ask to sign in again.

**Microsoft Graph.** A Graph account signs in with the same Microsoft client but asks for `https://graph.microsoft.com/Mail.Read https://graph.microsoft.com/User.Read offline_access` instead of the IMAP scope, and its refreshes ask for the same scopes: the account's kind decides, since an IMAP token is refused by Graph. With your own client, add the delegated Microsoft Graph permissions `Mail.Read` and `User.Read` (and `offline_access`) next to, or instead of, `IMAP.AccessAsUser.All`. Whether Thunderbird's client is granted `Mail.Read` has not been checked against Microsoft (Thunderbird itself asks for `Mail.ReadWrite` and more behind a preference).

**Google contacts and calendars.** An IMAP account with contacts and calendars on signs in with `https://www.googleapis.com/auth/carddav` and `https://www.googleapis.com/auth/calendar.readonly` next to the mail scope (`https://www.googleapis.com/auth/calendar` with Thunderbird's client, which is what Thunderbird asks for). With your own client, enable the CalDAV API and the CardDAV API in the project and add those scopes to the consent screen.

**After sign-in.** The refresh token is sealed with `secret.key` (bound to the account id) like passwords; the account's settings record `oauth: { provider, needs_sign_in, access, send, write, missing_consent }` (`send` when the sign-in included the send scope, `write` when it included the write scope, `missing_consent` while a capability waits for one). Access tokens live only in memory: before each sync the server uses the cached one while it has more than two minutes left, else refreshes it, and stores a rotated refresh token when the provider sends one. When the provider answers `invalid_grant` (access revoked, password changed, token expired) the account is marked as needing sign-in: the scheduler skips it, "Sync now" is refused, and the web app offers "Sign in again", which replaces the stored token and clears the mark. A password account can move to OAuth the same way. Waiting sign-ins (`state`, PKCE verifier, provider, what they are for) are kept in memory for 10 minutes and used once; a restart drops them. Tokens, codes and verifiers are never logged.

## Config

Optional TOML file (`-c holtmail.toml` or `HOLTMAIL_CONFIG`). Every key has a default:

```toml
listen = "127.0.0.1:8080" # HOLTMAIL_LISTEN
data_dir = "data" # HOLTMAIL_DATA_DIR: holtmail.db, index/, blobs/
web_dir = "apps/web/dist" # HOLTMAIL_WEB_DIR: serve the built web app; unknown paths get index.html
# sync_interval_minutes = 15 # HOLTMAIL_SYNC_INTERVAL: accounts without their own interval; 0 syncs them only on request; when set, the web app cannot change it
# image_proxy = "socks5h://127.0.0.1:9050" # HOLTMAIL_IMAGE_PROXY: outbound proxy for remote images
# tls_ca_file = "/etc/holtmail/ca.pem" # HOLTMAIL_TLS_CA_FILE: extra CA certificates for outbound TLS
# public_url = "https://mail.example.com" # HOLTMAIL_PUBLIC_URL: also where WebDAV-Push notices are posted

[watch]
enabled = true # HOLTMAIL_WATCH: watch accounts whose servers push (IMAP IDLE, JMAP, WebDAV-Push); false leaves the intervals
parallel_syncs = 4 # accounts syncing at once, 1 to 64

[aliases]

sync_interval_minutes = 360 # list every connected alias service's aliases; 0 only on request

# addy_signing_domains = ["addy.example.org"] # self-hosted addy.io or custom domains
# relay_domains = ["relay.example.org"] # self-hosted Firefox Relay
# [[aliases.rules]] provider, domains, header, alias_header, sender_header, signing_domains; see "Email aliases"

[insights]
enabled = true # HOLTMAIL_INSIGHTS: read codes, unsubscribe links and the like out of archived mail; false computes and serves none
extractors = [
  "unsubscribe",
  "schemaorg",
  "pass",
  "parcel",
  "links",
  "code",
] # which to run; they always run in this order
# show_possible.code = 500 # also show Possible items of a kind scoring at least this; Likely and Certain only by default
import_authserv_ids = [] # authserv-ids trusted for imported mail; none by default
one_click = true # false sends no one-click unsubscribe requests (the kill switch)
# one_click_test_networks = ["11.88.77.0/24"] # only in builds with the insights-test-data feature

[insights.categories]
health = true # false derives and shows no health topic
sources = ["signals", "domains"] # voters; signals always votes, domains is the bundled table
update = false # true checks for signed category data releases weekly
data_sources = ["wikidata"] # downloaded tables to use; add "ut1" (CC BY-SA 4.0) to opt in
# update_base_url, update_hosts, update_interval_secs, update_delay_secs: only in builds with the insights-test-data feature

[write]
enabled = true # false: nothing is written to any mail, contacts or calendars server, whatever accounts allow
send = true # false: no mail is sent
rules = true # false: no rule flow runs
undo_seconds = 10 # how long a queued message waits so it can be undone

# [oauth.google] and [oauth.microsoft]: public_client, client_id, client_secret, redirect_url, authorize_url, token_url,
# imap_host, imap_port, and for Microsoft graph_url; see "Gmail and Microsoft sign-in"

[blobs]
kind = "fs" # blobs in <data_dir>/blobs
# kind = "fs_at", path = "/mnt/mail"
# kind = "s3", bucket = "holtmail", region = "eu-central-1",
#   endpoint = "https://s3.example.com", prefix = "archive", path_style = true
```

`[write]` switches sit above the per-account capabilities: an account allows nothing until an owner or admin turns its capabilities on (`mail.flags`, `mail.move`, `mail.delete`, `mail.expunge`, `mail.append`, `mail.send`, `pim.edit`, `pim.respond`), and a switch set to `false` closes its capabilities on every account without changing what is stored, so turning it back on restores them. The server also removes `Idempotency-Key` records older than 24 hours every hour.

`tls_ca_file` names a PEM file of CA certificates that every outbound TLS connection trusts besides the built-in roots: IMAP (the Mozilla roots), and JMAP, CardDAV/CalDAV, Microsoft Graph, OAuth token endpoints, S3 and remote images (the system's roots). It is for self-hosted servers with a private CA. Verification stays on: a server still needs a certificate for the name it is reached by, signed by a trusted CA; there is no switch to accept any certificate. Every command reads it at start and refuses to run when the file is missing or holds no certificate.

S3 credentials come only from `HOLTMAIL_S3_ACCESS_KEY_ID` and `HOLTMAIL_S3_SECRET_ACCESS_KEY`, never from the file. Unknown keys are an error, so a typo does not silently fall back to a default.

## Logs

`RUST_LOG` sets the level (`info` by default). Logs carry counts, ids and errors, never message content, addresses, passwords, session tokens or OAuth codes and tokens. The one exception is the setup link above, which is how the owner is bootstrapped.

## Serving to clients

```toml
[serve]
tls_cert = "/etc/holtmail/fullchain.pem" # both or neither; shared by the protocol listeners
tls_key = "/etc/holtmail/privkey.pem"
proxy_protocol = false # PROXY v2 from trusted_proxies only
trusted_proxies = ["10.0.0.0/8"] # also trusted for X-Forwarded-For on HTTP
members = true # false: only the owner and admins make devices
```

`src/config.rs` refuses a section that cannot work at start: `tls_cert` without `tls_key`, `proxy_protocol` without `trusted_proxies`, an entry that is not an IP address or CIDR range, or certificate files that cannot be read. A renewed certificate is picked up within a minute without a restart (`holtmail_serve_net::TlsCertificates::watch`). `serve` builds [`LocalDeviceAuth`](../../../crates/device-local/docs/README.md) and gives it to the API. The other protocol listeners arrive with their phases ([SERVE.md](../../../docs/SERVE.md)).

### SMTP submission

```toml
[serve.submit]
listen_tls = ["0.0.0.0:465"] # TLS from the first byte; needs [serve] tls_cert
listen_starttls = ["0.0.0.0:587"] # needs tls_cert too, unless every address is loopback
undo_seconds = 0 # the client already had its own chance
messages_per_hour = 200 # per user, across their devices
recipients_per_day = 2000
# hostname = "mail.example.org"   # the greeting; the host of public_url by default
```

Without this section no listener starts. `src/submit.rs` builds [`OutboxSubmission`](../../../crates/submission-outbox/docs/README.md), which the API's send handler uses whether or not submission is on, and [`SubmitServer`](../../../crates/serve-submit/docs/README.md) on each address. The instance's token for the [loop guard](../../../docs/SERVE.md#loops) is made once and kept in the `instance_token` setting, so a restored backup is the same instance; every SMTP transport refuses a server greeting with it. Clients sign in with their email address and a device's app password.

## Behind a reverse proxy

Terminate TLS in the proxy, pass `Host` through unchanged, set `X-Forwarded-Proto`, and set `public_url` to the https address. Writes are refused when the browser's `Origin` does not match `Host`. Sign-in attempts are rate-limited per client address and email; behind a proxy every client shares the proxy's address, so the limit is effectively per email, unless the proxy is listed in `[serve] trusted_proxies`: then its `X-Forwarded-For` gives each client its own count.
